## 总览

KodaX 当前 AMA harness 是一条 4 节点流水线（Scout → Planner → Generator → Evaluator），由 [`managed-protocol.ts:118-148`](../../packages/coding/src/managed-protocol.ts#L118-L148) 的 `H0_DIRECT / H1_EXECUTE_EVAL / H2_PLAN_EXECUTE_EVAL` 三档枚举驱动。FEATURE_084（v0.7.26）把它从文本协议升级到 Layer A 原语；FEATURE_097（v0.7.34）把 `execution_obligations` 接到 TodoListSurface。

但同时存在**第二条架构债**：当前 [`dispatch-child-tasks.ts:114`](../../packages/coding/src/tools/dispatch-child-tasks.ts#L114) 走 `await executeChildAgents([bundle], ctx, options)` 同步阻塞——主 Worker 派 child 后必须等 child 跑完才能继续。child 跑长任务（npm test 90s）时 Worker 完全空闲，用户插话只能 pending 等到 turn 末。**5 codebase 调研**（[multi-agent-async-orchestration-deep-dive.md](../../../tmp/multi-agent-async-orchestration-deep-dive.md)）确认这是 KodaX 当前的核心架构债。

**六个独立但同期 ship 的 Feature**：

- **FEATURE_114（AMA Harness V2）**：Worker+Evaluator 二角色重构。**Evaluator 保留为 structural gate**——5 轮调研事实证明这是 KodaX 比 Claude Code 强的护城河，绝不替换为 Claude Code 风格的 opportunistic verification nudge。
- **FEATURE_115（Message Queue Foundation）**：agentId-scoped 2 档优先级队列 + Sleep-gated mid-turn drain。是 v0.7.39 FEATURE_120（SendMessage/TaskStop）/ v0.7.44 FEATURE_123（Peer-to-peer SendMessage）的底座；本版本同时**吸收 FEATURE_111 soft-pause 的 UX 能力**（FEATURE_111 设计文档保留为历史，实现统一走 message queue）。
- **FEATURE_119（Async Child Dispatch — Pattern B）**：把 `dispatch_child_task` 拆成 `dispatch_child_task` (launch, 立即返回 task_id) + `await_child_task(task_id)` (poll, Worker 显式 await)。`KodaXToolExecutionContext` 新增 `childTaskRegistry: Map`。是 5 轮调研推荐方案——**用 ~100 行代码解决 Pattern A (Coordinator/Worker 分层) 用 ~1500 行解决的同一问题**。
- **FEATURE_130（Provider Retry-After + Exponential Backoff）—— Async Safety Pack 之一**：跨 12 provider 标准化处理 4 个 retry-after header 形态（`Retry-After: <seconds>` / `Retry-After: <HTTP-date>` / Anthropic `retry-after-ms` / 无 header → exponential backoff fallback）+ UI 倒计时 status push。**必须与 FEATURE_119 同期 ship**——Pattern B 多 child 并行直接拉高 429 概率，单 ship 119 = ship known regression（特别是 5 个共享 quota 的 coding plan provider：kimi-coding / zhipu-coding / mimo-coding / ark-coding / minimax-coding）。
- **FEATURE_131（Tool Safety Patch Pack）—— Async Safety Pack 之二**：两个独立修复合一打包。Part A: file-mutation-queue.ts（path-keyed 串行队列）防 119 多 child 同文件 race 静默丢改动；Part B: edit-diff.ts:normalizeForFuzzyMatch（NFKC + smart quotes / em-dash / 全角字符 → ASCII）解决 KodaX 实战 silent edit-fail 主因（用户从 Word/网页/聊天复制代码 + 输入法自动替换 typographic 字符）。两个 part 独立 ship 都 work，119 落地后两者频率都被放大，合一打包减少 PR review 面。
- **FEATURE_143（Skill UX Upgrade + prompt-overlay 错位修正）**：v0.7.35.1 FEATURE_144 已经把 6 段 capability "missing data" 漂移修完（mcp / skills / project-agents / tool-construction / git-context / project-snapshot），本 feature 只剩 1 段 "position 类" 漂移（`prompt-overlay` 从 user prompt 头迁回 system prompt）+ Skill 用户层 UX 三件（manifest 措辞硬化为 Claude Code 风格强约束 / classic CLI 与 Ink TUI skillsPrompt 构造对齐 / mid-line `/skill:foo` parser）。触发完整 prompt eval 验证 prompt-overlay 位置迁移不退化 worker H0/H1/H2 routing 行为。

六个 feature 都触及核心 runtime 路径，一起 ship 减少 PR 风险面。FEATURE_130/131 是 FEATURE_119 的 Async Safety Pack（独立 feature 但与 119 紧耦合 ship）；FEATURE_114/115 共享 `KODAX_HARNESS_V2` feature flag 双轨保护；FEATURE_143 与其他 5 feature 不在同条路径上，可独立并行。

## FEATURE_114: AMA Harness V2 — Worker + Evaluator (Evaluator Preserved as Structural Gate)

**Status**: Planned
**Priority**: High
**Category**: Internal / Architecture

### 背景

#### 当前 H2 的 5 个结构性矛盾

1. **Plan 被劈成两半**——Scout 的 `execution_obligations` 是真实 plan（TodoStore seed 来自这），Planner 只产出 `success_criteria + constraints`。两个 role 干一件事的两半（[role-prompt.ts:627-669](../../packages/coding/src/task-engine/_internal/managed-task/role-prompt.ts#L627-L669)）。
2. **FEATURE_107 实测证明 Planner 没创造价值**——`benchmark/datasets/h2-plan-execute-boundary/` 跑出 H2-A vs H2-B = **0pp delta**，Planner 引入的 "信息压缩" 假设被否决。
3. **Generator 在 H2 是 dispatcher 不是执行者**——Generator H2 模式下 fan-out 给写子 Agent，自己不写文件。Issue 124 显示这层 fanout 触发率偏低。
4. **Evaluator 时机错位**——当前 Evaluator 在 Generator 全部跑完后跑一次；用户要求的"每个计划节点根据需要加 evaluator"无法表达。
5. **Replan = 全量 reset**——`runner-driven.ts` 中 `revise + next_harness=H2` 触发 `todoStore.reset()` 清空全部 todo。

更关键：**这套结构和 FEATURE_097 的"计划列表可见性"诉求结构性打架**。32c5205（FEATURE_097 P0-followup）用 prompt-only 强制 Scout "EARLY emit"，但 Scout 的 prior 是 "verdict = 调研后产物"，prompt 软对抗一直压不住——review 类任务尤其严重（review 天然先调查后定论）。

#### 三轮深度调研结论

- **Phase 0**（[claude-code-architecture-study.md](../../../tmp/claude-code-architecture-study.md)）：业界 4/4 codebase 一致——单 primary agent + 按需 subagent + 实时 todo UI；KodaX 4 角色 + 3 档在工业界**找不到对应物**。
- **Phase 0.5**（[kodax-capabilities-inventory.md](../../../tmp/kodax-capabilities-inventory.md)）：KodaX 已有 Self-Construction 4 tier + Admission Contract + capability tier，远比初轮调研估计的丰富；MCP 渐进式披露是 KodaX 比 Claude Code 更优雅的设计。
- **Phase 0.6**（[claude-code-actual-usage.md](../../../tmp/claude-code-actual-usage.md)）：Claude Code 的 `'now'` priority 零生产用例；6 个 built-in agent 0 个用 frontmatter mcpServers；Explore 是 hot path（34M+ spawns/week）。
- **Phase 0.7**（[claude-code-multi-agent-deep-dive.md](../../../tmp/claude-code-multi-agent-deep-dive.md)）：Coordinator Mode 和 Team/Swarm Mode 是**两个独立子系统**；Team Mode 整体推迟到 v0.8.10。

#### KodaX Evaluator 是结构性护城河，绝不替换

Phase 0.7 §11 + Phase 0 §12 综合证明：

| 维度 | Claude Code | KodaX 当前 |
|---|---|---|
| Verification 触发 | opportunistic nudge（≥3 todo 关闭后 tool result 加提醒，LLM 可忽略）| **structurally enforced**——`resolveHandoffTarget(generator) → EVALUATOR_AGENT_NAME`，Generator 物理上无法绕过 |
| Verdict 强制 | system prompt 要求 `VERDICT:` 格式，无机制保证 | 必经 `emit_verdict` 工具，schema 强制 verdict 字段 |
| Revision loops | LLM 自决是否再调 verification | Evaluator `revise` 走确定性 routing 回 Generator/Planner |

**结论**：把 Evaluator 换成"按需 Verification subagent"= 把 KodaX 的结构保证降级成 Claude Code 的 prompt 约定。**这是回归不是进步。FEATURE_114 保留 Evaluator 为独立 role**。

### 设计

#### 顶层结构：Worker + Evaluator


#### Plan-first 实现：prompt + nudge，不是 gate

业界 4/4 codebase 一致——**没有 runner-enforced plan-first gate**。Claude Code（最规范的）用 system prompt + TodoWriteTool structural nudge。

**Worker system prompt 核心条款**（伪代码）：

```
You are the Worker — KodaX's single primary agent.

For non-trivial tasks (>=2 distinct execution steps, or any task touching
>=2 files/areas/feature threads), your FIRST tool call MUST be
todo_update to commit your plan.

Trivial tasks (single typo fix, single-line edit, single-question lookup,
pure conversational answer) skip todo_update — answer or execute directly.

If you find mid-task that what looked trivial is actually multi-step,
call todo_update at that moment to retrofit the plan.

todo_update items have an optional evaluator hint:
  { content, status, evaluator: 'none' | 'build' | 'test' | 'lint' }
Mark milestone steps with the appropriate deterministic check; leave
routine steps as 'none'.
```

**Runner-side structural nudge**（[runner-driven.ts](../../packages/coding/src/task-engine/runner-driven.ts) 修改）：

```
After each tool_call, if:
  - tool count since last todo_update >= 5
  - and at least one read/grep/glob has fired
  - and no todo_update has fired this session
Append to tool_result:
  "[nudge] You have read N files without committing a plan.
   If this task is non-trivial, call todo_update now."
```

#### Per-step evaluator：仅 deterministic，不接 LLM-as-judge

`TodoItem` schema 扩展（[todo-store.ts](../../packages/coding/src/task-engine/todo-store.ts)）：

```ts
interface TodoItem {
  id: string;
  content: string;
  status: 'pending' | 'in_progress' | 'completed' | 'failed' | 'cancelled';
  evaluator?: 'build' | 'test' | 'lint' | 'eval-case:X';  // 可选
  sourceObligationIndex?: number;                          // 既有
}
```

**触发**：runner 看到 `todo_update` 把某 item 从 `in_progress` → `completed`，且该 item 有 `evaluator`，自动跑对应 deterministic check：

| evaluator 值 | 命令 | 失败处理 |
|---|---|---|
| `'build'` | `npm run build`（项目级，timeout 90s）| stderr → tool result，标 `failed`，Worker 自决修补 |
| `'test'` | `npm run test --` 或 `npx vitest run <path>` | 同上 |
| `'lint'` | `npm run lint` 或 `tsc --noEmit` | 同上 |
| `'eval-case:X'` | 调 FEATURE_104 prompt eval harness 跑指定 case | 仅 prompt 改动相关节点用 |

**为什么不做 `evaluator: 'judge'` LLM-as-judge**：业界 4/4 不做。Claude Code 的 verification subagent 是末端一次而非 per-step，且内部主要靠 build/test/lint。Per-step LLM-judge 让每个任务的 LLM call 数翻倍，违反 KodaX `CLAUDE.md` minimalist 原则。

#### 4→2 角色衰减的 4 项保护措施

Phase 0.7 调研确认 4→2 是有衰减风险的真实重构。简单删 role 文件会衰减，做对（带 4 项保护措施）净正。

1. **SCOPE COMMITMENT hard rule（FEATURE_106）port 到 Worker prompt**——当前在 Scout prompt 里，要 port 到 Worker prompt 同位
2. **Generator 的 dispatch RULE A/B/C port 到 Worker prompt**——dispatch_child_task 决策规则不丢
3. **Evaluator 仍是独立 agent invocation**——不并入 Worker turn（保持独立 reviewer 视角）
4. **新 invariant `planBeforeMutate`**——替换 FEATURE_101 第 8 项 `harnessSelectionTiming`：Worker 第一个 mutation tool 调用前必须有 `todo_update` **或** 显式 trivial 声明（observe-only severity=`warn`）

#### Replan：iterative，不 reset

| 操作 | 实现 | UI 反映 |
|---|---|---|
| **adjust** | LLM 调 `todo_update` 改当前 in_progress item description / evaluator | 内容变更，状态保留 |
| **insert** | `todo_update` 在当前 item 后插新 item（`inserted_after` 标记）| 新 item 出现，注 "added mid-task" |
| **drop** | `todo_update` 标某 pending item `cancelled` | 划线显示 |
| **branch** | `todo_update` 一次性增删多 item | 列表实时刷新 |

**reset 仅作为兜底**：Evaluator `revise` 不再自动触发 reset；Worker 显式调 `todo_reset(reason)` 工具时才清空。

#### Trivial 路径：自然形式，零额外机制

不写任何 fast path 代码。Trivial 任务的天然形式是：

- LLM 看 system prompt 判断"这是 trivial"
- 直接答 / 直接调一次 tool 结束
- 不调 `todo_update`
- runner loop 在 `finish: 'stop'` 时退出

UI 表现：TodoListSurface 在没有 todo 时**完全不渲染**（既有行为）。

### 验收标准

1. **V2 单 role 跑通基本三类任务**：trivial answer / 多步实现 / review/audit。三类都能 finish，trivial 不调 `todo_update`，多步任务首个 tool call 是 `todo_update`，**review 任务在前 1-2 turn emit 计划列表**（不再后置）。

## FEATURE_115: Message Queue Foundation — agentId-Scoped 2-Tier Priority Queue + Sleep-Gated Mid-Turn Drain

**Status**: Planned
**Priority**: High
**Category**: Internal / Infrastructure

### 背景

#### 当前 KodaX 通信能力的限制

- `pending-inputs.ts` 只支持用户输入 → REPL 单向队列；`MAX_PENDING_INPUTS=5`
- 无 cross-agent 路由（child agent 输出全 inline 进父 tool result）
- 无 mid-turn drain（要等 turn 自然结束）
- FEATURE_111 soft-pause 设计本质是"runner loop 加 paused boolean + tool 边界检查"——是 message queue 的**简化特例**

#### Phase 0.7 实测数据

Claude Code `messageQueueManager` 三档（now/next/later）实际：
- `'now'` priority **零生产用例**（仅 `print.ts:1860` abort 检测）
- `'next'` 是用户命令主路径
- `'later'` 是 task notification（subagent → coordinator）
- agentId-scoped drain + Sleep-gated mid-turn drain 是 correctness 必需

**KodaX 简化为 2 档**：用户级（user）+ 后台级（background），删去无生产用例的 `'now'`。

#### FEATURE_111 absorption

FEATURE_111（v0.7.43 原计划）的 soft-pause UX——单击 ESC tool 边界软暂停 + 文字注入——本质是 message queue 的具体应用：
- ESC → mark Worker `paused=true` → message queue 在 tool 边界 drain
- 文字注入 → 入 queue priority='user' → 下一轮 LLM 调用前 drain

FEATURE_115 message queue 完整实现后，FEATURE_111 设计可**完全用 queue 实现**——FEATURE_111 设计文档保留为历史，实现统一走 queue。v0.7.43 slot 腾出给 FEATURE_124（Memory alignment）。

### 设计

#### 2 档优先级 + agentId routing

```ts
type MessagePriority = 'user' | 'background';

interface QueuedMessage {
  id: string;
  priority: MessagePriority;
  agentId?: string;          // undefined = 主线程；具体值 = subagent
  mode: 'prompt' | 'task-notification' | 'system-reminder';
  content: string;
  enqueuedAt: number;
}

// agentId 路由：
//   主线程 drain agentId === undefined
//   subagent drain mode === 'task-notification' && agentId === currentAgentId
//   slash command 排除在 mid-turn drain（必须 turn 末才处理）
```

#### Sleep-gated mid-turn drain

仿 Claude Code [`query.ts:1551-1566`](file:///c:/Works/claudecode/src/query.ts#L1551) 模式：

```ts
// runner-driven.ts 修改
async function maybeDrainMidTurn(state: RunnerState): Promise<QueuedMessage[]> {
  const sleepRan = state.lastTurnToolUseBlocks.some(
    (b) => b.name === SLEEP_TOOL_NAME
  );
  // 默认只 drain user priority
  // 跑了 Sleep tool 才 drain background（包含 task-notification）
  const maxPriority = sleepRan ? 'background' : 'user';
  return queue.dequeue({
    agentId: state.currentAgentId,
    maxPriority,
  });
}

// 调用点：每个 tool 执行完、下一轮 LLM 调用之前
```

**为什么 Sleep-gated**：防止 background task notification 在 Worker 干主线工作时被处理（Sleep 是显式 yield 信号）。

#### FEATURE_111 soft-pause UX 走 queue 实现

```

  - InkREPL 设 Worker paused=true
  - spinner 文字变 "Paused (waiting for tool to finish)"

当前 tool 跑完后 runner 检查 paused：
  - 走 maybeDrainMidTurn 但跳过实际 drain
  - 等用户输入或继续

用户输入 + Enter：
  - 内容入 queue priority='user', agentId=undefined
  - paused=false
  - 下一轮 LLM 调用前 drain → 注入下一轮 user message（前置 <user-interjected> 标签）

空 Enter：
  - paused=false
  - 不入 queue
  - 下一轮 LLM 调用按原计划继续

paused 期间再按 ESC：
  - 升级为 abort（既有 double-ESC 路径）
```

完全等价 FEATURE_111 设计的 UX，实现机制走更通用的 message queue。

#### Pending-inputs migration

`pending-inputs.ts` 内部从"独立单向队列"重构为"message queue 的 user priority + agentId=undefined 视图"。对外 API（`enqueueInput()` / `dequeueInput()`）保留语义不变。`MAX_PENDING_INPUTS=5` 保留为同 priority 的入队上限。

## FEATURE_119: Async Child Dispatch — Pattern B (Launch + Await)

**Status**: Planned
**Priority**: High
**Category**: Internal / Architecture

### 背景

#### 当前 KodaX dispatch_child_task 同步阻塞问题

[`dispatch-child-tasks.ts:114`](../../packages/coding/src/tools/dispatch-child-tasks.ts#L114) 走 `await executeChildAgents([bundle], ctx, options)` ——主 Worker 派 child 后**必须等 child 跑完**才能继续。child 跑长任务（npm test 90s+）时：
- Worker 完全空闲不可用
- 用户插话只能 pending 等到 turn 末（即使 FEATURE_115 message queue 也无法 drain，因为 Worker 还没拿到 LLM call 机会）
- 不能起新 child 并行
- 不能 abort 单个 child（只能 abort 整个 Worker）

#### 5 codebase 调研结论

[multi-agent-async-orchestration-deep-dive.md](../../../tmp/multi-agent-async-orchestration-deep-dive.md) 调研明确：

| 系统 | 模式 | 主 agent 阻塞 |
|---|---|---|
| Claude Code Coordinator | Fire-and-forget + priority queue + XML notification（Pattern A，~1500 行）| **从不阻塞** |
| OpenCode TaskTool | 有 Effect Fiber 但 task.ts:131 仍 synchronous yield | **总是阻塞** |
| pi-mono agentLoop | Fire-and-forget EventStream | **从不阻塞** |
| Warp | Cancel-on-FollowUp（用户插话直接 kill 重启）| 流式期间 |
| **KodaX 当前** | `await executeChildAgents` | **总是阻塞** |
| **KodaX 推荐 Pattern B** | Launch + Await 拆分（~100 行）| **仅 await 时阻塞** |

调研推荐 **Pattern B**——用 1/15 工作量解决 Pattern A 解决的同一问题，且**符合 KodaX minimalist 哲学**（CLAUDE.md "abstract only after 3+ use cases"）。

### 设计

#### Step 1：拆分 `dispatch_child_task` → launch + await

```typescript
// dispatch_child_task — launch only（不 await）
async function* toolDispatchChildTask(input, ctx): AsyncGenerator<...> {
  // ... validation 不变 ...
  const taskId = `child-${Date.now()}-${randomSuffix()}`;

  // Fire-and-forget: 不 await
  const promise = executeChildAgents([bundle], ctx, options);
  ctx.childTaskRegistry.set(taskId, promise);

  yield { stage: 'launched', message: `Child "${taskId}" launched` };
  return `task_id:${taskId} launched. Use await_child_task("${taskId}") when result needed.`;
}

// await_child_task — 显式 await
async function toolAwaitChildTask(input, ctx): Promise<string> {
  const taskId = input.task_id;
  const promise = ctx.childTaskRegistry.get(taskId);
  if (!promise) return `[Tool Error] Unknown task_id: ${taskId}`;

  const result = await promise;
  ctx.childTaskRegistry.delete(taskId);
  return formatChildResult(result);
}
```

#### Step 2：`KodaXToolExecutionContext` 新增 `childTaskRegistry`

```typescript
// types.ts
interface KodaXToolExecutionContext {
  // ... 既有字段（abortSignal / extensionRuntime / guardrails）...
  childTaskRegistry: Map<string, Promise<KodaXChildExecutionResult>>;  // 新增
}
```

context 跨 Worker turn 持续——Promise 在多个 tool call 之间存活。

#### Step 3：Abort 传播（既有机制）

既有 `abortSignal: ctx.abortSignal` 已传给 `executeChildAgents`。父 abort 时所有 running children 在下次 `signal.throwIfAborted()` 检查停止。**无新 abort 路径**。

#### Step 4：Worker prompt 引导

新增 Worker system prompt 段落：

```
Async child dispatch protocol:
- dispatch_child_task launches a child and returns task_id IMMEDIATELY (does not block).
- After launch, you may continue using other tools, summarize progress, or
  start additional parallel children.
- Use await_child_task(task_id) when you actually need the child's result.
- Do NOT await immediately after dispatching unless you have nothing else to do.
- For multiple parallel children: dispatch all first, then await each in sequence.

Common patterns:
1. Parallel research: dispatch N read-only children → continue analyzing existing
   data → await all when ready to synthesize.
2. Long-running test/build: dispatch child for `npm test` → continue with code edits
   → await after edits done.
3. Verification: dispatch verification child → continue summarizing → await before
   reporting to user.

Synthesis discipline (when fan-out warranted):
- When you launch ≥2 parallel children for research/audit, await all, read
  their summaries, then decide implementation plan — do NOT dispatch
  implementation children based on partial information.
- You ARE the synthesizer. Don't spawn a "synthesis child" — that's your job.
```

替代当前隐式"派 child 必阻塞"行为，改为显式异步协议——类比 Claude Code coordinator system prompt 显式告诉 LLM async worker 协议。

**Synthesis hint 来源**：原 FEATURE_122 PM Thinking Framework（v0.7.41）取消后，把 Synthesis discipline 这一最有价值的 1 行从独立 feature 降级为 worker prompt 微调，合并到本 feature 的 worker dispatch protocol 段落。Continue-vs-Spawn 决策由 send_message vs dispatch_child_task 工具描述自然引导，不需要额外 prompt。

#### Step 5：与 FEATURE_115 message queue 的协同

Worker 在 await_child_task 之间的 tool call 之间，runner 走 `maybeDrainMidTurn`（FEATURE_115）—— **用户插话现在能在 child 跑中被 Worker 接收**：

```
T+0s:  Worker 调 dispatch_child_task(npm test)  → 立即返 task_id, child 在后台跑
T+1s:  Worker 调 read_file(...)                 → 期间 message queue drain check
T+5s:  用户插话 "测试要包含 X 场景" → 入 queue priority='user'
T+5s:  Worker 下一轮 LLM call 看到 user message 注入 → 处理
T+10s: Worker 决定继续 → 调 await_child_task(...)
T+90s: child 完成，await 解锁，Worker 拿结果
```

**这是 FEATURE_115 + FEATURE_119 联合产生的核心 UX 提升**：Worker 不再阻塞，用户 ESC 软暂停 + 文字注入 + 长 child 后台跑可以**同时**工作。

### 影响范围

**新增**：

- `packages/coding/src/tools/await-child-task.ts`：新工具实现（~50 行）
- `packages/coding/src/types.ts`：`KodaXToolExecutionContext.childTaskRegistry` 字段

## FEATURE_130: Provider Retry-After Header + Exponential Backoff

**Status**: Planned
**Priority**: High
**Category**: Internal / Robustness

### 背景

KodaX 当前 12 provider 处理 rate-limit / overload 的策略不统一——大多数 provider adapter 没有标准化的 retry-after header 感知，遇到 429 / 503 大概率走 timeout 或直接 throw 给用户。FEATURE_119 (Pattern B) 落地后，Worker 一次响应里可以 `dispatch_child_task` N 个 child 并行调 provider，**直接放大 rate-limit 触发概率**。

特别危险的是 5 个共享 quota 的 coding plan provider：

- `kimi-coding` / `zhipu-coding` / `mimo-coding` / `ark-coding` / `minimax-coding`

同一 plan 多 session、多 child 互相抢 quota，没有标准化 retry 策略 = 119 落地即用户高频踩坑"为什么我的 Worker 派了 3 个 child 全 timeout 了"。

业界范式参照 opencode `session/retry.ts:14-123`——4 个 retry-after header 形态全覆盖（`Retry-After: 120` 秒数 / `Retry-After: HTTP-date` / Anthropic 扩展 `retry-after-ms` 毫秒精度 / 无 header 走 exponential backoff fallback）。

### 设计

#### 公共 helper：`@kodax/ai/src/retry/retry-after.ts`

```typescript
type RetryAfterResult =
  | { type: 'header'; waitMs: number; source: 'retry-after-seconds' | 'retry-after-date' | 'retry-after-ms' }
  | { type: 'backoff'; waitMs: number; attempt: number };

interface ParseRetryAfterOptions {
  attempt: number;          // 用于 exponential backoff
  baseBackoffMs?: number;   // default 1000
  maxBackoffMs?: number;    // default 30000
}

function parseRetryAfter(
  headers: Headers | Record<string, string>,
  options: ParseRetryAfterOptions
): RetryAfterResult;
```

支持 4 个形态：

- `Retry-After: 120` —— 秒数（HTTP 标准）→ `{type: 'header', waitMs: 120000, source: 'retry-after-seconds'}`
- `Retry-After: Wed, 21 Oct 2026 07:28:00 GMT` —— HTTP-date → 计算到该时间点的差值
- `retry-after-ms: 45000` —— Anthropic 扩展毫秒
- 无 header → exponential backoff `min(baseBackoff * 2^attempt, maxBackoff)`

#### 12 provider adapter wire-level 接入

每个 provider 在 stream loop 的 catch 429 / 503 处加（伪码，具体接入点因 provider 而异）：

```typescript
catch (err) {
  if (isRateLimit(err) || isOverloaded(err)) {
    const retry = parseRetryAfter(err.response?.headers ?? {}, { attempt });
    ctx.events?.onRetryAfter?.({
      provider: this.name,
      waitMs: retry.waitMs,
      reason: err.status === 429 ? 'rate-limit' : 'overloaded',
      source: retry.type === 'header' ? retry.source : 'exponential-backoff',
    });
    await sleep(retry.waitMs, { abortSignal });
    continue;  // retry
  }
  throw err;
}
```

#### UI 倒计时 status push

新增 `KodaXEvents.onRetryAfter?(payload)` 事件，InkREPL spinner 文字：

```
[⠋] Rate limited (zhipu-coding) — retrying in 45s... (3 child also waiting)
```

让用户**明确知道**不是 KodaX 卡死、不是 bug、是 quota 等待。

### 影响范围

**新增**：

- `packages/ai/src/retry/retry-after.ts` —— ~80 行 helper + 类型
- `packages/ai/src/retry/retry-after.test.ts` —— 4 个 header 形态 + exp backoff 单测
- `tests/provider-retry-after.eval.ts`（可选）—— mock 429 response 验证 12 provider 全部正确解析

**修改**：

- 12 provider adapter 各 ~10-15 行 wire（`packages/ai/src/providers/*.ts`）
- `packages/ai/src/types.ts` 加 `KodaXEvents.onRetryAfter?` 事件
- `packages/repl/src/ui/InkREPL.tsx` spinner 文字读 retry 状态
- `packages/coding/src/agent.ts` cost tracker 记录 retry 次数

**不改动**：

- 既有 abort signal 路径
- provider stream protocol（仅 catch 后加 retry）
- 既有 timeout 配置

### 与 FEATURE_119 的强耦合

| 119 状态 | 130 状态 | 风险 |
|---|---|---|
| Ship 119, 不 ship 130 | — | **High** —— 多 child 并行触发 429 集体 fail，用户感知"119 让事情更糟" |
| 130 single ship | 119 不 ship | 低收益（单 child 触发 429 概率不高，但 130 helper 仍有用）|
| **119 + 130 同期** | — | **正确范式** —— 119 的并行优势 + 130 的 graceful degradation |

故 v0.7.36 FEATURE_LIST 明确"必须与 FEATURE_119 同期 ship"。

### 验收标准

1. **4 个 header 形态全识别**：`tests/retry-after.test.ts` 覆盖 `Retry-After: <seconds>` / `Retry-After: <HTTP-date>` / `retry-after-ms: <ms>` / 无 header 四类，全部正确返 waitMs
2. **12 provider 接入完整**：mock 429 response 跨 12 provider 全部触发 retry（不是直接 throw）
3. **UI 倒计时显示**：触发 retry 时 InkREPL spinner 文字含倒计时秒数
4. **Abort signal 仍然 work**：用户在 retry sleep 中按 ESC，立即中断不等 sleep 完成
5. **Cost tracker 记录 retry**：`/cost` 命令显示总 retry 次数和累计 wait 时长
6. **与 FEATURE_119 联动**：3 个 child 并行触发 429 时，3 个 child 都看到独立倒计时（不互相阻塞）
7. **无回归**：既有 200 / 400 / 401 / 500 错误路径行为不变

### 非目标

- **不** 实现 client-side rate limiter（不预测 quota，只 react retry-after header）
- **不** 跨 provider 智能切换（FEATURE_102 v0.7.45 做）
- **不** 持久化 retry budget（重启清零）
- **不** 自动降级到 fallback model（无 header 信号支持）
- **不** UI 加 retry 暂停/取消按钮（ESC 已是统一暂停入口）

## FEATURE_131: Tool Safety Patch Pack — File Mutation Queue + Edit Unicode Normalization

**Status**: Planned
**Priority**: High
**Category**: Core / Tool Safety

### 背景

两个独立修复合一打包——都是 FEATURE_119 (Pattern B) 落地的伴生品。

#### Part A：File Mutation Queue（同文件 race 防护）

FEATURE_119 落地后，Worker 可以同时 dispatch 多 child 并行写文件——典型场景"派 2 个 child 修同一文件的 2 处 bug"。当前 KodaX 没有 file-level mutation lock，**两个 child 的 read-modify-write 可能 race**：

```
T+5s:  child-1 read src/auth.ts → 拿到 v1
T+6s:  child-2 read src/auth.ts → 拿到 v1
T+8s:  child-1 write src/auth.ts ← 基于 v1 改 line 45 → 文件变 v2
T+9s:  child-2 write src/auth.ts ← 基于 v1 改 line 78 → 文件变 v3，丢失 child-1 的 line 45 改动
```

业界范式参照 pi-mono `file-mutation-queue.ts`——**path-keyed 串行队列**：同 path 的 mutation 排队执行，不同 path 仍然并行。

#### Part B：Edit Unicode Normalization（解决 silent edit-fail 高频痛点）

KodaX edit / multi_edit 工具走精确字节匹配——但用户从 Word / 网页 / 聊天复制代码到 prompt 时，OS 输入法或来源系统会**自动替换 typographic 字符**：

| 视觉相同 | 实际字节 | Edit tool 行为 |
|---|---|---|
| `"foo"` | smart quotes (U+201C/U+201D) vs ASCII quotes (U+0022) | 找不到 → silent fail |
| `a -- b` | em-dash (U+2014) vs 两个 hyphen (U+002D) | 找不到 → silent fail |
| `arr.length` | 全角句号 (U+3002) vs ASCII period | 找不到 → silent fail |
| `key: value` | 全角冒号 (U+FF1A) vs ASCII colon | 找不到 → silent fail |
| `import X` | nbsp (U+00A0) vs ASCII space | 找不到 → silent fail |

**这是 KodaX 实战 silent edit-fail 的主因之一**——edit 工具跑过、tool result 看起来正常、但文件实际没改、用户以为做了实际没做。

业界范式参照 pi-mono `edit-diff.ts:normalizeForFuzzyMatch`——**精确匹配先试，失败时启用 normalize 后再 fuzzy match，但写入仍用原 new_string 字节**（不污染用户实际 quotes 风格）。

#### 为什么合一 ship

两个修复**实现独立、风险等级相同（low）、都是 119 Pattern B 落地的伴生品**：

- A 是 119 多 child 并行写入触发的 race（行为放大）—— 119 不 ship 时也存在但概率低
- B 是 119 落地后 child agent LLM 输出更频繁触发的 silent edit-fail（频率放大）—— 119 不 ship 时也是高频痛点

合一打包比拆两个 feature 更省：单次 prompt eval 只需要一份，两个 part 都是 low-risk 编译器 + 单测兜底。

### 设计

#### Part A：path-keyed mutation queue

新建 `packages/coding/src/tools/_internal/file-mutation-queue.ts`：

```typescript
const fileMutationQueue = new Map<string, Promise<unknown>>();

export async function withFileMutation<T>(
  absolutePath: string,
  fn: () => Promise<T>
): Promise<T> {
  const normalizedPath = normalizePathForKey(absolutePath);  // case-insensitive on Windows
  const previous = fileMutationQueue.get(normalizedPath) ?? Promise.resolve();
  const next = previous.then(fn).finally(() => {
    if (fileMutationQueue.get(normalizedPath) === next) {
      fileMutationQueue.delete(normalizedPath);
    }
  });
  fileMutationQueue.set(normalizedPath, next);
  return next as Promise<T>;
}
```

接入 write / edit / multi_edit / insert_after_anchor 4 个 mutation tool：

```typescript
// tools/edit.ts 等
const result = await withFileMutation(absolutePath, async () => {
  // 既有 read-modify-write 逻辑
});
```

- 同 path 的 mutation **串行**（即使来自不同 child / 不同 tool）
- 不同 path 仍然**并行**
- 队列粒度 = 进程级 process-global Map
- 队列**不**跨 KodaX 进程（多 KodaX 实例的多进程协作走 v0.7.41 FEATURE_125 content-hash safety net）

#### Part B：edit fuzzy match unicode normalize

修改 `packages/coding/src/tools/_internal/edit-diff.ts`——加 `normalizeForFuzzyMatch` helper：

```typescript
function normalizeForFuzzyMatch(text: string): string {
  return text
    .normalize('NFKC')                  // 全角 → 半角，CJK compat → 标准
    .replace(/[“”]/g, '"')    // smart double quotes → ASCII
    .replace(/[‘’]/g, "'")    // smart single quotes
    .replace(/[–—]/g, '-')    // en-dash / em-dash → ASCII -
    .replace(/ /g, ' ')            // nbsp → space
    .replace(/　/g, ' ');           // 全角空格 → 半角
}
```

接入策略：

1. **精确匹配先试**——`old_string` 字节级在 `file content` 出现 → 直接用
2. **精确匹配失败 + 既有 fuzzy match 失败时启用 normalize**——needle 和 haystack 同时 normalize，用 normalized 字节做 substring search
3. **匹配位置映射回原 offset**——确保 replace 范围正确（normalize 改的是 substring search 视角，不改实际写入）
4. **写入用 `new_string` 原字节**——不污染用户文件的 quotes 风格

⚠️ **关键不变量**：normalize 仅用于 match 决策，**不改写文件实际字节**。

### 影响范围

**新增**：

- `packages/coding/src/tools/_internal/file-mutation-queue.ts` —— ~80 行
- `packages/coding/src/tools/_internal/file-mutation-queue.test.ts` —— 同 path 串行 / 不同 path 并行 / cleanup
- `packages/coding/src/tools/_internal/edit-diff.test.ts` —— normalize 4 类输入（smart quotes / em-dash / 全角 / NFKC）

**修改**：

- `packages/coding/src/tools/write.ts` —— `withFileMutation` wrap
- `packages/coding/src/tools/edit.ts` —— `withFileMutation` wrap + `normalizeForFuzzyMatch` 接入 fuzzy match path
- `packages/coding/src/tools/multi-edit.ts` —— 同上
- `packages/coding/src/tools/insert-after-anchor.ts` —— 同上
- `packages/coding/src/tools/_internal/edit-diff.ts` —— 加 `normalizeForFuzzyMatch` + fuzzy match 路径接入

**不改动**：

- read tool（无 mutation 不需要 queue）
- bash tool（用户自负责 shell 命令的 file race）
- diff display（normalize 只影响 match，不影响 diff 显示——用户看到的还是真实字节差异）

### 与 FEATURE_119 的关系

| 119 状态 | 131 状态 | 风险 |
|---|---|---|
| Ship 119, 不 ship 131 | — | **High (Part A)** —— 多 child 同文件 race 静默丢改动；**Medium (Part B)** —— child agent 触发 silent edit-fail 增频 |
| 131 single ship | 119 不 ship | **Part A** 收益小但仍正确（单进程同 turn 内不会 race）；**Part B** 仍然高价值（解决既有高频痛点）|
| **119 + 131 同期** | — | **正确范式** |

### 验收标准

1. **Part A：同 path mutation 串行**：unit test —— 2 个并发 write 同 path，结果是顺序应用而非 race
2. **Part A：不同 path mutation 并行**：unit test —— 2 个并发 write 不同 path，wall-clock 时间约等于单次（不是 2×）
3. **Part A：cleanup 不泄漏**：unit test —— 1000 次连续 mutation 后 fileMutationQueue.size === 0
4. **Part B：smart quotes match**：edit needle 含 `"foo"`（ASCII），file 含 `"foo"`（U+201C/U+201D）→ fuzzy match 命中，写入后文件保留原 smart quotes 字节（除非 needle 字节级覆盖）
5. **Part B：em-dash match**：edit needle 含 `--`，file 含 `—` → 命中
6. **Part B：全角 match**：edit needle 含 `arr.length`，file 含 `arr。length` → 命中
7. **Part B：精确匹配优先**：file 同时含 ASCII 和 smart quotes 版本时，needle 是 ASCII → 命中 ASCII 版本（不被 normalize 误导）
8. **Part B：写入字节不污染**：edit 把 `"old"`（smart）改成 `"new"`（ASCII），file 其他未涉及 smart quotes 区域字节不变
9. **跨平台 path normalize**：Windows `C:\Foo\Bar` 与 `c:/foo/bar` 视为同一 mutation queue key
10. **无回归**：既有 edit / multi-edit 测试全绿，既有 fuzzy match 测试不退化

- **不** 实现跨进程文件锁（v0.7.41 FEATURE_125 用 content-hash safety net 兜底多 KodaX 实例）
- **不** 实现 OS-level file lock（lock contention 不可控，且 git / IDE 也写文件会冲突）
- **不** 持久化 mutation queue（重启清零，与 TodoStore / message-queue 一致）

- **不** 改 normalize rule list（不开 config —— 4 类典型字符已覆盖 95%+ 痛点，按 KodaX `NEVER add config for hypothetical needs` 哲学）
