## 总览

v0.7.35.1 解决三类**v0.7.36+ 启动前必须清理**的债：

1. **包边界漂移**（v0.7.24 FEATURE_082 设计错位 + 后续实现漂移）：`@kodax/core` 名实倒挂、`@kodax/agent` 定义错位、`@kodax/capabilities` 死设计。本类是结构修复，零业务逻辑改动。
2. **AMA worker capability context 断链**（v0.7.26 FEATURE_084 / v0.7.27 FEATURE_086 后遗症）：`@kodax/coding/src/prompts/builder.ts` 的 13 个 prompt section 中**6 段在 AMA worker 完全漏注入 + 1 段错位**；过去 v0.7.26 / v0.7.27 已经手工补过 5 段（注释里自陈），本次用集中 helper 终结这种"每加新 capability 就静默漏一遍 worker"的反复回归。本类含行为修复（worker 多看到 4 段已存在的 system context），需 prompt eval 配合验证。
3. **Substrate consumer 无法重定向 config dir 的耦合**：当前 `~/.kodax/` 在 6 个包共 ~30 处硬编码（仅 1 处有 `KODAX_HOME` env var 兜底），导致 `@kodax/agent` 作为通用底座被未来 consumer agent（如 `@kodax/ops-agent`）调用时无法重定向 config dir。本次抽 3-tier resolution helper（DI 入参 > env var > hardcoded default），DI 不传时与现状字节级等价。本类零行为变更。

三类合并 ship，让 v0.7.36 AMA Harness V2 能在**包边界正确 + AMA worker 与 SA path capability 视野等价 + agent config home 可被 substrate consumer 重定向**的基线上推进。

修复目标：

- `@kodax/agent` 重新正名为**通用 Agent 框架（智能体底座）**
- `@kodax/coding` 严格对应 **coding-specific** 的工具、prompt、H2 状态机
- `@kodax/core` 撤销（设计漂移，无独立责任面）
- `@kodax/capabilities` 撤销死设计（FEATURE_082 设计但从未创建包）
- `@kodax/session-lineage` 承接 session 实体回流（保持现有职责，扩充内容）
- **AMA worker（Scout / Planner / Generator / Evaluator）capability context 与 SA path 等价**：6 段 "missing data" 漂移一次性全清——mcp-capability-context / skills-addendum / project-agents（AGENTS.md/CLAUDE.md）/ tool-construction / git-context / project-snapshot；其中 git-context / project-snapshot 通过新增 parent cache 字段实现，避免每 worker 重复 FS load。`prompt-overlay` 错位（属 position 类，数据已传到 worker 只是位置不对）留 v0.7.36 FEATURE_143 配合 prompt eval 处理
- **Agent config home 3-tier resolution**：~30 处分散硬编码 `~/.kodax/` 集中到 `@kodax/agent/runtime/agent-home.ts` helper，3 层优先级（DI 入参 > `KODAX_HOME` env var > `~/.kodax/` hardcoded default）。DI 入参支持 substrate consumer agent 在 boot 时调 `setAgentConfigHome(path)` 一次性重定向整个进程的 config dir，无需发明 brand 抽象

## FEATURE_142: Package Boundary Cleanup — `@kodax/core` Removal & `@kodax/agent` Reaffirmation

**Status**: Planned
**Priority**: Critical（v0.7.36+ 全部 feature 的前置）
**Category**: Internal / Refactor

### 背景：FEATURE_082 漂移分析

v0.7.24 FEATURE_082 设计稿要建立 `ai → core → capabilities → coding` 的 4 层模型，并定义 `@kodax/agent` 为 "coding-specific session / extension runtime"。两年回看，这个设计在两个维度发生漂移：

#### 设计漂移（FEATURE_082 设计本身的错误）

| # | 漂移点 | 实证 |
|---|---|---|
| D1 | `@kodax/agent` 定义为 coding-specific | 与"coding 包才是 coding-specific"的自然读法直接矛盾；让 agent 与 coding 边界靠"装会话还是装工具"任意切分 |
| D2 | `@kodax/core` 单独成包的理由建立在 D1 之上 | 因为 agent 被错误定位为 coding-specific，"通用 agent 入口"无处可放，才被迫新开 core |
| D3 | `@kodax/capabilities` 设计为 Layer B 包 | `packages/capabilities/` **从未被创建**；FEATURE_084 v0.7.26 真要落 Scout/Evaluator 时绕开该包，直接放 `coding/src/agents/`——证明"通用 capabilities"是预先抽象 |
| D4 | 4 层模型违反 KodaX `NEVER add abstractions until 3+ concrete use cases` | 082 落地时只有 1 个真实 consumer（coding），却建了 4 层；capabilities 死包 + core 后续被 runtime 漂移填满，是 3+ rule 违反的实证后果 |

#### 实现漂移（082 之后落地偏离设计）

| # | 漂移点 | 实证 |
|---|---|---|
| I5 | runtime 漂入 `@kodax/core` | v0.7.26 FEATURE_084 / v0.7.31 FEATURE_101 把 createAgent 工厂、Runner class、Admission runtime、invariants 实现陆续加进 core；core 从"types + 少量基础实现"漂成"完整 agent runtime（误命名）" |
| I6 | Scout/Evaluator/Generator 进 coding 而非 capabilities | 表面是漂移，结果上**做对了**（这些是 coding AMA H2 实例，本来就该在 coding）——反而修复了 D3 |
| I7 | `@kodax/agent/package.json` 描述被改错 | 现描述写"通用 Agent 框架"，与 082 设计稿的"coding-specific"矛盾，又与实际内容（仅 session/persistence/compaction/tokenizer）也对不上——典型的语义自欺 |

#### 当前状态总结

| 包 | FEATURE_082 设计角色 | package.json 描述 | 实际内容 | 三方一致性 |
|---|---|---|---|---|
| `@kodax/core` | Layer A types + DefaultSummaryCompaction | "Layer A primitives" | createAgent 工厂 / Runner class / Admission runtime / invariants 实现（30 文件） | ❌ 设计错位 + 描述对、实现漂移 |
| `@kodax/agent` | coding-specific session / extension runtime | "通用 Agent 框架" | session.ts / persistence.ts / compaction/ / tokenizer.ts（10 文件） | ❌ 设计错位 + 描述自欺 + 实现淘空 |
| `@kodax/capabilities` | Layer B 组合能力包 | — | **包不存在** | ❌ 设计成死包 |

#### Batch C — Self-Construction 性质重判：留在 coding（v0.7.35.1 实施期审计修订）

**原方案（已弃）**：迁 `coding/src/construction/` 整体到 `@kodax/agent/construction/`，仅拆 `agent-resolver.ts`。

**实施期 grep 审计发现**：原方案对 construction 性质判断错误。

| 文件 | coding-side 引用 |
|---|---|
| `agent-resolver.ts:51` | `getRegisteredToolDefinition` |

**性质重判**：FEATURE_087/088 self-modify 不是"通用 Agent 平台能力"，是"**coding tool ecosystem 的 self-modify 子系统**"——agent 在运行时创造新的 coding 工具、注册进 coding TOOL_REGISTRY、用 coding ctx 执行、过 coding auto-mode permission。OpenAI Agents SDK / Anthropic Agent SDK / LangChain / LangGraph 都不把 self-modify 列为 primitive，原因结构性：每个 agent 的 tool space 由领域决定，self-modify 必然是领域能力。

**决定**：construction 留在 `@kodax/coding/src/construction/`。

| 来源 | 处理 |
|---|---|
| `@kodax/coding/src/construction/`（全 41 文件） | **保留**原位 |
| `agent-resolver.ts` 拆分 | **不拆**（拆 DI adapter 撞 KodaX 3+ rule，仅 1 个 consumer 强抽象是 YAGNI）|
| `@kodax/coding/src/tools/{construction,self-modify-tool}.ts` | **保留**原位 |

**未来兼容**：当出现第二个 agent 实例（如 `@kodax/data-analysis-agent`）也想要 self-modify 时，它会有自己的 tool ecosystem（不同 ctx / 不同 permission 模型），其 construction 实现与 coding 的**共享概念但不共享代码**——届时再看是否值得抽通用层。当前 1-consumer 状态下不预先抽。

**实现简化说明**（vs 原设计稿）：

设计稿提议在 `KodaXContextOptions` 加 `gitContextSnapshot` + `projectSnapshotSnapshot` 两个 public 字段 + 改 `builder.ts` cache-first 逻辑，以让 SA path 也能复用缓存。实施时简化为：

- **不新增 public type 字段**：FS-load 重复关心仅在 AMA 路径成立（SA 每 session 仅渲染一次），所以缓存只需在 AMA 入口闭包变量内做即可。
- **不改 `builder.ts`**：保持 SA 路径 byte-equivalent（FEATURE_142 Batch E 的字节级契约不被打破），无 regression 风险。
- **runner-driven.ts 一次构建** `prebuiltCapabilityContextBlock` 后供同一 AMA entry 内所有 worker 复用（FS load 上限 = 每 AMA entry 1 次，与 N 个并发 worker 无关）。
- 满足 KodaX `NEVER add abstractions until 3+ concrete use cases`：当前只有 AMA 一个 consumer 需要"parent cache for many workers"模式，public 字段是预先抽象。

数据流（实施版）：

```
parent dispatch AMA worker（runner-driven.ts AMA entry）
  ↓
runner-driven.ts:4485 一次性调 buildCapabilityContextSections(options, isNewSession, executionCwd)
  ↓
filter 出 7 段 AMA-owned section（环境/工作目录/runtime-fact 已经在 workspaceSection；
                              repo-intel 已通过 prebuiltRepoIntelligenceContext；
                              prompt-overlay 已通过 Shard 6d-L stitching）
  ↓
join 剩 6 段成 prebuiltCapabilityContextBlock（闭包变量）
  ↓
rolePromptContextFactory 把 block 传入每个 role 的 ManagedRolePromptContext
  ↓

  ↓
4 个 role（Scout/Planner/Generator/Evaluator）system prompt 全部含 6 段 capability context
```

每 AMA entry FS load 上限：1 次。N 个 worker 并发不增加 IO。

**为什么不在 Batch E 同时做**：Batch E 是结构-only 重构（dedup + 输出字节级相同），Batch F 是行为修复（worker 多看到 6 段 system context + 新增 parent cache 字段）。两者性质不同，分 Batch 后 git bisect 时能干净区分"helper 抽出导致的 regression"vs"worker 接通导致的 regression"。

- `prompt-overlay` 错位修正 = 把它从 user prompt 移到 system prompt = 改 prompt 结构。worker 当前 prompt 已经在 user prompt 头看到 routing notes，迁移可能影响 routing decisions（H0/H1/H2 判断）的下游行为。
- 这一段的数据**已经能传到 worker**（只是位置不对），与本 Batch 修的"data missing"问题性质不同。
- 留给 v0.7.36 FEATURE_143 配合"加强版 prompt eval（位置迁移前后行为对比）"一起做。FEATURE_143 已经要跑 prompt eval（manifest 措辞硬化触发），多加这一项零边际成本。

**风险与保障**：

## FEATURE_145: Agent Config Home Resolution Pipeline — 3-Tier Priority (DI / Env / Default)

**Status**: Planned（与 FEATURE_142 / FEATURE_144 同 v0.7.35.1 patch release ship）
**Priority**: Medium
**Category**: Internal / Refactor

### 单 Batch 设计：Batch G

#### Batch G — Agent Config Home 集中（必做，零行为变更）

**问题**：当前 ~30 处直接调 `path.join(homedir(), '.kodax', ...)` 硬编码 user-config 目录，分散在 6 个包：

| 包 | 硬编码点数 | 是否有 env 兜底 |
|---|---|---|
| `@kodax/ai` | 1（reasoning-overrides） | ✅ `KODAX_HOME` env var（**唯一做对的一处**） |
| `@kodax/coding` | ~10（compaction / construction×4 / agents-loader / auto-mode rules / repo-intelligence / tool-truncate） | ❌ 全部硬编码 |
| `@kodax/mcp` | 2（catalog cache / oauth tokens） | ❌ 硬编码 |
| `@kodax/repl` | 8（utils.KODAX_DIR / commands / compaction / permission / paste-cache / memory-diagnostics / config） | ❌ 硬编码 |
| `@kodax/session-lineage` | 1（extension-store） | ❌ 硬编码 |
| `@kodax/skills` | 3（discovery / types / install-script） | ❌ 硬编码 |

**两层后果**：

1. **漂移风险**：30 处分散硬编码没有单一来源；下次往哪个包加新 fs path，又是一处硬编码（同 v0.7.26 capability section 漂移 pattern）。
2. **Substrate consumer 耦合**：当 `@kodax/agent` 作为通用底座被未来 consumer agent（如 `@kodax/ops-agent` / `@kodax/data-analysis-agent`）调用时，无法重定向 config dir，**强制所有 derivative agent 共享 `~/.kodax/` 命名空间**——品牌语义错位 + 同机多 agent 共存时 config 互相冲突。

**修法**：3-tier resolution helper

新建 `@kodax/agent/src/runtime/agent-home.ts`（~30 LoC）：

```ts
import { homedir } from 'os';
import { join } from 'path';

const DEFAULT_DIRNAME = '.kodax';

let _programmaticOverride: string | undefined;

/**
 * Set the agent config home programmatically. Highest priority.
 *
 * Substrate consumers (e.g. an agent built on top of @kodax/agent) should
 * call this once at process boot, before any subsystem reads the path.
 * Pass `undefined` to reset (used in tests).
 */
export function setAgentConfigHome(path: string | undefined): void {
  _programmaticOverride = path;
}

/**
 * Resolve the agent runtime config home directory.
 *
 * Priority (high → low):
 *   1. Programmatic override via setAgentConfigHome()  — substrate consumer
 *   2. KODAX_HOME env var                              — user / shell / CI
 *   3. ~/.kodax (hardcoded default)                    — standalone kodax CLI
 */
export function getAgentConfigHome(): string {
  if (_programmaticOverride) return _programmaticOverride;
  if (process.env.KODAX_HOME) return process.env.KODAX_HOME;
  return join(homedir(), DEFAULT_DIRNAME);
}

/** Resolve a sub-path under agent home. */
export function getAgentConfigPath(...segments: string[]): string {
  return join(getAgentConfigHome(), ...segments);
}
```

**3-tier 优先级覆盖三类 use case**：

| Tier | 设值方 | 优先级 | use case |
|---|---|---|---|
| 1 | `setAgentConfigHome(path)` 程序入参 | 最高 | substrate consumer agent boot 时 set 一次（`@kodax/ops-agent` 启动调 `setAgentConfigHome('~/.opsagent')`） |
| 2 | `KODAX_HOME` env var | 中 | shell / CI / 测试隔离 / 多用户共享机器 |
| 3 | `~/.kodax/` 硬编码 default | 最低 | standalone kodax CLI（90% 场景，与现状字节级等价） |

**为什么用 process-level singleton 而非 per-call DI**：30 处 fs 调用深嵌在 library helper 里（construction / mcp catalog / oauth tokens / paste-cache 等），thread `configHome` 参数会改 ~50 个函数签名，且每个 caller 必须记得 thread（漏一个就 silent fallback）。Singleton 是 pragmatic right tool，与 `process.env.NODE_ENV` 同模式——一个进程真的只有一个 config home（不存在同进程并发使用 `~/.kodax/` 和 `~/.opsagent/` 的合理场景）。

**改动**：

| 来源 | 改动 | LoC |
|---|---|---|
| 新建 `@kodax/agent/src/runtime/agent-home.ts` | helper + setter + path resolver | +30 |
| 新建 `@kodax/agent/src/runtime/agent-home.test.ts` | 3 tier 优先级单测（DI / env / default 各场景 + setter reset + path 拼接 / Windows 路径分隔符） | +60 |
| 替换 ~29 处硬编码 `path.join(homedir(), '.kodax', ...)` | 改为 `getAgentConfigPath(...)` 调用 | ~29 处各 -2 +2 |
| `@kodax/ai/src/reasoning-overrides.ts:49` 现有 `KODAX_HOME ??` 检查 | 替换为 helper 调用（消除两份独立优先级判断逻辑） | -3 +1 |
| 替换的 6 个包 `package.json` | 全部加 `@kodax/agent` 为 dependency（如尚未引用） | dependency 调整 |

**为什么不引入 brand abstraction**：DI 入参直接接受路径字符串，substrate consumer 想叫什么自己决定（`~/.opsagent` / `~/.dataagent` / 或 `/tmp/kodax-test-${pid}`），不需要 KodaX 端发明 brand 概念。按 [CLAUDE.md `NEVER add abstractions until 3+ concrete use cases`](../../CLAUDE.md)，brand 抽象触发条件**永久取消**——除非将来真出现"按 brand 自动衍生 multi-path（如 `${brand}-skills` / `${brand}-mcp` 二级目录）"复杂需求。

**风险与保障**：

- **零行为变更**：DI 不传 + env 不设时，3-tier resolution 落到 default 分支，与现状 `path.join(homedir(), '.kodax', ...)` 字节级相同输出
- 编译器全程兜底（任意未替换的硬编码不影响编译，但会拉低 grep gate 命中数）
- FEATURE_104 prompt eval **无需重跑**——零 prompt 改动
- 现有 ~5000 单测继续跑（含 KODAX_HOME env var 场景测试，仍通过）
- 新增 `@kodax/agent/src/runtime/agent-home.test.ts` 60 LoC 覆盖 3 tier 优先级 + Windows path

**显式不做**：

- ❌ 改 default 为非 `~/.kodax/`（破坏现有用户）
- ❌ 改 `KODAX_HOME` env var 名（向后兼容）
- ❌ 把 `configHome` 塞进 `KodaXContextOptions` per-call DI（30 处 helper 签名改动 invasive；singleton pattern 更适合"进程级单值"的 library use case）
- ❌ Brand abstraction（YAGNI；DI 入参已覆盖所有 substrate consumer 重定向 use case）
- ❌ 同进程内并发支持多 config home（无合理 use case；与 Node.js 单进程单 NODE_ENV 模式一致）
