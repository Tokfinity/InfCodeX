## FEATURE_142: Package Boundary Cleanup — `@kodax/core` Removal & `@kodax/agent` Reaffirmation

**Status**: Planned
**Priority**: Critical（v0.7.36+ 全部 feature 的前置）
**Category**: Internal / Refactor

### 背景：FEATURE_082 漂移分析

v0.7.24 FEATURE_082 设计稿要建立 `ai → core → capabilities → coding` 的 4 层模型，并定义 `@kodax/agent` 为 "coding-specific session / extension runtime"。两年回看，这个设计在两个维度发生漂移：

#### 设计漂移（FEATURE_082 设计本身的错误）

| # | 漂移点 | 实证 |
|---|---|---|
| D1 | `@kodax/agent` 定义为 coding-specific | 与"coding 包才是 coding-specific"的自然读法直接矛盾；让 agent 与 coding 边界靠"装会话还是装工具"任意切分 |
| D2 | `@kodax/core` 单独成包的理由建立在 D1 之上 | 因为 agent 被错误定位为 coding-specific，"通用 agent 入口"无处可放，才被迫新开 core |
| D3 | `@kodax/capabilities` 设计为 Layer B 包 | `packages/capabilities/` **从未被创建**；FEATURE_084 v0.7.26 真要落 Scout/Evaluator 时绕开该包，直接放 `coding/src/agents/`——证明"通用 capabilities"是预先抽象 |
| D4 | 4 层模型违反 KodaX `NEVER add abstractions until 3+ concrete use cases` | 082 落地时只有 1 个真实 consumer（coding），却建了 4 层；capabilities 死包 + core 后续被 runtime 漂移填满，是 3+ rule 违反的实证后果 |

#### 实现漂移（082 之后落地偏离设计）

| # | 漂移点 | 实证 |
|---|---|---|
| I5 | runtime 漂入 `@kodax/core` | v0.7.26 FEATURE_084 / v0.7.31 FEATURE_101 把 createAgent 工厂、Runner class、Admission runtime、invariants 实现陆续加进 core；core 从"types + 少量基础实现"漂成"完整 agent runtime（误命名）" |
| I6 | Scout/Evaluator/Generator 进 coding 而非 capabilities | 表面是漂移，结果上**做对了**（这些是 coding AMA H2 实例，本来就该在 coding）——反而修复了 D3 |
| I7 | `@kodax/agent/package.json` 描述被改错 | 现描述写"通用 Agent 框架"，与 082 设计稿的"coding-specific"矛盾，又与实际内容（仅 session/persistence/compaction/tokenizer）也对不上——典型的语义自欺 |

#### 当前状态总结

| 包 | FEATURE_082 设计角色 | package.json 描述 | 实际内容 | 三方一致性 |
|---|---|---|---|---|
| `@kodax/core` | Layer A types + DefaultSummaryCompaction | "Layer A primitives" | createAgent 工厂 / Runner class / Admission runtime / invariants 实现（30 文件） | ❌ 设计错位 + 描述对、实现漂移 |
| `@kodax/agent` | coding-specific session / extension runtime | "通用 Agent 框架" | session.ts / persistence.ts / compaction/ / tokenizer.ts（10 文件） | ❌ 设计错位 + 描述自欺 + 实现淘空 |
| `@kodax/capabilities` | Layer B 组合能力包 | — | **包不存在** | ❌ 设计成死包 |

**为什么留 `coding/prompts/` 而不是 `@kodax/agent/`**：

- helper 调用方都在 coding 内（builder.ts + 未来 role-prompt.ts），未来 `@kodax/data-analysis-agent` 出现时它会有自己的 builder + 自己的 role-prompt，可以**复用 helper 的 pattern 但不需要复用具体 sections**（如 `prompt-overlay` 是 coding routing-specific，data-analysis 不会有同名段）。

- 满足 [ADR-021](../ADR.md#adr-021-agent-framework-boundary--kodaxagent-vs-kodaxcoding) §"任何只对 coding agent 有意义的内容 → `@kodax/coding`"——`prompt-overlay` 段是 coding-routing-specific，让整个 helper 留 coding 是边界正确选择。
- `@kodax/skills` / `@kodax/mcp` 包**已经在正确位置**（与 `@kodax/agent` 平级、零依赖入侵），漂移问题不在 package 边界，在 coding 内部 SA/AMA 拼装重复。

**本 Batch 行为不变**——SA path 调用 helper 后输出字节级相同；AMA worker 在本 Batch 不动；FEATURE_104 prompt eval 无需重跑。AMA worker 接通由 Batch F 完成。

**为什么必做不可延**：

- v0.7.35.1 是**唯一**"结构-only patch"窗口。一旦 v0.7.36 FEATURE_143 开始动 AMA worker，没有 helper 就要在 worker 里直接粘段拼装代码；先抽 helper，后续接通就是 1 次调用而不是多次复制粘贴 + 维护负担。
- 历史已经反复出现这种漂移（FEATURE_086 + v0.7.26 共 5 项 manual fix），再不抽 helper，下次加 capability 几乎确定再漏。
- 与 Batch C（Self-Construction agent-resolver 拆分通用部分进 agent / coding adapter 留 coding）对仗：本 Batch 是"coding 内部去重，不跨包上提"的不同 pattern，但同样是"识别重复 + 单一 source of truth"。

**Parent cache 机制**（新增 `gitContextSnapshot` / `projectSnapshotSnapshot`）：

数据流：

```
session 启动（turn 1）
  ↓
parent agent SA path 走 builder.ts
  ↓
builder.ts:85-106 检查 options.context.gitContextSnapshot
  ├─ 命中：直接用（已缓存）
  └─ miss：调用 getGitContext() / getProjectSnapshot() FS load
            ↓
            写回 options.context.gitContextSnapshot / .projectSnapshotSnapshot（同 turn 内复用）
  ↓
SA path 用结果拼 system prompt（与现状字节级相同）
  ↓
parent dispatch AMA worker
  ↓
worker 通过 options.context.* 读到已缓存的 snapshot（不再 FS load）
  ↓
worker role-prompt.ts 调 capability-sections helper
  ↓
helper 输出 6 段 capability context（含 git/project orientation）
  ↓
worker system prompt 拼入 capabilityContextBlock
```

每 turn FS load 上限：1 次（parent boot），不论多少 worker 并发。无 N×M 重复 IO 风险。

**为什么不在 Batch E 同时做**：Batch E 是结构-only 重构（dedup + 输出字节级相同），Batch F 是行为修复（worker 多看到 6 段 system context + 新增 parent cache 字段）。两者性质不同，分 Batch 后 git bisect 时能干净区分"helper 抽出导致的 regression"vs"worker 接通导致的 regression"。

**为什么只留 `prompt-overlay` 错位不修**：

- `prompt-overlay` 错位修正 = 把它从 user prompt 移到 system prompt = 改 prompt 结构。worker 当前 prompt 已经在 user prompt 头看到 routing notes，迁移可能影响 routing decisions（H0/H1/H2 判断）的下游行为。
- 这一段的数据**已经能传到 worker**（只是位置不对），与本 Batch 修的"data missing"问题性质不同。
- 留给 v0.7.36 FEATURE_143 配合"加强版 prompt eval（位置迁移前后行为对比）"一起做。FEATURE_143 已经要跑 prompt eval（manifest 措辞硬化触发），多加这一项零边际成本。

**风险与保障**：

- 6 段都是 SA path 已经在用的 capability content；worker 收到的是同样 content（只是 SA 一直见、worker 一直没见），不引入"未经验证的新 prompt 字面量"
- 触发 [CLAUDE.md §"Prompt Eval"](../../CLAUDE.md) 的 `role-prompt.ts` 修改条款，必须加新 eval case 跑通
- 新 eval case 跨 8 alias（FEATURE_104 标准），mean ≥80% 通过率作为 ship gate
- prompt eval 验证维度：
  - (a) worker 看到 6 段不退化 instruction following（baseline 对比，单 case ≥ baseline -10pp）
  - (b) `mcp-capability-context` 注入后 worker 在用户配置 MCP 时**主动**调用 `mcp_search` 至少一次（实战回归 fixture）
  - (c) `project-agents` 注入后 worker 遵守项目 CLAUDE.md 规则的比率提升（KodaX 自身 CLAUDE.md 含"❌ NEVER use any type"等硬规则可作 fixture）
  - (d) `git-context` 注入后 Generator 在 dirty repo 上执行 edit 前能**主动声明**当前分支 / 是否有 uncommitted changes（实战回归 fixture）

**FEATURE_144 prompt eval 失败的 follow-up 路径**：

| 失败 root cause | 处理 |
|---|---|
| Prompt 措辞调优可解决（小范围 instruction tuning，如 capability section 顺序 / 引导词） | FEATURE_144 单独回退到 **v0.7.35.2 patch release** retry，FEATURE_142 在 v0.7.35.1 ship 不阻塞；retry cycle 在 1-3 天内 close |
| 设计层面问题（如 6 段 capability content 累计 token 超 worker 预算 / worker prompt template 与 capability content 风格冲突需要重设计） | **fold 进 v0.7.36 FEATURE_143** 重新设计 capability injection 形态（如借鉴 Claude Code skill_listing attachment 模式 / 或 dynamic capability discovery）；v0.7.35.1 仍以 FEATURE_142 ship，AMA worker 继续沿用 v0.7.35 的"6 段漂移"现状直到 FEATURE_143 ship |
| Eval baseline 本身不稳定（aliasing 噪声 / 数据集太小） | 优先扩 eval 数据集 + alias 数；不直接 ship FEATURE_144；evaluation gap 进入 FEATURE_104 followup |

**用户实战影响**：FEATURE_142 ship 后 SA path 用户立刻享受 dedup helper 整理收益（无可见行为变化）；FEATURE_144 ship 后 AMA path 用户立刻看到 MCP server / skill / CLAUDE.md / git status / project snapshot 5 类信息开始进入 Scout/Worker 视野。如 FEATURE_144 走 v0.7.35.2 retry，AMA path 用户多等 1-3 天看到这一波改善。
