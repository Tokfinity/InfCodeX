# v0.7.38 Feature Designs

> 中文标题：`v0.7.38 Feature 设计`
>
> Version: `v0.7.38`
>
> Status: Planned (not yet released)
>
> Theme:
> 1. **FEATURE_117 — Read-Path Context Stripping**：给 read-only child agent 跳过 CLAUDE.md / AGENTS.md / git status 等大块 stable context 注入，缩窄版（仅 read-only child；mutation child 仍带全 context）。

---

## 总览

KodaX 当前 [`packages/coding/src/child-executor.ts`](../../packages/coding/src/child-executor.ts) 派 child 时把父 session 的 system prompt + CLAUDE.md / AGENTS.md / `.kodaxrc` / git status 全部继承给 child。这是"安全默认"——child 拿到所有 context 不会意外丢信息。

但**对 read-only child（只调 read/grep/glob/bash-readonly）这是浪费**：
- CLAUDE.md / AGENTS.md 是 mutation policy / forbidden items / coding style——read-only child 不写不动，这些规则不适用
- git status 是当前 working tree 状态——read-only child 不 commit 不 reset，状态对它不重要
- `.kodaxrc` 项目配置——read-only child 不需要知道项目用 vitest 还是 jest 才能 read 文件

Phase 0.7 调研显示 Claude Code 在 Explore agent（read-only）派发时**主动 strip** 这些大块——这是 Claude Code 的 34M+ Explore spawns/week 能撑住成本的关键之一。

KodaX 已有 FEATURE_119 Pattern B 之后，read-only child 派发频率会大幅上升（`dispatch_child_task` 不再阻塞 → Worker 更倾向于 fan-out 多个并行 read-only research child）。FEATURE_117 是 FEATURE_119 之后的成本兜底。

## FEATURE_117: Read-Path Context Stripping — Skip CLAUDE.md/AGENTS.md/git status for Read-Only Children

**Status**: Planned
**Priority**: Medium
**Category**: Enhancement / Cost Optimization

### 背景

#### 当前 child 派发的 context payload

[`packages/coding/src/child-executor.ts`](../../packages/coding/src/child-executor.ts) 在 `executeChildAgents` 内部构造 child system prompt 时继承父 session 的：

| Block | 来源 | Read-only child 是否需要 |
|---|---|---|
| Worker base system prompt | role-prompt.ts | ✅ 需要（child 也要遵循通用协议） |
| `<environment>` block | environment.ts | ✅ 需要（cwd / platform / git branch） |
| CLAUDE.md / AGENTS.md | repo root | ❌ 不需要（mutation policy 不适用 read-only） |
| `.kodaxrc` 项目配置 | repo root | ❌ 不需要（child 不调 test/build） |
| git status (`git status -s`) | runtime fetch | ❌ 不需要（child 不 commit） |
| Tool definitions | registry.ts | ⚠️ 部分需要（read-only child 只需 read/grep/glob/bash-readonly） |

总 token 估算：CLAUDE.md ~3k + AGENTS.md ~2k + .kodaxrc ~500 + git status ~200 = **~5.7k tokens 浪费**。

按 KodaX 当前 daily Worker turn ~200 / 平均 fan-out 2 read-only child = ~400 child invocations/day，**每个 child 省 5.7k tokens × $3/M（Sonnet 4.6 input）= $0.017 节省/child × 400 = $6.8/day = $200/month**（单用户）。

#### Phase 0.7 实测对照

Claude Code Explore agent 的 system prompt：
- 不含 CLAUDE.md
- 不含 AGENTS.md
- 不含 git status
- 仅含：base system prompt + tool definitions（仅 read 类工具）

所以 Explore agent 单次 invocation 的 input tokens 只有 ~6k；KodaX 当前 read-only child ~12k——存在 50% 缩减空间。

### 设计

#### 缩窄版策略：仅 read-only child 触发 stripping

`packages/coding/src/child-executor.ts` 在构造 child system prompt 时检查 child agent definition 的 `readOnly` 标记（FEATURE_119 Pattern B 已经引入 `readOnly: boolean` 字段在 `dispatch_child_task` schema）：

```ts
function buildChildSystemPrompt(
  parentSystemPrompt: KodaXSystemPromptBlock[],
  childAgentDef: KodaXChildAgentDefinition,
  isReadOnly: boolean,
): KodaXSystemPromptBlock[] {
  const blocks = [...parentSystemPrompt];

  if (isReadOnly) {
    return blocks.filter((b) =>
      b.kind !== 'agent-md' &&
      b.kind !== 'kodax-rc' &&
      b.kind !== 'git-status'
    );
  }

  return blocks;
}
```

#### Tool restriction（既有）

`dispatch_child_task` schema 的 `readOnly: true` 已经触发 tool whitelist 缩减到 `read/grep/glob/bash`（bash 走 read-only sandbox）。FEATURE_117 不动这部分。

#### Fail-safe：child LLM 主动声明需要

如果 read-only child 在 task 中发现确实需要 CLAUDE.md（极少见，比如要 read 一个文件然后判断它是否符合 coding-style.md 规则），child 可以调 `read('CLAUDE.md')` 工具自行获取。**不在系统层做 fallback 预注入**——child 的工具集已经允许 read，强制注入是过度设计。

#### Cost telemetry 验证

`packages/ai/src/cost-tracker.ts` 在 child invocation 完成时记录 `inputTokensSavedByStripping` 字段（基于 stable block 移除的 token count 估算）。`/cost` 命令输出每日累计节省。

### 影响范围

**新增**：

- `packages/coding/src/child-executor-system-prompt.ts`：抽出 system prompt 构造逻辑（~80 行）
- `tests/child-readonly-stripping.test.ts`：unit test 覆盖 readOnly=true/false 的 system prompt 差异
- `tests/child-readonly-stripping.eval.ts`：FEATURE_104 prompt eval，验证 read-only child 在缺 CLAUDE.md 的情况下仍能正确完成 read/grep/glob 任务（不退化）
- `docs/test-guides/FEATURE_117_v0.7.38_TEST_GUIDE.md`：人测引导

**修改**：

- `packages/coding/src/child-executor.ts`：调用新 helper（~10 行修改）
- `packages/coding/src/agent-runtime/system-prompt-*.ts`：把 CLAUDE.md / AGENTS.md / .kodaxrc / git status 从纯字符串拼接重构为带 `kind` 字段的 block 数组（~100 行重构，但纯结构性，不改语义）
- `packages/ai/src/cost-tracker.ts`：新增 `inputTokensSavedByStripping` 字段

**不改动**：

- mutation child 的 system prompt（保持完整 context）
- tool registry / tool definitions（FEATURE_119 已经做了 read-only tool whitelist）
- Worker (parent) 的 system prompt（FEATURE_117 仅作用于 child path）

### 迁移策略

```
v0.7.38（本 feature）：
  - 落地 system prompt block 化重构（保持现有行为）
  - read-only child 默认开启 stripping（feature flag KODAX_CHILD_READPATH_STRIP=1 默认值=1）
  - 跑 prompt eval 三类 read-only 任务（lookup / audit / cross-file search）证明不退化

v0.7.39+（FEATURE_120 落地后）：
  - 监测一周生产 telemetry 验证 read-only child 完成率不退化
  - 默认值保持 1，提供 KODAX_CHILD_READPATH_STRIP=0 escape hatch
```

### 验收标准

1. **read-only child 不收到 CLAUDE.md / AGENTS.md / .kodaxrc / git status**：wire-level inspect child invocation 的 system prompt
2. **mutation child 仍收到全 context**：`readOnly: false` 时 system prompt 与父 session 一致
3. **read-only 任务完成率不退化**：FEATURE_104 prompt eval 三类（lookup / audit / cross-file search）在 8 alias mean ≥ baseline（与 stripping 前对比 ≤ 2pp 退化即可）
4. **cost 节省可验证**：`/cost` 命令输出 `Saved by read-path stripping: X tokens (Y$)`
5. **child 仍能 read CLAUDE.md（如确需）**：read-only child 在工具集允许范围内可以主动 read 任意文件
6. **escape hatch 工作**：`KODAX_CHILD_READPATH_STRIP=0` 时回归到完整 context 注入
7. **跨 family 验证**：4 family LLM（GLM/Kimi/Claude/GPT）read-only child 在 stripping 后表现 max-min spread ≤ 15pp
8. **无回归**：所有既有 child invocation 测试绿；FEATURE_119 Pattern B 路径全绿

### 非目标

- **不** strip mutation child 的 context（mutation 需要知道 coding-style / forbidden items）
- **不** strip Worker (parent) 的 context（Worker 是用户面对的 agent，必须有完整 context）
- **不** 引入 fine-grained per-block stripping（4 个 block 整体 strip 即可，per-line stripping 是过度设计）
- **不** 给 read-only child 加 fallback 预注入"必要的 read-style hint"（child 工具集已允许 read）
- **不** 持久化 stripping 决策（每次 child invocation 独立判断，基于 dispatch schema 的 readOnly）
- **不** 在 self-construction 生成的 agent 上自动 strip（自定义 agent 的 readOnly 由 admission contract 验证后决定）

### 与其他 Feature 的关系

- **依赖 FEATURE_119（v0.7.36）**：Pattern B 引入 `readOnly: boolean` 字段，FEATURE_117 消费这个字段
- **协同 FEATURE_116（v0.7.37）**：cache_control 减少 stable 部分重复计费；FEATURE_117 减少 read-only child 的 context payload——两个独立维度的成本优化
- **辅助 FEATURE_102（v0.7.45）**：FEATURE_102 capability routing 可以把 stripping 后的 child invocation routing 到更便宜的 model（如果 capability profile 允许）
- **辅助 FEATURE_120（v0.7.39）**：FEATURE_120 的 `model_hint?: 'fast'` 字段在 read-only + stripped child 上效果最好（小 input → fast model 完全够用）

## FEATURE_149: Queued Prompt Injection Latency & Mid-Turn UX Parity

**Status**: Planned
**Priority**: High
**Category**: Enhancement / UX + Internal / Performance

### 背景

用户实战反馈："输入 queue 排队指令时，并没有尽快注入"——感觉 KodaX 在 Claude Code 风格的多轮对话节奏上有明显"卡顿"。Phase 0.7 forensic 对照（`c:/Works/claudecode/src/`）证实**这不是错觉**，KodaX 在"上一轮结束 → 排队 prompt 实际抵达 LLM"之间叠加了 4 个延迟源 + 3 个架构 UX 缺口。

#### 已定位的延迟源（每轮排队均触发）

| # | 位置 | 性质 | 估算延迟 | Claude Code 对照 |
|---|---|---|---|---|
| L1 | [`packages/repl/src/ui/InkREPL.tsx:6267`](../../packages/repl/src/ui/InkREPL.tsx#L6267) | `stageQueuedPrompt` 末尾硬编码 `await new Promise(r => setTimeout(r, 50))` | **+50ms 不可避免** | 无（`queueProcessor.ts:52` 同步 dequeue + `void executeInput()`，零延迟） |
| L2 | [`packages/coding/src/context/agents-loader.ts:70`](../../packages/coding/src/context/agents-loader.ts#L70) `loadAgentsFiles` | 每轮 `existsSync` + `readFileSync` 全树遍历 cwd → root，无 mtime 缓存 | **+2~15ms / 轮**（视仓库深度 + 磁盘） | `claudemd.ts` + `fileReadCache.ts` mtime cache，命中即字节复用 |
| L3 | [`packages/repl/src/ui/contexts/StreamingContext.tsx:344`](../../packages/repl/src/ui/contexts/StreamingContext.tsx#L344) `FLUSH_INTERVAL = 80` | 流式 token batch flush 80ms 节流；如果 round-complete 信号挂在 React 状态 commit 上，可能延迟检测 | **0~80ms 抖动** | 无对应延迟（store `useSyncExternalStore` 在 commit 前同步发布，无 80ms 节流） |
| L4 | [`packages/repl/src/ui/contexts/StreamingContext.tsx`](../../packages/repl/src/ui/contexts/StreamingContext.tsx) `notify()` 走 `forceUpdate()` 订阅 | 队列变更通过 `forceUpdate` 推 React scheduler，非 sync external store | **+1~16ms 抖动**（一个 React tick） | `useSyncExternalStore` 在 commit 前同步读取 store snapshot |

**单轮排队累计**：`50 + (2~15) + (0~80) + (1~16) = 53~161ms` 之间，**floor 53ms**——用户在两轮快速排队时累计感知 100~300ms 卡顿。

#### 架构 UX 缺口（与 Claude Code 不对等的"自然感"差距）

| # | 缺口 | KodaX 现状 | Claude Code 行为 |
|---|---|---|---|
| G1 | **Interruptible-tool fast-abort** | submit 时永远走 `addPendingInput`（[`InkREPL.tsx:6522-6544`](../../packages/repl/src/ui/InkREPL.tsx#L6522-L6544)），30s 的 bash 工具必须跑完才轮到下一条 | `handlePromptSubmit.ts:331` 检测 `hasInterruptibleToolInProgress`（工具标 `interruptBehavior: 'cancel'`）时立即 `abortController.abort('interrupt')` 中断当前轮 |
| G2 | **批量 drain 单轮多 user message** | [`queued-prompt-sequence.ts:32-43`](../../packages/repl/src/ui/utils/queued-prompt-sequence.ts#L32-L43) 一次 shift 一条跑一整轮 agent，N 条 = N 次 agent 调用 | `queueProcessor.ts:52-87` 同 mode 多条命令批量 drain 进单次 `executeUserInput([...commands])`，多条 user message 进同一轮 context |
| G3 | **Up-arrow popAllEditable** | [`pending-inputs.ts:14-25`](../../packages/repl/src/ui/utils/pending-inputs.ts) 只显示一行摘要 + Esc 砍最新，不可编辑/重排 | `messageQueueManager.ts:428` `popAllEditable()` 把整个队列 pop 回输入框可编辑 |

### 设计

#### Slice A：消除延迟源（零行为变更，无需 prompt eval）

**A1 — 移除 hardcoded `setTimeout(50)`**

[`InkREPL.tsx:6267`](../../packages/repl/src/ui/InkREPL.tsx#L6267) 的 50ms 等待是历史遗留（git blame 待考古，疑似为"等 React 状态 commit"的盲等待）。改为 `flushSync` 包裹同步 state 写入：

```ts
const stageQueuedPrompt = useCallback(async (prompt: string) => {
  const normalizedPrompt = prompt.trim();
  if (!normalizedPrompt) return;

  // flushSync 确保下一轮 runRound 读到最新 history / submitCounter / context
  flushSync(() => {
    addHistoryItem({ type: "user", text: normalizedPrompt });
    setSubmitCounter((prev) => prev + 1);
    touchContext(context);
  });
}, [addHistoryItem, context]);
```

**A2 — AGENTS.md / CLAUDE.md mtime cache**

[`packages/coding/src/context/agents-loader.ts`](../../packages/coding/src/context/agents-loader.ts) `loadAgentsFiles` 加 module-level `Map<string, { mtimeMs: number; content: string }>`，`statSync().mtimeMs` 命中则字节复用。Cache key = 绝对路径，cache miss / mtime mismatch 时正常 read 并写回。**Singleton pattern**（与 `process.env.NODE_ENV` 同模式），不引入 DI。

**A3 — Round-complete 信号与 80ms FLUSH_INTERVAL 解耦**

审计 [`StreamingContext.tsx:344`](../../packages/repl/src/ui/contexts/StreamingContext.tsx#L344) `FLUSH_INTERVAL = 80` 节流是否影响 `runRound` 返回时序。预期路径是 `provider.stream()` resolve → `runRound` 直接 return，与 token flush timer 无关；如果中间存在 `await flushPendingUpdates()` 之类调用，改为不阻塞 round-complete 信号。

**A4 —（可选）队列 notify 改 `useSyncExternalStore`**

将 `pendingInputs` 改用 React 18 `useSyncExternalStore` 订阅，去掉 `forceUpdate()` 间接 dispatch。Cost：~30 行 refactor。Benefit：~16ms 抖动消除 + 与 Claude Code 同模式。

#### Slice B：架构 UX 对齐（行为变更，触发 prompt eval）

**B1 — Tool `interruptBehavior` 字段 + fast-abort 路径**

`packages/coding/src/tools/types.ts` 新增可选字段：

```ts
interface KodaXToolDefinition {
  // ...existing...
  interruptBehavior?: 'cancel' | 'wait';  // 默认 'wait'
}
```

工具标记策略：
- `'cancel'`：bash（长 exec）/ sleep / 长 LLM 调用类工具（dispatch_child_task 同步等待路径）
- `'wait'`（默认）：read / grep / glob / write / edit 等原子工具

[`InkREPL.tsx:6522`](../../packages/repl/src/ui/InkREPL.tsx#L6522) `handleSubmit` 在 `isLoading && canQueueFollowUps` 分支前置检查：当前 `currentTool?.interruptBehavior === 'cancel'` 时，先 `abort()` 再 `addPendingInput`，下一轮立即起。否则走原排队路径。

**B2 — Abort 时合成 `tool_result` error block**

中断后给悬空的 `tool_use` 注入合成 `tool_result`（type=`error`，content=`"User interrupted before completion"`），保证 message history 闭合，下一轮 LLM context 一致。对照 Claude Code `query.ts:1015-1051` 的 `yieldMissingToolResultBlocks` / `getRemainingResults`。位置：`packages/coding/src/agent-runtime/runner-driven.ts` agent 主循环 abort 分支。

**B3 — 批量 drain 单轮多 user message**

改 [`queued-prompt-sequence.ts`](../../packages/repl/src/ui/utils/queued-prompt-sequence.ts)：在 `onRoundComplete` 之后 drain **所有**待排队 prompts（而非一次 shift 一条），合并为多个 user message 进 `runRound([...prompts])` 单次 agent 调用。`runRound` 签名从 `(prompt: string)` 改为 `(prompts: string[])`，agent path 把数组拼成多个连续 `{ role: 'user', content: ... }` 块。

**优势**：
- N 条排队从 N 次 agent 调用降到 1 次（cost 节省 ~50-90%）
- LLM 在同一 context 看到全部排队意图，可做整体规划而非孤立处理
- Cache 命中率↑（同一 system prompt + 同一历史只算一次 cache）

#### Slice C：Queue UX 表面（纯 UI，无 eval）

**C1 — Up-arrow popAllEditable**

`PromptFooter.tsx` 输入框为空时按 ↑ 键，把队列内容（按入队顺序拼接，分隔符 `\n---\n`）pop 回输入框，清空队列；用户可编辑/重排后重新 submit。对照 Claude Code `messageQueueManager.ts:428`。

**C2 — 队列每条独立渲染**

`QueuedCommandsSurface.tsx` 改为渲染队列每条（最多 5 条），每条一行 `[1/3] <preview>`，替换当前的 "Queued N follow-ups. Latest: …" 单行摘要。

2. **AGENTS.md cache 命中**：unit test 验证同 cwd 第二次 `loadAgentsFiles` 调用 0 次 `readFileSync`（mtime 未变时）
3. **Bash 长跑可中断**：人测引导 — `bash` 跑 30s sleep 时按 Enter 提交新 prompt，**500ms 内**新 prompt 起轮（B1 fast-abort 验证）
4. **批量 drain cohesion**：5 条排队 prompts 触发 1 次 agent 调用（不是 5 次），LLM 输出体现整体规划意识（人测主观判断 + cost tracker `agentInvocationCount` 字段）
5. **Up-arrow editable**：人测 — 输入框为空时按 ↑ 把队列 pop 回输入框，清空队列状态指示
6. **跨 family 不退化**：B3 prompt eval 5 alias mean ≥ baseline，max-min spread ≤ 15pp
7. **既有测试全绿**：`packages/repl/src/ui/utils/queued-prompt-sequence.test.ts` + `pending-inputs.test.ts` + `StreamingContext.queue-mirror.test.ts` 全绿（签名变更可改测试，行为变更不可）
8. **零 known regression**：FEATURE_115 Message Queue Foundation / FEATURE_119 Pattern B / FEATURE_111 soft-pause（v0.7.43 未实施，不冲突）路径全绿
