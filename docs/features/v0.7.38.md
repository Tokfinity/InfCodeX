## FEATURE_117 v2: Write-Child Mutation Context Injection

**Status**: Implemented (v0.7.38)
**Priority**: Medium
**Category**: Enhancement / Correctness (project-rules compliance)

### 背景

[`packages/coding/src/child-executor.ts`](../../packages/coding/src/child-executor.ts) 当前对 read 与 write child **共用同一 minimal override**：

```ts
// child-executor.ts before v2 (read + write 都用这一行)
context: {
  ...,
  systemPromptOverride: CHILD_AGENT_SYSTEM_PROMPT, // ~500 token, no project rules
  ...
}
```

`CHILD_AGENT_SYSTEM_PROMPT` 是一段 task-focused parallel-tool-call 引导文本，**不含 AGENTS.md**（mutation policy / forbidden items / coding style）。对 read child 这是合理的——它只调 read/grep/glob/bash-readonly，不会违反项目规则。

但 **write child（H2 Generator fan-out，独立 worktree 写入）也用这一行**——这意味着 write child 完全看不到项目级的 mutation 规则。例如 KodaX 自身 `AGENTS.md` 的 `❌ NEVER use \`any\``、`❌ NEVER hardcode config`、`❌ NEVER commit console.log` 等约束，write child 不知道这些约束就会写出违规代码。Evaluator review 阶段才会发现，浪费 fan-out 成本。

### 设计

**Step 1** — `buildWriteSystemPrompt(gitRoot)` helper（[`packages/coding/src/child-executor.ts`](../../packages/coding/src/child-executor.ts) 内部，不导出）：

```ts
async function buildWriteSystemPrompt(gitRoot: string): Promise<string> {
  const agentsFiles = loadAgentsFiles({ cwd: gitRoot, projectRoot: gitRoot });
  const formatted = formatAgentsForPrompt(agentsFiles);
  if (!formatted) return CHILD_AGENT_SYSTEM_PROMPT;
  // formatted 已含自身的 `# Project Context` H1 + `## … Rules` H2 + `---`，
  // 不再外包 H2，否则 heading 会出现 H2→H1 倒置。仅前置一句 framing。
  return [
    CHILD_AGENT_SYSTEM_PROMPT,
    '',
    'Project rules apply to your mutations. Follow them as the parent agent would:',
    formatted,
  ].join('\n');
}
```

**Step 2** — `executeWriteChild` 用 helper 替换字面量 override（read child 不动）：

```ts
const writeSystemPrompt = await buildWriteSystemPrompt(parentCtx.gitRoot ?? wtPath);
// ...
context: {
  gitRoot: wtPath,
  executionCwd: wtPath,
  systemPromptOverride: writeSystemPrompt,
  excludeTools: CHILD_EXCLUDE_TOOLS_BASE,
}
```

**关键设计点**：

1. **Lookup 用 `parentCtx.gitRoot`，不用 `wtPath`**：worktree 是同 repo 的临时 checkout，其内部不含 AGENTS.md（worktree create 不会复制非 tracked 文件）。AGENTS.md 必须从原 project root 找。
2. **缓存复用 FEATURE_149 Phase 1.2 mtime cache**：`loadAgentsFiles` 已有模块级 `fileContentCache` (`agents-loader.ts:69`)，多 child fan-out 同一 AGENTS.md 仅触发一次 disk read。
3. **prompt cache 友好**：write child 的 system prompt = 稳定 `CHILD_AGENT_SYSTEM_PROMPT` + 稳定 AGENTS.md content，Anthropic `cache_control: ephemeral`（FEATURE_116）覆盖整段——5 min cache window 内 fan-out 只在第一次计费。
4. **Read child 完全不动**：read child 不 mutate，AGENTS.md 不适用——继续走 bare `CHILD_AGENT_SYSTEM_PROMPT`。

### 配套清理（v0.7.38 同期，**不属于 FEATURE_117 范围**）

[`packages/coding/src/context/agents-loader.ts`](../../packages/coding/src/context/agents-loader.ts) `CONTEXT_FILE_CANDIDATES` 从 `["AGENTS.md", "CLAUDE.md"]` 改为 `["AGENTS.md"]`。

**Why**：KodaX **只读 `AGENTS.md`，不读 `CLAUDE.md`**——`CLAUDE.md` 是 Claude Code 专属项目规则文件（其内容是写给 CC CLI 消费的）。当一个项目同时有 `AGENTS.md` + `CLAUDE.md` 时内容通常重合：fallback 在两个目录层级都命中即双重注入；项目仅有 `CLAUDE.md` 时把 CC 专属规则注入到 KodaX agent 上下文会造成语义错配。Dogfood KodaX 仓库自身 `docs/CLAUDE.md` 就是 CC 项目规则，是该 bug 的真实命中场景。

**Minor breaking change**：项目仅有 `CLAUDE.md`、无 `AGENTS.md` 时，KodaX 不再读取——迁移：`mv CLAUDE.md AGENTS.md` 或建 symlink（`AGENTS.md` 是跨工具的标准 AI-agent 规则文件名）。CHANGELOG 标记。

## FEATURE_117 v1（archived）: Read-Path Context Stripping — Skip CLAUDE.md/AGENTS.md/git status for Read-Only Children

**Status**: ~~Planned~~ → **Replaced by v2 (above) in v0.7.38**

> v1 假设 child 继承父 5.2k token stable context（CLAUDE.md ~3k + AGENTS.md ~2k + git status）。Phase 3 实施期检查 `child-executor.ts:236, 311` 发现 `systemPromptOverride` 已短路 `buildSystemPrompt`——child 实际处于 ~500 token 干净状态，原稿数字（5.2k token / $187 月节省）全部基于错误假设。
>
> **真实问题反向**：write child 同样走这条 minimal override 路径，看不到 AGENTS.md 的 mutation policy。v2 = 在 write child 注入 AGENTS.md（read child 维持 minimal），上文是 v2 设计。
>
> v1 设计稿正文保留如下作反例参考。

### 背景

#### 当前 child 派发的 context payload

[`packages/coding/src/child-executor.ts:32-67`](../../packages/coding/src/child-executor.ts#L32-L67) 通过 lazy-load `runKodaX` 给 child 起一个**全新的 agent run** —— child 不继承 parent 已组装的 system prompt，而是自己调用 `buildSystemPrompt` → [`packages/coding/src/prompts/capability-sections.ts`](../../packages/coding/src/prompts/capability-sections.ts) 重新拼装 13 个 capability section（FEATURE_142 v0.7.35.1 Batch E 的统一入口）。

`capability-sections.ts` 文件头注释列出的 13 个 section 中，与 read-only child 相关的判定如下：

| # | Section ID | 当前触发条件 | Read-only child 是否需要 |
|---|---|---|---|
| 1-5 | base-system / suffix / environment / runtime-fact / working-directory | 总是注入 | ✅ 需要（基础协议 + cwd / platform） |
| 6 | `git-context` | `isNewSession && repo has git output` | ❌ 不需要（child 不 commit / reset） |
| 7 | `project-snapshot` | `isNewSession` | ✅ 需要（**read-only child 用于文件结构导航**） |
| 8 | `repo-intelligence-context` | `context.repoIntelligenceContext` 非空 | ✅ 需要（repointel 数据是 read-only 价值核心） |
| 9 | `mcp-capability-context` | extensionRuntime 返回 mcp ctx | ✅ 需要（MCP 工具发现） |
| 10 | `prompt-overlay` | `context.promptOverlay` | ✅ 需要（routing 配套） |
| 11 | `project-agents` | AGENTS.md / CLAUDE.md 找到 | ❌ 不需要（mutation policy 不适用 read-only） |
| 12 | `skills-addendum` | `context.skillsPrompt` | ✅ 需要（skills 是 read-only child 也可用） |
| 13 | `tool-construction` | `toolConstructionMode` 含此模式 | ✅ 需要（tool semantics） |

**Strip 目标 = section 6 + section 11 共 2 项。**

> **修订说明**（与原设计稿对齐）：
> - 原稿列出的 `.kodaxrc` 不在 system prompt 注入路径——`grep -rn "kodaxrc" packages/ src/` 在非测试代码中**完全不命中**，是从 Claude Code 对照引入的 phantom 目标，**已删除**
> - 原稿列出的"git status -s"对应 `capability-sections.ts:292` `git status --short`——位置确认正确
> - 原稿假设的"`buildChildSystemPrompt(parentSystemPrompt, …)` 后过滤"路径**与现实不符**——child 是独立 agent run 自己 build prompt，没有"继承"过程。改为在 child 自己 build 时通过 `KodaXOptions` flag gate section 即可

总 token 估算：CLAUDE.md ~3k + AGENTS.md ~2k + git status ~200 = **~5.2k tokens 浪费**。

按 KodaX 当前 daily Worker turn ~200 / 平均 fan-out 2 read-only child = ~400 child invocations/day，**每个 child 省 5.2k tokens × $3/M（Sonnet 4.6 input）= $0.0156 节省/child × 400 = $6.24/day = $187/month**（单用户）。

#### Phase 0.7 实测对照

Claude Code Explore agent 的 system prompt：
- 不含 CLAUDE.md
- 不含 AGENTS.md
- 不含 git status
- 仅含：base system prompt + tool definitions（仅 read 类工具）

所以 Explore agent 单次 invocation 的 input tokens 只有 ~6k；KodaX 当前 read-only child ~12k——存在 ~45% 缩减空间。

### 设计

#### 缩窄版策略：在 child 自己 build prompt 时 gate 两个 section

不做 block 化重构、不抽 helper、不改 capability-sections 的语义。仅在 [`packages/coding/src/types.ts`](../../packages/coding/src/types.ts) `KodaXOptions` 加一个 optional flag，并在 `capability-sections.ts` 的 section 6 / 11 condition 里 OR 上 gate：

**Step 1** — `KodaXOptions` 加字段（`packages/coding/src/types.ts`）：

```ts
export interface KodaXOptions {
  // ...existing fields...

  /**
   * @experimental FEATURE_117 (v0.7.38)
   * Skip stable system-prompt sections that read-only child agents do not need.
   * Set by child-executor when dispatching read-only children. Parent / mutation
   * children leave this undefined → all sections preserved.
   */
  readonly systemPromptStrip?: {
    readonly agentsMd?: boolean;   // skip section 11 (project-agents = CLAUDE.md/AGENTS.md)
    readonly gitContext?: boolean; // skip section 6  (git-context = `git status --short`)
  };
}
```

**Step 2** — `capability-sections.ts` 在两个 section 的 condition 里 OR 上 gate（~6 LoC）：

```ts
// section 6: git-context
if (isNewSession && hasGitOutput && !options.systemPromptStrip?.gitContext) {
  sections.push(createPromptSection('git-context', ...));
}

// section 11: project-agents
const agentsFiles = options.systemPromptStrip?.agentsMd
  ? []
  : loadAgentsFiles({ cwd: executionCwd });
if (agentsFiles.length > 0) {
  sections.push(createPromptSection('project-agents', ...));
}
```

**Step 3** — `child-executor.ts` 在派 read-only child 时把 flag 注入 child 的 `KodaXOptions`（~6 LoC）：

```ts
const childOptions: KodaXOptions = {
  ...inheritedOptions,
  ...(readOnly ? {
    systemPromptStrip: { agentsMd: true, gitContext: true }
  } : {}),
};
const childResult = await runKodaX(childOptions, taskPrompt);
```

总实施量 **~15 LoC**（vs 原稿的 ~100 行 block 化重构），符合 KodaX minimalist 原则。

#### Tool restriction（既有）

`dispatch_child_task` schema 的 `readOnly: true` 已经触发 tool whitelist 缩减到 `read/grep/glob/bash`（bash 走 read-only sandbox）。FEATURE_117 不动这部分。

#### Fail-safe：child LLM 主动声明需要

如果 read-only child 在 task 中发现确实需要 CLAUDE.md（极少见），child 可以调 `read('CLAUDE.md')` 工具自行获取。**不在系统层做 fallback 预注入**——child 工具集允许 read，强制注入是过度设计。

#### Cost telemetry 验证

`packages/ai/src/cost-tracker.ts` 在 child invocation 完成时记录 `inputTokensSavedByStripping` 字段（基于 stripped section 的 token count 估算 = `sum(section 6 + 11 rendered length / 4)`）。`/cost` 命令输出每日累计节省。

## FEATURE_149: Queued Prompt Injection Latency & Mid-Turn UX Parity

**Status**: Planned
**Priority**: High
**Category**: Enhancement / UX + Internal / Performance

### 背景

用户实战反馈："输入 queue 排队指令时，并没有尽快注入"——感觉 KodaX 在 Claude Code 风格的多轮对话节奏上有明显"卡顿"。Phase 0.7 forensic 对照（`c:/Works/claudecode/src/`）证实**这不是错觉**，KodaX 在"上一轮结束 → 排队 prompt 实际抵达 LLM"之间叠加了 4 个延迟源 + 3 个架构 UX 缺口。

#### 已定位的延迟源（每轮排队均触发）

| # | 位置 | 性质 | 估算延迟 | Claude Code 对照 |
|---|---|---|---|---|
| L1 | [`packages/repl/src/ui/InkREPL.tsx:6267`](../../packages/repl/src/ui/InkREPL.tsx#L6267) | `stageQueuedPrompt` 末尾硬编码 `await new Promise(r => setTimeout(r, 50))` | **+50ms 不可避免** | 无（`queueProcessor.ts:52` 同步 dequeue + `void executeInput()`，零延迟） |
| L2 | [`packages/coding/src/context/agents-loader.ts:70`](../../packages/coding/src/context/agents-loader.ts#L70) `loadAgentsFiles` | 每轮 `existsSync` + `readFileSync` 全树遍历 cwd → root，无 mtime 缓存 | **+2~15ms / 轮**（视仓库深度 + 磁盘） | `claudemd.ts` + `fileReadCache.ts` mtime cache，命中即字节复用 |
| L3 | [`packages/repl/src/ui/contexts/StreamingContext.tsx:344`](../../packages/repl/src/ui/contexts/StreamingContext.tsx#L344) `FLUSH_INTERVAL = 80` | 流式 token batch flush 80ms 节流；如果 round-complete 信号挂在 React 状态 commit 上，可能延迟检测 | **0~80ms 抖动** | 无对应延迟（store `useSyncExternalStore` 在 commit 前同步发布，无 80ms 节流） |
| L4 | [`packages/repl/src/ui/contexts/StreamingContext.tsx`](../../packages/repl/src/ui/contexts/StreamingContext.tsx) `notify()` 走 `forceUpdate()` 订阅 | 队列变更通过 `forceUpdate` 推 React scheduler，非 sync external store | **+1~16ms 抖动**（一个 React tick） | `useSyncExternalStore` 在 commit 前同步读取 store snapshot |

**单轮排队累计**：`50 + (2~15) + (0~80) + (1~16) = 53~161ms` 之间，**floor 53ms**——用户在两轮快速排队时累计感知 100~300ms 卡顿。

#### 架构 UX 缺口（与 Claude Code 不对等的"自然感"差距）

| # | 缺口 | KodaX 现状 | Claude Code 行为 |
|---|---|---|---|
| G1 | **Interruptible-tool fast-abort** | submit 时永远走 `addPendingInput`（[`InkREPL.tsx:6522-6544`](../../packages/repl/src/ui/InkREPL.tsx#L6522-L6544)），30s 的 bash 工具必须跑完才轮到下一条 | `handlePromptSubmit.ts:331` 检测 `hasInterruptibleToolInProgress`（工具标 `interruptBehavior: 'cancel'`）时立即 `abortController.abort('interrupt')` 中断当前轮 |
| G2 | **批量 drain 单轮多 user message** | [`queued-prompt-sequence.ts:32-43`](../../packages/repl/src/ui/utils/queued-prompt-sequence.ts#L32-L43) 一次 shift 一条跑一整轮 agent，N 条 = N 次 agent 调用 | `queueProcessor.ts:52-87` 同 mode 多条命令批量 drain 进单次 `executeUserInput([...commands])`，多条 user message 进同一轮 context |
| G3 | **Up-arrow popAllEditable** | [`pending-inputs.ts:14-25`](../../packages/repl/src/ui/utils/pending-inputs.ts) 只显示一行摘要 + Esc 砍最新，不可编辑/重排 | `messageQueueManager.ts:428` `popAllEditable()` 把整个队列 pop 回输入框可编辑 |

### 设计

#### Slice A：消除延迟源（零行为变更，无需 prompt eval）

**A1 — 移除 hardcoded `setTimeout(50)`**

[`InkREPL.tsx:6267`](../../packages/repl/src/ui/InkREPL.tsx#L6267) 的 50ms 等待是历史遗留（git blame 待考古，疑似为"等 React 状态 commit"的盲等待）。改为 `flushSync` 包裹同步 state 写入：

```ts
const stageQueuedPrompt = useCallback(async (prompt: string) => {
  const normalizedPrompt = prompt.trim();
  if (!normalizedPrompt) return;

  // flushSync 确保下一轮 runRound 读到最新 history / submitCounter / context
  flushSync(() => {
    addHistoryItem({ type: "user", text: normalizedPrompt });
    setSubmitCounter((prev) => prev + 1);
    touchContext(context);
  });
}, [addHistoryItem, context]);
```

**A2 — AGENTS.md / CLAUDE.md mtime cache**

[`packages/coding/src/context/agents-loader.ts`](../../packages/coding/src/context/agents-loader.ts) `loadAgentsFiles` 加 module-level `Map<string, { mtimeMs: number; content: string }>`，`statSync().mtimeMs` 命中则字节复用。Cache key = 绝对路径，cache miss / mtime mismatch 时正常 read 并写回。**Singleton pattern**（与 `process.env.NODE_ENV` 同模式），不引入 DI。

**A3 — Round-complete 信号与 80ms FLUSH_INTERVAL 解耦审计**

> **审计结论（实施时落实）**：[`StreamingContext.tsx:344`](../../packages/repl/src/ui/contexts/StreamingContext.tsx#L344) `FLUSH_INTERVAL = 80` 仅作用于流式 token 渲染批量提交（`appendResponse` / `appendThinking` 走 `scheduleFlush()`）。所有状态切换方法（`setState` / `startStreaming` / `stopStreaming` / `setError` / `clearResponse` …等共 22 处）入口都**同步**调用 `flushPendingUpdates()` 清队列，`runRound` resolve 与 round-complete 检测路径中**不存在** 80ms 排队等待。L3 在 forensic 阶段提的"0~80ms 抖动"假设经实施期审计**不成立**，本子项无需代码改动；保留此节作为决策记录。

**A4 —（已 defer 到 v0.7.39+）队列 notify 改 `useSyncExternalStore`**

> **实施期决策**：本子项标"可选"是审慎设计。`StreamingContext` 当前 `subscribe`/`forceUpdate` 订阅模式有 N 个消费者组件，全量迁移 `useSyncExternalStore` 涉及面 ~30 行 + 跨组件回归面，风险显著。**A1 移除 `setTimeout(50)` 已拿到 ~90% 体感改善**（floor 53ms → < 5ms），剩余 ~16ms React tick 抖动单独追求性价比低。defer 到 v0.7.39+，等 telemetry 显示该路径仍是瓶颈再做。本 feature ship 时不实施。

#### Slice B：架构 UX 对齐（行为变更，触发 prompt eval）

**B1 — Tool `interruptBehavior` 字段 + fast-abort 路径（infrastructure-ready，无 tool opt-in）**

`packages/coding/src/tools/types.ts` 新增可选字段：

```ts
interface LocalToolDefinition {
  // ...existing...
  interruptBehavior?: 'cancel' | 'wait';  // 默认 'wait'
}
```

[`InkREPL.tsx:handleSubmit`](../../packages/repl/src/ui/InkREPL.tsx) 在 `isLoading && canQueueFollowUps` 分支前置检查：当前 `currentTool?.interruptBehavior === 'cancel'` 时，先 `addPendingInput` + `abort({ preservePendingInputs: true })`，下一轮立即起。否则走原排队路径。

`StreamingContext.abort` 新增 `AbortOptions { preservePendingInputs?: boolean }`：默认行为（Esc）清空队列，fast-abort 调用方传 `true` 保留刚提交的 prompt 给下一轮 drain。

**关键设计修正（实施期 2026-05-09）**：原稿规划 `bash` / `dispatch_child_task` 同步等待路径标 `'cancel'`，**已撤回**。事实核查 `c:/Works/claudecode/src/`：

```bash
$ grep -rn "interruptBehavior" c:/Works/claudecode/
# 5 处出现，0 个具体 tool 实现 interruptBehavior() => 'cancel'
```

[`Tool.ts:416`](c:/Works/claudecode/src/Tool.ts#L416) 接口存在但 BashTool / FileEditTool / TaskGetTool / TaskOutputTool 全部默认 `'block'`（≈ KodaX 的 `'wait'`）。[`StreamingToolExecutor.ts:255-259`](c:/Works/claudecode/src/services/tools/StreamingToolExecutor.ts#L255) 的 `hasInterruptibleToolInProgress` 判定用 `executing.every(t => 'cancel')`——只要有一个 'block' 就否决整体，**生产中几乎从不命中**。CC 注释 "e.g. SleepTool" 的 SleepTool 自己也没标，是为未来"显式无副作用等待工具"留的钩子。

**为什么不能照搬到 bash / await_child_task**：
- **bash 中断 = SIGTERM**：子进程可能写了一半文件、改了一半数据库、推了一半 git，留下半完成状态比让它跑完更危险
- **await_child_task 中断**：FEATURE_119 Pattern B 设计是 child 后台 detached 跑——abort 主轮后 child 还在 worktree 里继续写，造成"幽灵 child"

**实际落地**：
- `ToolInterruptBehavior` 类型 + `LocalToolDefinition.interruptBehavior` 字段：保留（接口与 CC 对齐）
- `InkREPL.tsx` fast-abort 路径：保留（接口齐了，没工具触发就走默认路径，是 dead-ish path 直到未来加纯等待工具）
- `bash` / `await_child_task`：**不**标 `'cancel'`（与 CC 一致的保守默认）
- 用户 ESC 仍是显式 abort 入口（不变）

**B2 — Abort 时合成 `tool_result` error block（已撤销，无需实施）**

实施期检查 substrate：[`run-substrate.ts:1447`](../../packages/coding/src/run-substrate.ts) AbortError 已经 graceful resolve `{ success: true, interrupted: true }`，且既有 `cleanupIncompleteToolCalls` + `validateAndFixToolHistory` 在下一轮 LLM 调用前自动剥 orphan `tool_use`。**B2 是修一个不存在的 bug**，撤销，节省 ~20 LoC。

**B3 — 批量 drain 单轮多 user message**

改 [`queued-prompt-sequence.ts`](../../packages/repl/src/ui/utils/queued-prompt-sequence.ts)：在 `onRoundComplete` 之后 drain **所有**待排队 prompts（而非一次 shift 一条），合并为多个 user message 进 `runRound([...prompts])` 单次 agent 调用。`runRound` 签名从 `(prompt: string)` 改为 `(prompts: string[])`，agent path 把数组拼成多个连续 `{ role: 'user', content: ... }` 块。

**优势**：
- N 条排队从 N 次 agent 调用降到 1 次（cost 节省 ~50-90%）
- LLM 在同一 context 看到全部排队意图，可做整体规划而非孤立处理
- Cache 命中率↑（同一 system prompt + 同一历史只算一次 cache）

**C6 — Slash 命令 mid-task 拒绝排队（实施期 2026-05-09 加入）**

发现 P0：CC `queueProcessor.ts:70` 在 dequeue 时把 slash 命令单独走 command pipeline。KodaX 队列把所有项当 plain text，drain 时 `runQueuedPromptSequence` verbatim 给 agent——**用户在 loading 时按 Enter 发 `/cost` 会被 LLM 当字符串收到**，明显错误。

**实施**（[`packages/repl/src/ui/InkREPL.tsx:6571`](../../packages/repl/src/ui/InkREPL.tsx#L6571)）：在 `handleSubmit` 的 isLoading 分支，检测 slash 前缀就 `emitInfoItemToCorrectLayer` 显示友好提示并 `return`——不入队、不丢、不当 plain text 发出去。

```ts
if (fullText.trimStart().startsWith('/')) {
  emitInfoItemToCorrectLayer({
    type: "info",
    icon: "⚠",
    text: 'Slash commands cannot be queued mid-task. Press Esc to abort the current task, then run the command.',
  }, 'queue-limit');
  return;
}
```

**对照 CC 的差异**：CC 实际上做得更多——区分 "immediate local-jsx commands"（如 `/help` / `/cost`）可以在 loading 中**立即同步执行**，与 "long-running slash commands" 进队列单步执行。KodaX 走的是更保守路径（拒绝 + 提示）。Future v0.7.39+ 可以分层加入 immediate-execute 路径。

**FEATURE_149 v0.7.38 最终 ship 边界**：Slice A（latency 清理）+ Slice B（B1 infra-only + B3 batched drain）+ Slice C（C1 up-arrow + C2 multi-line queue + C3 line-buffered streaming + **C4 activeForm spinner** + **C5 bash live progress** + **C6 slash-mid-task guard**）。CC 调研 5 项 + queue parity 14 维度全部 ship 或确认对齐。剩余 minor-drift 项（mode 字段 / uuid / MAX_PENDING_INPUTS 上限）经审查均不影响用户体验，留 v0.7.39+ 视实际反馈再处理。
