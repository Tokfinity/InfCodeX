# v0.7.50 Feature Designs

> 中文标题：`v0.7.50 Feature 设计`
>
> Version: `v0.7.50`
>
> Status: Planned (not yet released)
>
> Theme: **Dispatch-to-Self-Construction Bridge** — 给 `dispatch_child_task` schema 加 `subagent_type?: string` 可选字段，让 Worker 能直接派遣**用户在 Self-Construction 系统（FEATURE_087-090 / 101）下注册的自定义 agent**作为 child；同时引入 dynamic agent list cache 把已注册 agent 的描述符注入 Worker prompt 让 LLM 知道有哪些可调用的 specialist。

---

## 总览

KodaX 的 Self-Construction 系统（FEATURE_087-090 v0.7.28-32 + FEATURE_101 admission contract v0.7.31）已经允许用户**注册自己的 specialist agent**——比如 `db-reviewer` / `python-reviewer` / `e2e-runner` 等。但这些 agent **当前不能通过 `dispatch_child_task` 派遣**——dispatch 只能派"通用 anonymous child"。

这是一条 **architectural debt**：Self-Construction registry 和 dispatch_child_task 没有 wire 起来。Worker 想用 db-reviewer agent → 只能通过 system command（构造 admit 流程，不是 dispatch 路径），或者派一个 anonymous child + 在 child 的 prompt 里手动指定它要扮演 db-reviewer。

FEATURE_128 把两者连起来：

1. `dispatch_child_task` schema 加 `subagent_type?: string` 字段
2. Worker prompt 注入 dynamic agent list（缓存），LLM 看到哪些 specialist 可用 + 各自专长
3. dispatch 时 `subagent_type` 路由到 Self-Construction registry，注入对应 agent 的 system prompt + tool whitelist + capability tier

---

## FEATURE_128: Dispatch-to-Self-Construction Bridge — subagent_type Field + Dynamic Agent List Cache

**Status**: Planned
**Priority**: Medium
**Category**: Internal / Architecture

### 背景

#### 当前两个独立子系统

| 子系统 | 入口 | Agent 注册路径 | Agent 调用路径 |
|---|---|---|---|
| **Self-Construction**（FEATURE_087-090 / 101） | `kodax constructed admit` CLI | 用户写 manifest，admission contract 验证 7 invariant，runner.admit 5-step pipeline | `Runner.run(constructedAgent, ...)` 显式调用（不通过 dispatch） |
| **dispatch_child_task** | Worker tool | Anonymous（不注册）| `executeChildAgents([bundle], ctx)`（FEATURE_119 改为 Pattern B） |

两条路径不交汇——Worker 不能通过 dispatch 派 constructed agent。

#### 为什么这是债

- 用户花精力 admit 一个 db-reviewer 后，唯一的使用方式是通过 CLI 显式调用 `kodax run db-reviewer`，**LLM 在 coding session 里看不到这个 agent 存在**
- Worker 想审查 SQL 修改时只能：(a) 自己审；(b) 派 anonymous child + prompt 里手写 "扮演 db reviewer"。前者丢了 admission 验证，后者绕开了 specialist agent 的精炼 prompt
- KodaX 极简哲学讲究"agent 由数据驱动"——dispatch 应该看到 registry，registry 应该被 dispatch 消费

#### Phase 0.7 调研对照

Claude Code 通过 `subagent_type` 字段 + dynamic agent list 注入 prompt 直接桥接，6 个 built-in + 用户自定义都通过 dispatch 派遣。KodaX 的 Self-Construction 比 Claude Code 用户级 agent 系统更系统化（admission contract / capability tier / 5-step staircase），但**没接入 dispatch 是当前最大的"投入未变现"**。

#### 为什么放到 v0.7.50 不是更早

- FEATURE_087-090 / 101 在 v0.7.28-31 已 ship，registry / admission 已稳定
- FEATURE_119 (v0.7.36) Pattern B 是 dispatch 异步基础——FEATURE_128 在 Pattern B 之上加 subagent_type 字段而不是同期重构两次
- v0.7.36 - v0.7.44 有更迫切的多 agent 编排基础设施要做（message queue / envelope spillover [FEATURE_121 v0.7.40] / peer messaging / PM framework / memory）
- v0.7.50 在编排基础设施齐备后接入 Self-Construction 是最自然的 sequencing

### 设计

#### Step 1：dispatch schema 扩展

#### Step 2：dispatch 路由逻辑

`packages/coding/src/tools/dispatch-child-tasks.ts`：

```ts
async function* toolDispatchChildTask(input, ctx) {
  if (input.subagent_type) {
    const constructedAgent = ctx.constructionRuntime.getRegisteredAgent(input.subagent_type);
    if (!constructedAgent) {
      return `[Tool Error] subagent_type "${input.subagent_type}" not registered.
Available: ${ctx.constructionRuntime.listAgentNames().join(', ')}`;
    }
    // Re-admit at dispatch time（FEATURE_101 admission contract 在 dispatch 时再跑一次，
    // 防止注册后 manifest 被外部 tampered）
    const admitResult = await ctx.constructionRuntime.reAdmit(constructedAgent);
    if (!admitResult.passed) {
      return `[Tool Error] subagent_type "${input.subagent_type}" failed re-admission: ${admitResult.reason}`;
    }
    // 构造 child execution bundle 时使用 constructedAgent 的 system prompt / tool whitelist / capability tier
    const bundle = {
      ...buildBundleFromInput(input),
      systemPrompt: constructedAgent.systemPrompt,
      toolWhitelist: constructedAgent.toolWhitelist,
      capabilityTier: constructedAgent.capabilityTier,
    };
    // 既有 Pattern B launch
    const promise = executeChildAgents([bundle], ctx, options);
    ctx.childTaskRegistry.set(taskId, promise);
    return `task_id:${taskId} launched as ${input.subagent_type}.`;
  }
  // 无 subagent_type：既有 generic anonymous child 路径
  // ...
}
```

#### Step 3：`list_agents()` 工具

```ts
const listAgentsSchema = z.object({});

async function toolListAgents(_, ctx): Promise<string> {
  const agents = ctx.constructionRuntime.listAgents();
  return agents.map(a => `- ${a.name}: ${a.shortDescription} (tier: ${a.capabilityTier})`).join('\n');
}
```

#### Step 4：Dynamic agent list cache

启动时 + 每次 admit/remove constructed agent 后，刷新一份 agent 摘要数组：

```ts
// packages/agent/src/construction/agent-list-cache.ts
class AgentListCache {
  private cache: AgentSummary[] = [];

  rebuild(runtime: ConstructionRuntime): void {
    this.cache = runtime.listAgents().map(a => ({
      name: a.name,
      shortDescription: a.shortDescription,
      capabilityTier: a.capabilityTier,
    }));
  }

  injectIntoSystemPrompt(): string {
    if (this.cache.length === 0) return '';
    return `=== Registered specialist agents ===\n` +
      this.cache.map(a => `- ${a.name}: ${a.shortDescription} (tier: ${a.capabilityTier})`).join('\n') +
      `\n\nDispatch via dispatch_child_task(subagent_type="<name>", ...).\n` +
      `If you need a specialist not listed, dispatch generic (omit subagent_type).`;
  }
}
```

注入到 Worker system prompt 作为新 block。

#### Step 5：Worker prompt 引导

```
=== When to use subagent_type vs generic child ===

Use subagent_type=<name> when:
- The task matches a registered specialist's domain (e.g., SQL changes →
  db-reviewer; Python code review → python-reviewer)
- You want the specialist's curated system prompt + tool whitelist
- You want admission-validated quality (capability tier known)

Use generic child (omit subagent_type) when:
- No specialist matches
- Task is a simple parallel research / lookup
- You want flexibility (no tool whitelist restrictions beyond readOnly)
```

#### Step 6：Re-admit 性能

每次 dispatch 都 re-admit 是性能开销。FEATURE_101 admission 跑 7 invariant，预估 5-50ms。在 dispatch 路径加 re-admit：
- ✅ 安全（防 manifest tampering）
- ⚠️ 性能（额外 5-50ms × 每个 dispatch）

**优化**：admission result 缓存 5 分钟（manifest 文件 mtime 作为 cache key）。如 manifest 未变 → cache hit；变了 → 重跑。

### 验收标准

1. **subagent_type 路由正确**：dispatch 带 `subagent_type='db-reviewer'` → child 用 db-reviewer 的 system prompt + tool whitelist 启动
2. **未知 subagent_type 报错**：返 `[Tool Error] not registered. Available: [list]`
3. **Re-admit at dispatch**：dispatch 时跑一次 admission contract；manifest tampered 时拒绝
4. **Admit cache 命中**：未变 manifest 的连续 dispatch 不重跑 admission（cache hit）；mtime 变化后下一次 dispatch re-runs
5. **Agent list 注入 prompt**：Worker system prompt 中可见已注册 agent 列表 + 描述 + capability tier
6. **Worker 自决使用 subagent_type**：FEATURE_104 prompt eval 验证 Worker 在 specialist-applicable 场景下（如 SQL 改动）**主动**用 subagent_type；generic 任务不用
7. **list_agents 工具工作**：返回当前已注册 agent 列表（与 cache 一致）
8. **空 registry 不影响**：用户没注册任何 agent 时，agent list block 为空（不注入），Worker 仍能正常 dispatch generic child
9. **跨 family 验证**：4 family LLM specialist routing 正确率 max-min spread ≤ 15pp
10. **无回归**：FEATURE_087-101 / FEATURE_119 / FEATURE_120 路径全绿

### 非目标

- **不** 改 admission contract 7 invariant
- **不** 实现 dispatch-time agent generation（仅消费已 admit 的；运行时 generation 是 FEATURE_089 路径）
- **不** 在 prompt 注入 agent **完整** system prompt（只注入 short description + tier）
- **不** 实现 agent versioning（用户 re-admit 时覆盖）
- **不** 跨 session 持久化 admit cache（每 session 启动时 rebuild）
- **不** 引入 agent search by capability（list 一次 + LLM 自决足够）
