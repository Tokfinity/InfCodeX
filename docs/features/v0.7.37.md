## 总览

KodaX 当前 [`packages/ai/src/providers/anthropic.ts`](../../packages/ai/src/providers/anthropic.ts) 在响应解析层读 `cache_creation_input_tokens` / `cache_read_input_tokens` 字段（写入 cost-tracker 的 `cacheReadTokens` / `cacheWriteTokens`，[`packages/ai/src/cost-tracker.ts:14-17`](../../packages/ai/src/cost-tracker.ts#L14-L17)），但**请求构造时没有任何代码设置 `cache_control` marker**——这是把 Anthropic 系 provider 的 prompt cache 当成"自动开启的服务端能力"而非"客户端可控原语"。

[`packages/ai/src/providers/registry.ts`](../../packages/ai/src/providers/registry.ts) 的 13 个 provider 实例继承自 **3 个基类**：

| 基类 | 子类 | cache 协议 |
|---|---|---|
| `KodaXAnthropicCompatProvider` | anthropic / zhipu-coding / kimi-code / minimax-coding / mimo-coding / ark-coding（6 个） | 请求 body 内 `cache_control:{type:'ephemeral'}` marker |
| `KodaXOpenAICompatProvider` | openai / deepseek / kimi / qwen / zhipu（5 个） | 服务端自动 prefix cache（OpenAI / DeepSeek 自动；Kimi/Zhipu/通义自家 cache_id 端点不在 OpenAI 兼容协议表面上） |
| `KodaXAcpProvider`（CLI bridge） | gemini-cli / codex-cli（2 个） | 不直连 wire，子进程协议 |

业界对照：

- **Claude Code** 在 system prompt + tools section + agent definitions 三个稳定位置主动打 `cache_control: { type: 'ephemeral' }` marker，benchmark 实测可减少 60-90% cache miss
- **OpenAI / DeepSeek**：服务端自动 prefix cache，**客户端无需任何动作**
- **Kimi / Zhipu / 通义**：自家 cache 走独立 REST 端点（`POST /v1/caching` 注册 `cache_id`，请求带 header）——**不在 OpenAI 兼容协议表面上**，需要独立 cache_id 生命周期子系统（注册/失效/持久化）。本版本**显式不做**，留 v0.7.45+ 与 FEATURE_102 一起做

FEATURE_116 引入**单一 cache boundary 抽象**：lower 一次性下沉到 3 个 provider 基类（Anthropic-compat 加 `cache_control`；OpenAI-compat 与 ACP 仅 strip boundary marker），不是 13 个子类各自实现。上层 ai-layer 和 coding-layer 不需要知道每家 provider 的 cache 协议细节。

## FEATURE_116: Active Cache Control Foundation — cache_control Markers in 2 Provider Base Classes

**Status**: Planned
**Priority**: High
**Category**: Internal / Cost Optimization

### 背景

#### 当前 KodaX cache 状态

[`packages/ai/src/providers/anthropic.ts`](../../packages/ai/src/providers/anthropic.ts) 解析响应时读：

```ts
const cacheCreation = response.usage?.cache_creation_input_tokens ?? 0;
const cacheRead = response.usage?.cache_read_input_tokens ?? 0;
```

但请求构造时**不写** `cache_control`。这意味着：
- 即使是 stable system prompt 也每次重新计费 input tokens
- Tool definitions 大块（KodaX 当前 ~30 工具，~8k tokens）每次重新计费
- Worker role prompt（含 SCOPE COMMITMENT / dispatch RULE A/B/C / 协议描述，~4k tokens）每次重新计费

**Cost 估算（基于 FEATURE_098 per-model context window 数据）**：
- Anthropic Sonnet 4.6 input: $3/M tokens；cache hit: $0.30/M（90% off）
- Worker turn 平均 input ~12k tokens，其中 ~10k 是 stable（system + tool def + role prompt）
- 当前每 Worker turn input cost ≈ $0.036；启用 cache 后 ≈ $0.0066；节省 ~80%

#### Phase 0.7 调研对照

Claude Code 把 cache_control 打在 3 个稳定位置：
1. **System prompt 末尾**——整段 system prompt 作为 cache prefix
2. **Tools array 末尾**——整个 tools 定义作为 cache prefix
3. **Agent frontmatter mcpServers 末尾**——agent definition 作为 cache prefix

**关键观察**：cache_control marker 是 *suffix* 标记——表示"从开头到这里都缓存"，不是包裹某段。这是 Anthropic SDK 的语义。

#### KodaX 利好：prompt section 已有 `stability` 字段

[`packages/coding/src/prompts/sections.ts`](../../packages/coding/src/prompts/sections.ts) 的 `KodaXPromptSectionStability` 已经把 section 标注为 `stable | dynamic | project | specialist`——cache boundary 自然落在 `stable → 其他` 边界，**不需要手工插标记到任意位置**。`buildSystemPromptSnapshot`（[`prompts/builder.ts`](../../packages/coding/src/prompts/builder.ts)）和 `buildCapabilityContextSections`（[`prompts/capability-sections.ts`](../../packages/coding/src/prompts/capability-sections.ts)）已经把 13 段 capability section 集中收口（FEATURE_142 Batch E），是 cache lower 的天然接通点。

### 设计

#### 单一抽象：`KodaXCacheBoundary` 标记

`packages/ai/src/types.ts` 引入：

```ts
/**
 * Marks the end of a cacheable prefix in the request. Provider base classes
 * lower this to the wire-level cache_control marker their API expects:
 * - KodaXAnthropicCompatProvider: cache_control:{type:'ephemeral'} on last block
 * - KodaXOpenAICompatProvider: no-op (OpenAI/DeepSeek auto prefix cache; Kimi/Zhipu
 *   self-cache via separate cache_id endpoint deferred to v0.7.45+)
 * - KodaXAcpProvider (gemini-cli/codex-cli): no-op (CLI bridge does not touch wire)
 *
 * Place at the end of any stable section (system prompt, tools, role prompt).
 */
export interface KodaXCacheBoundary {
  readonly kind: 'cache-boundary';
  readonly hint?: 'system' | 'tools' | 'role-prompt';
}
```

请求层在构造 messages / system / tools 时插入 `KodaXCacheBoundary` 标记，**provider 基类**（不是子类）各自决定如何 lower。

#### 3 个标记位置

```
[
  ...stable system prompt blocks...,
  { kind: 'cache-boundary', hint: 'system' },     // ← 标记 1
  ...volatile system prompt blocks（用户级 context）...,
]

tools: [
  ...all tool definitions...,
  { kind: 'cache-boundary', hint: 'tools' },      // ← 标记 2（tools 末尾）
]

role-prompt:
  [...stable role prompt blocks...,
   { kind: 'cache-boundary', hint: 'role-prompt' }, // ← 标记 3
   ...per-turn dynamic context...]
```

由于 [`prompts/sections.ts`](../../packages/coding/src/prompts/sections.ts) 已有 `stability` 字段，标记 1 + 标记 3 的插入可以基于现有 stability 边界**自动派生**，不需要为本 feature 单独维护 stable/volatile 切分逻辑。

#### Lower 实现下沉到 3 个基类

[`packages/ai/src/providers/registry.ts`](../../packages/ai/src/providers/registry.ts) 实证 13 个 provider 实例继承自 3 个基类。lower 只需在 **3 个基类**实现：

| 基类 | Lower 行为 | 覆盖子类 |
|---|---|---|
| `KodaXAnthropicCompatProvider` | 遇 `KodaXCacheBoundary` → 在 wire 上把它前一个 block 的字段加上 `cache_control:{type:'ephemeral'}`，然后 strip 掉 boundary 自身 | anthropic / zhipu-coding / kimi-code / minimax-coding / mimo-coding / ark-coding（6 子类） |
| `KodaXOpenAICompatProvider` | 遇 `KodaXCacheBoundary` → 直接 strip（OpenAI / DeepSeek 自动 prefix cache；Kimi/Zhipu OpenAI 兼容路径无 client-side cache 接口） | openai / deepseek / kimi / qwen / zhipu（5 子类） |
| `KodaXAcpProvider`（CLI bridge） | 直接 strip（CLI bridge 不直连 wire，避免把 boundary marker 误传给子进程） | gemini-cli / codex-cli（2 子类） |

**实现量估计**：lower helper（~30 行）+ Anthropic-compat lower 钩子（~25 行）+ OpenAI-compat strip 钩子（~10 行）+ ACP strip 钩子（~5 行）= **~70 行**，远低于设计稿原版"~30 行 × 12 = ~360 行"的高估。

#### 显式不做：Kimi / Zhipu / 通义自家 cache_id 端点集成

这三家在 OpenAI 兼容路径下没有客户端 cache 接口；自家 cache 走独立 REST 端点（如 Kimi `POST /v1/caching` 返 cache_id，请求带 `X-Msh-Context-Cache` header），需要独立子系统：cache_id 生命周期管理（注册 / 查询 / 失效 / 持久化）+ TTL 处理 + 跨 KodaX session 持久化。这是 ~3-5 天工作量的独立 feature，**留 v0.7.45+ 与 FEATURE_102 capability profile 一起做**。本版本 OpenAI-compat 路径全 no-op——Anthropic 路径用户拿到 90% off 主要价值，OpenAI/DeepSeek 用户继续享受服务端自动 prefix cache 不变，Kimi/Zhipu OpenAI-compat 路径用户**无回退也无新省**（与现状一致）。

#### 测量与验证

[`packages/ai/src/cost-tracker.ts`](../../packages/ai/src/cost-tracker.ts) 已经记录 `cacheReadTokens` / `cacheWriteTokens`（不是设计稿原版误称的 `cacheReadInputTokens` / `cacheCreationInputTokens`，实际字段在 `cost-tracker.ts:14-17`）。FEATURE_116 新增 `cacheHitRate` 字段：`cacheReadTokens / (cacheReadTokens + cacheWriteTokens)`。

```
Acceptance: 启用 cache_control 后，5 分钟 TTL 窗口内连续 5 个 Worker turn
的 cacheHitRate ≥ 70%（首 turn 全是 write；后续 turn 在 stable 部分应全是 read）
```

> Anthropic ephemeral cache TTL 5 分钟——超过该窗口必然 miss，不算 acceptance 失败。

### 验收标准

1. **Anthropic 路径 cache 命中**：5 分钟 TTL 窗口内连续 5 个 Worker turn，第 2 turn 起 cacheHitRate ≥ 70%
2. **OpenAI-compat 路径 strip**：boundary marker 不出现在 OpenAI / DeepSeek / Kimi / Qwen / Zhipu 任一 wire request 中；不影响 OpenAI / DeepSeek 的服务端自动 prefix cache 行为（响应中 `cached_tokens` 字段照旧）
3. **CLI bridge strip**：boundary marker 不出现在 gemini-cli / codex-cli 的子进程 input 中
4. **首 turn 退化**：首 turn 必然全是 write（无可读），cacheHitRate=0% 不算失败
5. **Volatile 部分不缓存**：volatile system prompt section（`stability !== 'stable'`）修改不导致整段 cache miss
6. **跨 provider 一致**：同一 Worker turn 切 provider 不破 cache（cache 是 provider 内部的）
7. **`/cost` 命令输出 cacheHitRate**：用户能看到节省效果
8. **无回归**：`npm run test` / `npm run build` 全绿；FEATURE_092 / FEATURE_104 / FEATURE_106 路径不受影响

### 非目标

- **不** 引入 cache invalidation 主动控制（boundary 是 suffix marker，没有"主动 invalidate" 概念）
- **不** 在用户代码中暴露 cache_control 概念（封装在 ai-layer）
- **不** 跨 provider 共享 cache（每家 provider 独立）
- **不** 持久化 cache（5 分钟 TTL 由 provider 决定）
- **不** 集成 Kimi / Zhipu / 通义自家 cache_id 端点（独立 cache_id 子系统留 v0.7.45+ 与 FEATURE_102 一起做）
- **不** 优化 child agent 的 cache（child 走独立 session，FEATURE_117 v0.7.38 处理 read-path stripping 是另一个维度）
- **不** 引入 cache-aware routing（FEATURE_102 v0.7.45 才考虑）
- **不** 在 13 个 provider 子类各自实现 lower（lower 全部下沉到 3 个基类）

### 与其他 Feature 的关系

- **依赖 FEATURE_098（已 ship）**：per-model context window 数据是 cost 估算前提
- **辅助 FEATURE_117（v0.7.38）**：read-path stripping 减少 child invocation 的 input tokens；FEATURE_116 减少 stable 部分的 cache miss——两个独立维度的成本优化

### Sub-task 116-D: DeepSeek 私有 cache 字段适配（已 ship 2026-05-08）

**Status**: ✅ **Shipped 2026-05-08** — 在 [`packages/ai/src/providers/openai.ts`](../../packages/ai/src/providers/openai.ts) 加 OpenAI 标准 → DeepSeek 私有的 fallback 链 + 7 个单元测试 ([`openai-usage-cache-fields.test.ts`](../../packages/ai/src/providers/openai-usage-cache-fields.test.ts))。包含真 OpenAI 字段、DeepSeek 私有字段、双字段共存优先级、null/负数防御、DeepSeek docs 标准响应 shape 5 个核心 case + 2 个边界 case。148/148 既有 provider 测试不退化。同 v0.7.37 release 出。
**Actual effort**: ~30 分钟。下方原 brief 内容保留作为 ship 时的执行档案 + 未来回看时的方向区分参考。

#### 问题陈述

KodaX 当前用 OpenAI-compat 路径（`baseUrl: 'https://api.deepseek.com'`）调 DeepSeek。response usage 解析在 [`packages/ai/src/providers/openai.ts:74-78`](../../packages/ai/src/providers/openai.ts#L74-L78) 只读 OpenAI 标准字段：

```typescript
const cachedReadTokens =
  typeof usage.prompt_tokens_details?.cached_tokens === 'number' &&
  usage.prompt_tokens_details.cached_tokens >= 0
    ? usage.prompt_tokens_details.cached_tokens
    : undefined;
```

但 **DeepSeek 不返回 `prompt_tokens_details.cached_tokens`**——它返回**自己的私有字段名**（已查证 https://api-docs.deepseek.com/zh-cn/api/create-chat-completion 2026-05-08）：

```json
{
  "usage": {
    "completion_tokens": 100,
    "prompt_tokens": 1000,
    "prompt_cache_hit_tokens": 800,    ← DeepSeek 私有字段（顶级 usage 下，不嵌套）
    "prompt_cache_miss_tokens": 200,    ← DeepSeek 私有字段
    "total_tokens": 1100,
    "completion_tokens_details": {
      "reasoning_tokens": 0
    }
  }
}
```

不变量：`prompt_tokens === prompt_cache_hit_tokens + prompt_cache_miss_tokens`（即 `prompt_cache_hit_tokens` 是 `prompt_tokens` 的子集，与 OpenAI `prompt_tokens_details.cached_tokens` 同语义）。

**当前后果**：
- DeepSeek 跑下来 KodaX cost-tracker 看到的 `cachedReadTokens` 永远是 `undefined`
- DeepSeek V4 Pro cache hit 折扣（[`cost-rates.ts:33`](../../packages/ai/src/cost-rates.ts#L33)，`inputPer1M: 1.68 → cachePer1M: 0.14`，约 12% 价格）**完全没生效**——所有 cache hit 都按 input 全价计费
- FEATURE_098 cost reporting / FEATURE_102 routing 决策拿到的 cache hit rate 是错的（永远 0%）

#### 三类 endpoint 对比（已查证）

| 接口 | base URL | 字段位置 | KodaX 现状 | 推荐 |
|---|---|---|---|---|
| **OpenAI-compat（当前）** | `https://api.deepseek.com` | `usage.prompt_cache_hit_tokens` 顶级 | ❌ 读不到（读的是 `prompt_tokens_details.cached_tokens`） | **修复** |
| Anthropic-compat | `https://api.deepseek.com/anthropic` | docs 完全没提 cache 统计字段（`cache_control` 也明确写 "Ignored"） | N/A（KodaX 没用此路径） | **不切**——Anthropic-compat 缺 cache 统计 + 缺 image/document/search content + thinking budget 被忽略 + 仅支持 deepseek-v4-pro 单模型 |
| DeepSeek 自家 KV cache 端点 | 无（无独立 endpoint） | 全自动，无客户端控制 | N/A | **不需要做**——服务端自动，cache breakpoint 由 DeepSeek 服务端按 request 边界 / 公共前缀 / 固定 token 间隔自动创建 |

**结论**：DeepSeek cache 完全在 OpenAI-compat 接口下工作，KodaX 不需要切接口，**只需要在 OpenAI 用法解析器里多读一个字段名**。

#### 实施步骤

**Step 1**：扩展 [`OpenAIUsageLike`](../../packages/ai/src/providers/openai.ts#L45-L52) 类型 + `normalizeOpenAIUsage` 解析逻辑

```typescript
// packages/ai/src/providers/openai.ts:45-52
type OpenAIUsageLike = {
  prompt_tokens?: number;
  completion_tokens?: number;
  total_tokens?: number;
  prompt_tokens_details?: {
    cached_tokens?: number | null;
  } | null;
  // FEATURE_116 Sub-task D: DeepSeek private field. Top-level under
  // `usage`, not nested. Co-exists with OpenAI's `prompt_tokens_details.cached_tokens`
  // (different providers use different field names; we read whichever
  // is present, OpenAI standard wins on conflict for forward compat).
  prompt_cache_hit_tokens?: number | null;
  prompt_cache_miss_tokens?: number | null;
} | null | undefined;

// packages/ai/src/providers/openai.ts:74-78
const cachedReadTokens =
  // OpenAI standard takes priority (forward compat: if DeepSeek
  // ever adds the OpenAI field, prefer the standard one)
  (typeof usage.prompt_tokens_details?.cached_tokens === 'number' &&
   usage.prompt_tokens_details.cached_tokens >= 0
    ? usage.prompt_tokens_details.cached_tokens
    : typeof usage.prompt_cache_hit_tokens === 'number' &&
      usage.prompt_cache_hit_tokens >= 0
      ? usage.prompt_cache_hit_tokens
      : undefined);
```

**Step 2**：单元测试 — 在 [`packages/ai/src/providers/openai-message-serialization.test.ts`](../../packages/ai/src/providers/openai-message-serialization.test.ts) 或新文件 `openai-deepseek-cache-fields.test.ts` 加 4 个 case：

| DeepSeek 私有字段单独存在 | `prompt_cache_hit_tokens: 600` | 600 |

## FEATURE_141: Transcript Inline Diff Renderer — Edit / Multi-Edit / Write Tool Result Hunk Display

**Status**: Planned
**Priority**: High
**Category**: Enhancement / UX

### 背景

#### 当前 KodaX 状态（核查实证 2026-05-08）

`packages/coding/src/tools/edit.ts` / `multi-edit.ts` / `write.ts` 内部使用 KodaX **自实现** [`generateDiff`](../../packages/coding/src/tools/diff.ts)（**不是** 设计稿原版误称的 `diff` 包 `structuredPatch`，KodaX 也未引入 `diff` npm 依赖）生成 unified-diff 字符串，并通过 [`formatDiffPreview`](../../packages/coding/src/tools/truncate.ts) 把它附加到 tool result 字符串末尾。

```bash
# 核查命令（2026-05-08）
$ rg -l 'generateDiff' packages/coding/src/tools/
# 命中 edit.ts:5 / multi-edit.ts:23 / write.ts:5 / insert-after-anchor.ts

$ rg -nE 'formatDiffPreview' packages/coding/src/tools/edit.ts
# edit.ts:7   import { formatDiffPreview } from './truncate.js';
# edit.ts:169 const preview = await formatDiffPreview({ diff, toolName: 'edit', ... });
# edit.ts:170 result += `\n\n${preview}`;
```

**真实差距**：tool result 字符串里**已经包含** unified-diff 文本（含 `@@ ` 行 / `+`/`-`/` ` 行），用户在 transcript 已经能看到 diff 内容——但 REPL 把它当**纯文本**渲染，没有按 `+` / `-` / `@@` 行前缀**着色**。

```
当前用户在 transcript 看到（无颜色）：
  ✔ Edit packages/coding/src/foo.ts
    (+3 lines, -1 lines)

  --- packages/coding/src/foo.ts
  +++ packages/coding/src/foo.ts
  @@ -42,7 +42,9 @@
     function processInput(input: string) {
  -    return input.toLowerCase();
  +    if (!input) return '';
  +    const normalized = input.trim().toLowerCase();
  +    return normalized;
     }
```

期望体验：`+` 行绿色、`-` 行红色、`@@` 灰色——这是 FEATURE_141 唯一要补的。设计稿原版"transcript 完全没有 diff 渲染组件"是夸大表述。

#### 为什么这是 138（Turn Diff Dialog）的前置

[FEATURE_138 Turn-Level Diff Dialog](../../FEATURE_LIST.md)（claudecode 风格 `/diff` overlay）需要在 REPL 端把 turn 内多次 edit 的 unified-diff 文本合并展示——141 在 REPL 端建立的 unified-diff parser + DiffHunk 渲染组件**正是 138 的 UI 底座**。先做 141 着色（满足"看到改了什么"的基础需求），再根据用户实际反馈决定是否补 138 turn-level 聚合。

#### 业界对照

- **Claude Code**：每次 FileEdit / FileWrite 工具结束在 transcript 渲染 colored hunk（`+` 绿 / `-` 红 / context 灰）+ 行号 + 文件路径
- **opencode**：同上，且文件首次 read 时 lazy-cache，edit 时基于 cache 渲染
- **Cursor / Aider / 其他主流 coding agent**：都做 inline diff

KodaX 是**唯一一个 transcript 不对 diff 着色的主流 coding agent**——unified-diff 文本已经在 result 里，但是无颜色纯文本，体验上比同行差一截。

### 设计

#### 数据流（A 方案：REPL parse 既有 unified-diff 文本，零 wire format 改动）

```
edit / multi-edit / write tool
  ├─ 既有：调 generateDiff(oldContent, newContent, filePath) 生成 unified-diff 字符串
  ├─ 既有：调 formatDiffPreview 把 diff 字符串拼到 tool result 末尾
  └─ 既有：返 string tool result（含 unified-diff 文本）—— 不动

REPL 渲染层：
  └─ 新增：tool result 文本扫描 → 识别 unified-diff 段（含 ^@@ .+ @@$ 行）
        → 切成 [前缀文字] + [DiffHunk 组件] 两段渲染
        → DiffHunk 按 + / - / @@ / ' ' 行前缀着色
```

**为什么选 A 不选 B（结构化 payload 旁路）**：

| 维度 | A 方案（本设计） | B 方案（设计稿原版：`KodaXToolResult` 加 `diff?` 字段） |
|---|---|---|
| 改动文件数 | 2-3 个（仅 `packages/repl/src/ui/`） | 30+ 个（`packages/ai/src/types.ts` `KodaXToolResultBlock.content: string` 是 LLM 协议层契约 + 13 个 provider serialization 路径 + child 冒泡 + persistence + repl） |
| LLM wire format 风险 | 0 | 高（漏一个 provider serialization 就把 `[object Object]` 发给 LLM） |
| 当前 use case 数 | 1（着色） | 1（着色）→ 抽象浪费 |
| 工时 | 2-2.5 天 | 5+ 天 |

A 方案契合 KodaX `Add code cautiously` / `NEVER add abstractions until 3+ concrete use cases` 哲学。FEATURE_138 turn-level overlay 若未来真要做且 parsing 不够用，那时累计 ≥2 use case，再升级到 B。

#### 渲染规范

```
✔ Edit packages/coding/src/foo.ts  (+3 -1)

  @@ 42,7 +42,9 @@
   function processInput(input: string) {
  -  return input.toLowerCase();
  +  if (!input) return '';
  +  const normalized = input.trim().toLowerCase();
  +  return normalized;
   }
```

**视觉规范**：
- 文件标题行：`✔ <Tool> <path>` + 右对齐 `(+N -N)` 数字摘要
- Hunk 头：`@@ <oldStart>,<oldCount> +<newStart>,<newCount> @@` 灰色
- 增加行：前缀 `+` + 整行绿色背景或绿色前景（取决于主题）
- 删除行：前缀 `-` + 整行红色
- 上下文行：前缀 ` `（空格）+ 默认色
- 多 hunk：hunk 之间空行分隔
- 多文件（`multi_edit`）：每个文件独立标题块

#### 折叠 / 展开（避免大文件刷屏）

- 默认显示前 8 行 + 后 8 行（共 16 行 / hunk）
- 超过则中间显示 `... <N> lines collapsed; full diff persisted at <path> ...`（依赖既有 [`formatDiffPreview`](../../packages/coding/src/tools/truncate.ts#L267) 的 `persistToolOutput` 机制，把完整 diff 写文件并在提示里给路径）
- **v1 不做 inline 交互**——KodaX 当前没有 transcript 内交互能力（hover / 折叠展开切换 / 跳转），用户想看完整 diff 直接打开 persisted 文件即可
- 极端大 diff（>200 行）只显示文件名 + 摘要 + 提示 `[diff too large; run \`git diff\` for full view]`

#### Theme awareness

复用 [FEATURE_007 Theme System Consolidation](../../FEATURE_LIST.md) 之前已有的 theme primitives：
- 绿色 token（add）
- 红色 token（remove）
- 灰色 token（context / hunk header）
- 黑底 / 白底自动适应

如 FEATURE_007 未 ship，先用硬编码 `theme.diff.add` / `theme.diff.remove` 后续替换。

#### 与 multi_edit 协同

`multi_edit` 一次调用改一个文件多个位置：UI 把所有 hunks 渲染在同一文件标题块下，按行号排序。

#### 与 write（新建文件）协同

新建文件 = 全部新增。渲染为单 hunk，无 `-` 行，标题 `+ Created packages/coding/src/foo.ts (+N lines)`。

#### 与 dispatch_child_task 协同（v1：自然继承，不另建旁路）

KodaX 当前 child agent 的原始 tool result **不会**逐条冒泡到主 transcript——会被打包成 child summary 字符串。**v1 不为 child 单独建立 diff 旁路事件流**，原因：
- A 方案的 REPL parser 不区分文本来源——只要 child summary 文本里包含 unified-diff（含 `@@ ` 行），主 transcript 就**自动**着色
- 子 agent 的 summary 模板里粘 diff 文本是自然行为（这取决于子 agent 怎么写自己的总结）
- 如果未来用户反馈"我想看 child 内部每次 edit 的逐条 diff" → 那时再做正式的 child diff 旁路（届时是真实 user request 不是预测，符合 KodaX 哲学）

跨层旁路代码（child→parent diff 事件流 + scope 维护 + 渲染缩进）**显式不做**——v1 仅依赖 A 方案 parser 自然覆盖。

#### Pre/Post tool 执行的渲染时机

不在 tool 执行**前**做 preview（那是 FEATURE_138 的责任）。141 仅在 tool 完成**后**展示已发生的变更。

### 影响范围

### 验收标准

## FEATURE_148: Pattern B Post-Dispatch Probe — Anti-Immediate-Await Rule + Layer 2 Single-Turn 行为 eval

**Status**: Shipped 2026-05-08（与 v0.7.37 同期 ship，原计划 v0.7.37.1，最终 fold 进 v0.7.37 重发）
**Priority**: High
**Category**: LLM Prompt / Quality Gate

### 背景

v0.7.36 FEATURE_119 ship 了 Pattern B（`dispatch_child_task` + `await_child_task` 拆分），v0.7.37 FEATURE_146-B 验证了**单轮 parallel-dispatch 触发率**（5 alias × 5 task，76-88% 远超 60% PASS 门）。但用户实战日志里观察到 Worker 在多轮鲁棒性上有一个**结构 eval / 单轮 eval 都查不到的退化模式**：

```
T+0s:  Worker → dispatch_child_task("research-X")  →  task_id:child-1 launched
T+1s:  Worker → await_child_task("child-1")        →  阻塞等 30-90s
T+90s: child-1 完成，await 解锁
T+91s: Worker 才开始原本可以 T+1s 就开始做的并行工作 Y
```

**这是"派出去 → 立即 await"的 sync degeneration**：Pattern B 工具表面健康（dispatch + await 都被调用），但 Worker 仍然 wall-clock 阻塞在每个 child 后面，FEATURE_119 想消灭的核心架构债没真正解决。

#### 单轮 eval 测不出的原因

[v0.7.37.md:494-496](#) 已经写明：FEATURE_146-B 是**单轮探针**，dispatch 工具不真执行，LLM 在同轮拿不到 `task_id:<id>` 回执 → 同轮内必然 0 个 await call → orphan rate=100% 是单轮 baseline，**不是回归信号**。要测"派出去后下一步是 await 还是别的工具"必须**多轮 + mock executor**。

v0.7.37 Step 0.5 显式 skip 了 `mockChildExecutor` primitive（成本 / scope 取舍）。本 feature 加上 Worker prompt 的 anti-immediate-await 反例硬约束，并按 [`benchmark/EVAL_GUIDELINES.md`](../../benchmark/EVAL_GUIDELINES.md) **Layer 2 single-turn probe** 设计行为 eval 作为 ship gate。

#### 方法论说明（重要：本 feature 经历过一次 layer 误用）

初版本曾设计为多轮 mock executor harness（dispatch_child_task → 合成 task_id 回执 → LLM 自由决策下一轮 → 跑 6 轮 → aggregate trace 算指标）。这是 [`EVAL_GUIDELINES.md` §反模式 2](../../benchmark/EVAL_GUIDELINES.md#反模式-2让-llm-自由跑然后我们解读)：**让 LLM 自由跑 N 轮再解读 aggregate**——prompt 微调的效果被 N 轮自由决策的累积噪声淹没。

正确做法是 **Layer 2 single-turn probe**：构造"刚刚 dispatch 完，task_id 已回执"的 pre-canned 3-message history，**单次 LLM call**，机械化断言"下一个 tool_use 是不是 `await_child_task` on `child-1`"。FEATURE_146-B 用的就是这个 pattern，本 feature 对齐。

### 设计

#### Step 1：Layer 2 single-turn probe + 数据集

[`benchmark/datasets/pattern-b-post-dispatch-probe/cases.ts`](../../benchmark/datasets/pattern-b-post-dispatch-probe/cases.ts)（5 个场景）+ [README](../../benchmark/datasets/pattern-b-post-dispatch-probe/README.md)。

每个场景的 canned 3-message history：

1. **user message** — 任务里**显式说**"WHILE X (slow) runs, also do Y (cheap)"，Y 是独立于 child 输出的便宜工作（read / 第二个 dispatch / 总结草稿）
2. **assistant message** — 中性文本"I'll dispatch … as a background child task." + 一个 `dispatch_child_task` tool_use
3. **user message** — 一个 `tool_result` block，content = `task_id:child-1 launched. ...`（与 [`packages/coding/src/tools/dispatch-child-tasks.ts`](../../packages/coding/src/tools/dispatch-child-tasks.ts) 真实回执措辞一致）

assistant 文本**故意中性**，不预先承诺"接下来我读 Y"——下一个决策只受 system prompt + user task + task_id banner 驱动。

5 个场景：

| Scenario | 慢任务（已 dispatch） | 用户显式要求的 side-task |
|---|---|---|
| `long-test-with-side-read` | npm test ~90s | 读 package.json |
| `three-fanout-with-side-readme` | 3 个 test child 中的第 1 个 | 读 README.md |
| `slow-grep-with-side-tsconfig` | 全 repo grep | 读 tsconfig.json |
| `long-build-with-side-changelog` | npm run build ~60s | 读 CHANGELOG.md |
| `parallel-research-with-side-package` | 2 个 research child 中的第 1 个 | 读 package.json |

#### Step 2：Worker prompt anti-immediate-await rule

[`packages/coding/src/agents/worker-role-prompt.ts`](../../packages/coding/src/agents/worker-role-prompt.ts) `dispatchRules` 段加 1 条新规则：

```
- ANTI-PATTERN — DO NOT IMMEDIATELY AWAIT (FEATURE_148): after
  `dispatch_child_task` returns a `task_id:<id>`, your IMMEDIATE next
  move must NOT be `await_child_task` on that id when there is OTHER
  USEFUL WORK to do. Useful work includes: dispatching ADDITIONAL
  independent children, doing the SIDE-READS the user asked for in
  the same request, drafting a synthesis plan in text, OR reading
  context that will let you act on the child result faster once it
  arrives. Only call `await_child_task` when (a) you actually need
  the result to proceed and have run out of interleaved work, or
  (b) the user explicitly asked for the dispatched probe and nothing
  else. Concretely: if the user asks "do X (slow) AND also do Y
  (cheap)" — dispatch X, then DO Y, then await X. Awaiting X
  immediately after dispatch and only then doing Y collapses
  Pattern B back to a sync call with extra steps.
```

设计要点：
1. **具象的反例**（"dispatch X, then DO Y, then await X"）比抽象规则更有效——LLM 在 worker prompt 调研里反复证明命令式具体语句驱动行为优于声明式抽象规则
2. **明确"什么算 useful work"**——避免 LLM 把"think hard about X"也当成"useful work"过度延后 await
3. **保留 await 合理 case**——明确 (a) 真需要结果 (b) 用户只问了那一件事 → 这两种情况下立即 await 是对的，不是退化

#### Step 3：Layer 2 single-turn probe eval

[`tests/feature-148-post-dispatch-probe.eval.ts`](../../tests/feature-148-post-dispatch-probe.eval.ts) 跑 5 alias × 5 scenario × **N=3 reps = 75 probes**。每个 probe 是 **单次 `provider.stream`** 调用，传入 canned 3-message history，断言：

```typescript
degenerate :=
  result.toolBlocks[0]?.name === 'await_child_task'
  && (result.toolBlocks[0].input as {task_id?: string}).task_id === 'child-1'
```

机械化（无 LLM judge / 无人工 looks-good）。N=3 absorbs single-call 抖动；tool-name selection 比 text-quality 方差低，5+ 不必要。

### 通过门

| 指标 | PASS | INCONCLUSIVE | FAIL |
|---|---|---|---|
| **degenerate-rate** (load-bearing) | ≤ 40% | 40-70% | > 70% |
| **per-alias degenerate-rate** | informational | — | — |
| **non-degenerate next-tool histogram** | informational | — | — |

只 **FAIL gate** 在 vitest 里硬断言（>70% 红 CI）。PASS 是 aspirational，落 40-70% 区间记 INCONCLUSIVE 不阻塞——首版补丁出来落地数据后下一版可以再收紧门。

3. **AI 抽象层名字 `@kodax/ai` 与 org `@kodax-ai` 重复尴尬**：发到 npm 后是 `@kodax-ai/ai`，重复"ai"语义

### 为什么 `ai` 子包要改名为 `llm`

当前内部叫 `@kodax/ai`，发布后变 `@kodax-ai/ai`——重复"ai"语义令人困惑（用户看到 `npm install @kodax-ai/ai` 不知道这是干什么的）。把这个包改名为 **`llm`**：

- 准确：包内容是 LLM 抽象层（13 个 provider 实例 / 3 个 provider 基类 + cost-tracker + retry/backoff + token 计数），不只是"AI"这个泛词
- 内部代码不改：`KodaXBaseProvider` / `KodaXEvents` 等类名照旧，只改包名 + import 路径
- 跟同行一致：`@anthropic-ai/sdk`, `@google/generative-ai` 类似命名都靠"领域词 + 抽象层名"

替代候选（已评估并否决）：
- `provider`：单数，跟内部目录 `packages/ai/src/providers/` 复数不一致
- `providers`：跟内部基类 `KodaXBaseProvider`（单数）不一致
- `ai`（不改）：与 org 名 `@kodax-ai` 直接重复，差

#### B-Special. `@kodax/ai` → `@kodax-ai/llm` 改名策略

- **保留 `packages/ai/` 目录名不变** —— 仅改 `packages/ai/package.json:name` 字段（`"@kodax/ai"` → `"@kodax-ai/llm"`）。原因：避免 git history 跨目录 rename 断链，CHANGELOG / docs 中对 "ai 层" / "AI abstraction" 的语义一致性保留
- 同步改其他 8 个包的 `package.json:dependencies` + 3 个 tsconfig paths + ~290 处 `@kodax/ai` import → `@kodax-ai/llm`
- 内部代码（`KodaXBaseProvider` / `KodaXEvents` 等类名）**零改动**——只改包名 + import 路径，不动 API surface

#### C. publish-only 字段补全（每个 `packages/*/package.json` 都加）

```json
{
  "files": ["dist", "README.md", "LICENSE"],
  "publishConfig": { "access": "public" }
}
```

`files` 防止默认把整个目录（含 src / 测试 / node_modules 残留）打进 tarball，包体积爆炸。`publishConfig.access: public` 让 scoped 包默认 public（不加的话 npm 按"私有 scope"对待，会要求订阅付费版）。

#### D. 把 workspace 通配 `*` 改为 `workspace:^` 协议

monorepo workspace 内 `"@kodax/agent": "*"` 在本地工作正常（npm workspaces 解析到本地目录），但发到 registry 后用户安装拉不到具体版本。npm 9+ 已稳定支持 `workspace:^` 协议——发布时**自动展开为 `^<currentVersion>`**（即 `^0.7.37`），本地仍按 workspace 解析。

**直接选 `workspace:^`**，不留 fallback 路径（手动 `^0.7.37` 字符串），简化方案。

#### E. 写一键发布脚本 `scripts/release-npm.mjs`

依次发布（依赖顺序，2026-05-08 校准 — session-lineage 实证**真实运行时**依赖 agent，非 phantom dep）：
```
1.  @kodax-ai/llm                  (no internal deps)
2.  @kodax-ai/tracing              (no internal deps)
3.  @kodax-ai/repointel-protocol   (no internal deps)
4.  @kodax-ai/skills               (no internal deps)
5.  @kodax-ai/agent                (deps on llm + tracing)
6.  @kodax-ai/session-lineage      (deps on llm + agent — agent 真依赖，session-lineage/compaction/compaction.ts:11 值 import countTokens / estimateTokens；必须晚于 agent)
7.  @kodax-ai/mcp                  (deps on llm + agent)
8.  @kodax-ai/coding               (deps on agent + llm + mcp + repointel-protocol + session-lineage + skills)
9.  @kodax-ai/repl                 (deps on agent + coding + session-lineage + skills)
10. @kodax-ai/cli                  (deps on coding + repl + skills) — root → 替换占位 @kodax-ai/cli@0.0.1
```

> 设计稿原版注释"agent 是 phantom dep"**错误**——子 agent 实证 `packages/session-lineage/compaction/compaction.ts:11` 实际 `import { countTokens, estimateTokens } from '@kodax/agent'`（值 import，不是 type-only）；`session-lineage/package.json:23` 也声明在 `dependencies`（非 `devDependencies`）。发布顺序必须 agent 早于 session-lineage。

脚本支持：
- `--dry-run`：所有 publish 走 `--dry-run`
- `--only=<pkg>`：只发指定包（用于 patch release）
- 自动跑 `npm run build` 前置
- 失败回滚提示（npm publish 不可撤回，回滚靠 `npm deprecate`）

#### CHANGELOG 中需写的 migration note 模板

```markdown
### Breaking changes (npm scope migration)

The internal `@kodax/*` package scope has been renamed to `@kodax-ai/*`
to align with the npm-published org. The `@kodax/ai` package has
additionally been renamed to `@kodax-ai/llm` to remove redundant 'ai'
in the name (`@kodax-ai/ai` is awkward).

**Impact**:
- CLI users: no impact (use `npm install -g @kodax-ai/cli` from now on,
  but `git clone + kodax` still works as before).
- Library consumers via npm: this is the first npm publish, so there
  are no prior consumers to migrate.
- Library consumers via git clone + workspace integration: replace all
  `@kodax/` with `@kodax-ai/` in your imports, and `@kodax/ai` →
  `@kodax-ai/llm`.

Sed migration helper:
\`\`\`bash
find . -type f \( -name '*.ts' -o -name '*.tsx' -o -name '*.js' -o -name '*.mjs' \) \
  -not -path '*/node_modules/*' -exec sed -i \
  -e 's|@kodax/ai|@kodax-ai/llm|g' \
  -e 's|@kodax/|@kodax-ai/|g' {} +
\`\`\`

Replacement order matters: do `@kodax/ai` → `@kodax-ai/llm` FIRST, then
the catch-all `@kodax/` → `@kodax-ai/` second, otherwise the first
substitution will also match `@kodax/ai` and produce `@kodax-ai/ai`.
```
