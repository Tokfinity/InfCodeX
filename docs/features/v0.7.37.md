## 总览

KodaX 当前 [`packages/ai/src/providers/anthropic.ts`](../../packages/ai/src/providers/anthropic.ts) 等 provider 适配器在响应解析层读 `cache_creation_input_tokens` / `cache_read_input_tokens` 统计字段（用于 cost-tracker），但**没有任何代码主动设置 `cache_control` marker**——这是把 Anthropic / Bedrock / Vertex 等 provider 的 prompt cache 当成"自动开启的服务端能力"而非"客户端可控原语"。

业界对照：

- **Claude Code** 在 system prompt + tools section + agent definitions 三个稳定位置主动打 `cache_control: { type: 'ephemeral' }` marker，benchmark 实测可减少 60-90% cache miss
- **OpenAI** 没有 cache_control 概念但有 prompt-prefix 自动复用
- **DeepSeek / Kimi / Zhipu** 各家有独立 cache 协议，需要适配

FEATURE_116 引入**单一 cache control 抽象层**，让上层 ai-layer 和 coding-layer 不需要知道每家 provider 的 cache 协议细节，由 provider adapter 内部决定如何 lower 到 wire format。

## FEATURE_116: Active Cache Control Foundation — cache_control Markers + 12 Provider Adapters

**Status**: Planned
**Priority**: High
**Category**: Internal / Cost Optimization

### 背景

#### 当前 KodaX cache 状态

[`packages/ai/src/providers/anthropic.ts`](../../packages/ai/src/providers/anthropic.ts) 解析响应时读：

```ts
const cacheCreation = response.usage?.cache_creation_input_tokens ?? 0;
const cacheRead = response.usage?.cache_read_input_tokens ?? 0;
```

但请求构造时**不写** `cache_control`。这意味着：
- 即使是 stable system prompt 也每次重新计费 input tokens
- Tool definitions 大块（KodaX 当前 ~30 工具，~8k tokens）每次重新计费
- Worker role prompt（含 SCOPE COMMITMENT / dispatch RULE A/B/C / 协议描述，~4k tokens）每次重新计费

**Cost 估算（基于 FEATURE_098 per-model context window 数据）**：
- Anthropic Sonnet 4.6 input: $3/M tokens；cache hit: $0.30/M（90% off）
- Worker turn 平均 input ~12k tokens，其中 ~10k 是 stable（system + tool def + role prompt）
- 当前每 Worker turn input cost ≈ $0.036；启用 cache 后 ≈ $0.0066；节省 ~80%

#### Phase 0.7 调研对照

Claude Code 把 cache_control 打在 3 个稳定位置：
1. **System prompt 末尾**——整段 system prompt 作为 cache prefix
2. **Tools array 末尾**——整个 tools 定义作为 cache prefix
3. **Agent frontmatter mcpServers 末尾**——agent definition 作为 cache prefix

**关键观察**：cache_control marker 是 *suffix* 标记——表示"从开头到这里都缓存"，不是包裹某段。这是 Anthropic SDK 的语义。

### 设计

#### 单一抽象：`KodaXCacheBoundary` 标记

`packages/ai/src/types.ts` 引入：

```ts
/**
 * Marks the end of a cacheable prefix in the request. Provider adapters
 * lower this to the wire-level cache_control marker their API expects
 * (Anthropic: cache_control:{type:'ephemeral'}; DeepSeek/Kimi/Zhipu:
 * provider-specific; OpenAI: no-op since prefix caching is automatic).
 *
 * Place at the end of any stable section (system prompt, tools, role prompt).
 */
export interface KodaXCacheBoundary {
  readonly kind: 'cache-boundary';
  readonly hint?: 'system' | 'tools' | 'role-prompt';
}
```

请求层在构造 messages / system / tools 时插入 `KodaXCacheBoundary` 标记，provider adapter 各自决定如何 lower。

#### 3 个标记位置

```
[
  ...stable system prompt blocks...,
  { kind: 'cache-boundary', hint: 'system' },     // ← 标记 1
  ...volatile system prompt blocks（用户级 context）...,
]

tools: [
  ...all tool definitions...,
  { kind: 'cache-boundary', hint: 'tools' },      // ← 标记 2（tools 末尾）
]

role-prompt:
  [...stable role prompt blocks...,
   { kind: 'cache-boundary', hint: 'role-prompt' }, // ← 标记 3
   ...per-turn dynamic context...]
```

#### 12 个 provider adapter 各自 lower

| Provider | Lower 行为 |
|---|---|
| Anthropic | 把 `KodaXCacheBoundary` 翻译成 wire 上 last block 的 `cache_control: { type: 'ephemeral' }` |
| Bedrock (Anthropic) | 同上 |
| Vertex (Anthropic) | 同上 |
| OpenAI | no-op（OpenAI prefix caching 自动） |
| DeepSeek | 走 DeepSeek context caching 协议（`cache_id` mechanism） |
| Kimi | 走 Moonshot context caching API |
| Zhipu | 走 GLM cache 协议 |
| MiniMax | TBD（如 provider 无 cache 协议则 no-op） |
| MiMo | TBD |
| Gemini CLI | Gemini implicit caching（no-op） |
| Codex CLI | proxy 不动 |
| Qwen | DashScope context cache |

每个 adapter 在请求构造时遍历 messages / system / tools，遇 `KodaXCacheBoundary` 时按各家协议 lower。

#### 测量与验证

[`packages/ai/src/cost-tracker.ts`](../../packages/ai/src/cost-tracker.ts) 已经记录 `cacheReadInputTokens` / `cacheCreationInputTokens`。FEATURE_116 新增 `cacheHitRate` 字段（read / (read + creation)）。

```
Acceptance: 启用 cache_control 后，连续 5 个 Worker turn 的 cacheHitRate ≥ 70%
（首 turn 全是 creation；后续 turn 在 stable 部分应全是 read）
```

### 影响范围

**新增**：

- `packages/ai/src/types.ts`：`KodaXCacheBoundary` 类型
- `packages/ai/src/cache-control.ts`：标记插入 helper（~50 行）
- `packages/ai/src/providers/*.ts`：每个 adapter 加 lower 函数（~30 行 × 12 provider = ~360 行）
- `tests/cache-control.test.ts`：unit test 覆盖 12 provider lower 行为
- `tests/cache-hit-rate.eval.ts`：用 mocked provider 验证连续 5 turn cacheHitRate ≥70%
- `docs/test-guides/FEATURE_116_v0.7.37_TEST_GUIDE.md`：人测引导（看 `/cost` 输出 cache 占比）

**修改**：

- `packages/coding/src/agent-runtime/system-prompt-*.ts`：在 stable / volatile 之间插 boundary
- `packages/coding/src/task-engine/_internal/managed-task/role-prompt.ts`：role prompt 末尾插 boundary
- `packages/coding/src/tools/registry.ts`：tools array 末尾插 boundary
- `packages/ai/src/cost-tracker.ts`：新增 `cacheHitRate` 字段

**不改动**：

- 业务逻辑层（不需要知道 cache 存在）
- `packages/coding/src/task-engine/runner-driven.ts`（runner 不感知）
- 任何 v0.7.36 三件套核心路径

### 验收标准

1. **Anthropic 路径 cache 命中**：连续 5 个 Worker turn，第 2 turn 起 cacheHitRate ≥ 70%
2. **OpenAI 路径 no-op**：boundary marker 不出现在 OpenAI wire request 中（因为 OpenAI 不支持），且不影响 prefix caching 自动行为
3. **DeepSeek/Kimi/Zhipu 路径走自家协议**：wire-level inspect 验证各家 cache_id / context_id 正确传递
4. **首 turn 退化**：首 turn 必然全是 creation（无可读），cacheHitRate=0% 不算失败
5. **Volatile 部分不缓存**：volatile system prompt 修改（如用户加 context）不导致整段 cache miss
6. **跨 provider 一致**：同一 Worker turn 切 provider 不破 cache（cache 是 provider 内部的）
7. **`/cost` 命令输出 cacheHitRate**：用户能看到节省效果
8. **无回归**：`npm run test` / `npm run build` 全绿；FEATURE_092 / FEATURE_104 / FEATURE_106 路径不受影响

### 非目标

- **不** 引入 cache invalidation 主动控制（boundary 是 suffix marker，没有"主动 invalidate" 概念）
- **不** 在用户代码中暴露 cache_control 概念（封装在 ai-layer）
- **不** 跨 provider 共享 cache（每家 provider 独立）
- **不** 持久化 cache（5 分钟 TTL 由 provider 决定）
- **不** 优化 child agent 的 cache（child 走独立 session，FEATURE_117 v0.7.38 处理 read-path stripping 是另一个维度）
- **不** 引入 cache-aware routing（FEATURE_102 v0.7.45 才考虑）

### 与其他 Feature 的关系

- **依赖 FEATURE_098（已 ship）**：per-model context window 数据是 cost 估算前提
- **辅助 FEATURE_117（v0.7.38）**：read-path stripping 减少 child invocation 的 input tokens；FEATURE_116 减少 stable 部分的 cache miss——两个独立维度的成本优化
- **辅助 FEATURE_102（v0.7.45）**：FEATURE_102 capability routing 决策需要 cache hit rate 作为成本信号

## FEATURE_141: Transcript Inline Diff Renderer — Edit / Multi-Edit / Write Tool Result Hunk Display

**Status**: Planned
**Priority**: High
**Category**: Enhancement / UX

### 背景

#### 当前 KodaX 状态（核查实证）

`packages/coding/src/tools/edit.ts` / `multi-edit.ts` / `write.ts` 内部使用 `structuredPatch`（`diff` 包）生成结构化 diff 数据，但**`packages/repl/src/` 全目录无任何 diff 渲染组件**：

```bash
# 核查命令（2026-05-05）
$ rg -l 'structuredPatch|hunks|StructuredDiff|DiffLine|formatDiff|renderDiff|DiffSurface' packages/repl/src/
# 仅 1 个匹配：packages/repl/src/ui/json-events.test.ts（测试不算）

$ rg -l 'structuredPatch' packages/coding/src/tools/
# 命中 edit.ts / multi-edit.ts / write.ts（生成端有 diff 数据）
```

**当前用户体验**：LLM 调 `edit` 工具改文件后，用户在 transcript 看到的是诸如：

```
✔ Edit packages/coding/src/foo.ts
  Replaced 1 occurrence
```

完全不知道实际改了哪几行、什么内容。用户必须额外跑 `git diff` 才能看变更。

#### 为什么这是 138（Turn Diff Dialog）的前置

[FEATURE_138 Turn-Level Diff Dialog](../../FEATURE_LIST.md)（claudecode 风格 `/diff` overlay）依赖 transcript 中**已有结构化 diff 数据**——141 把 diff 数据从 tool 内部带到 UI 层后，138 才有数据可显示。先做 141，再根据用户实际反馈决定是否补 138。

#### 业界对照

- **Claude Code**：每次 FileEdit / FileWrite 工具结束在 transcript 渲染 colored hunk（`+` 绿 / `-` 红 / context 灰）+ 行号 + 文件路径
- **opencode**：同上，且文件首次 read 时 lazy-cache，edit 时基于 cache 渲染
- **Cursor / Aider / 其他主流 coding agent**：都做 inline diff

KodaX 是**唯一一个 transcript 不显示 diff 的主流 coding agent**——这是体验断链。

### 设计

#### 数据流

```
edit / multi-edit / write tool
  ├─ 既有：调 structuredPatch(filename, oldText, newText) 生成 hunk
  ├─ 既有：返 string tool result（"Replaced 1 occurrence"）
  └─ 新增：tool result payload 加 structured field：
       {
         text: "Replaced 1 occurrence",
         diff: {
           filename: "packages/coding/src/foo.ts",
           hunks: StructuredPatchHunk[],   // 既有的 diff lib 类型
           summary: { added: 3, removed: 1, files: 1 }
         }
       }
```

REPL 层在 transcript 渲染时检测 tool result 是否带 `diff` 字段，有则用新 `<DiffHunk />` 组件渲染。

#### 渲染规范

```
✔ Edit packages/coding/src/foo.ts  (+3 -1)

  @@ 42,7 +42,9 @@
   function processInput(input: string) {
  -  return input.toLowerCase();
  +  if (!input) return '';
  +  const normalized = input.trim().toLowerCase();
  +  return normalized;
   }
```

**视觉规范**：
- 文件标题行：`✔ <Tool> <path>` + 右对齐 `(+N -N)` 数字摘要
- Hunk 头：`@@ <oldStart>,<oldCount> +<newStart>,<newCount> @@` 灰色
- 增加行：前缀 `+` + 整行绿色背景或绿色前景（取决于主题）
- 删除行：前缀 `-` + 整行红色
- 上下文行：前缀 ` `（空格）+ 默认色
- 多 hunk：hunk 之间空行分隔
- 多文件（`multi_edit`）：每个文件独立标题块

#### 折叠 / 展开（避免大文件刷屏）

- 默认显示前 8 行 + 后 8 行（共 16 行 / hunk）
- 超过则中间显示 `... <N> lines collapsed (press space to expand) ...`
- 用户按 `space` 在该 hunk 上展开（KodaX 当前没有 transcript inline 交互，本 feature **不做交互**——v1 仅折叠显示，不做展开）
- 极端大 diff（>200 行）只显示文件名 + 摘要 + 提示 `[diff too large; run \`git diff\` for full view]`

#### Theme awareness

复用 [FEATURE_007 Theme System Consolidation](../../FEATURE_LIST.md) 之前已有的 theme primitives：
- 绿色 token（add）
- 红色 token（remove）
- 灰色 token（context / hunk header）
- 黑底 / 白底自动适应

如 FEATURE_007 未 ship，先用硬编码 `theme.diff.add` / `theme.diff.remove` 后续替换。

#### 与 multi_edit 协同

`multi_edit` 一次调用改一个文件多个位置：UI 把所有 hunks 渲染在同一文件标题块下，按行号排序。

#### 与 write（新建文件）协同

新建文件 = 全部新增。渲染为单 hunk，无 `-` 行，标题 `+ Created packages/coding/src/foo.ts (+N lines)`。

#### 与 dispatch_child_task 协同

child agent 跑的 edit 也走同一渲染路径（child 的 tool result 也会冒泡到主 transcript）；child 操作的 diff 在主 transcript 中显示，缩进或加 `[child:task_id]` 前缀作为 visual hint。

#### Pre/Post tool 执行的渲染时机

不在 tool 执行**前**做 preview（那是 FEATURE_138 的责任）。141 仅在 tool 完成**后**展示已发生的变更。

### 影响范围

**新增**：

- `packages/repl/src/ui/components/DiffHunk.tsx` — Ink 组件，~120 行
- `packages/repl/src/ui/components/DiffFileBlock.tsx` — 文件标题 + 多 hunk 容器，~60 行
- `packages/coding/src/tools/diff-payload.ts` — 把 `structuredPatch` 包成 `KodaXDiffPayload` 类型的 helper，~40 行
- `tests/diff-renderer.test.tsx` — Ink 组件测试 + 折叠 logic，~150 行
- `docs/test-guides/FEATURE_141_v0.7.37_TEST_GUIDE.md`

**修改**：

- `packages/coding/src/types.ts` — `KodaXToolResult` 接口加可选 `diff?: KodaXDiffPayload` 字段
- `packages/coding/src/tools/edit.ts` / `multi-edit.ts` / `write.ts` — 在返 result 时附 `diff` payload（既有 `structuredPatch` 数据，仅传递不重算）
- `packages/repl/src/ui/InkREPL.tsx` 或对应 transcript 渲染层 — 检测 `result.diff` 字段，渲染 `<DiffFileBlock />` 替代纯文本

**不改动**：

- `structuredPatch` 算法（既有 `diff` lib 不变）
- 任何 tool 业务逻辑
- guardrail / permission / runner / Layer A 协议

### 验收标准

1. **基础渲染**：用户调 LLM 改一个文件 1 处，transcript 显示 colored hunk（绿色 `+` / 红色 `-` / 上下文行），含 `(+N -N)` 摘要
2. **multi_edit 多 hunk**：单 multi_edit 改文件 3 处 → transcript 单文件块下显示 3 个 hunk，按行号排序
3. **write 新文件**：write 创建新文件 → 显示 `+ Created <path> (+N lines)` 单 hunk 全 add
4. **大文件折叠**：单 hunk > 16 行触发折叠（前 8 + 后 8 + 中间提示）；> 200 行触发摘要-only fallback
5. **child agent 路径**：child 调 edit / write 后主 transcript 也显示 hunk，含 `[child:task_id]` hint
6. **theme 自适应**：dark / light theme 下绿红颜色对比度合规
7. **零回归**：edit / multi_edit / write 业务逻辑不变；`npm run test` / `npm run build` 全绿
8. **transcript 性能**：单 turn 100 个 edit 渲染不卡顿（虚拟滚动或 React.memo）

### 非目标

- **不** 做 inline 交互（hover / 折叠展开切换 / 跳转）—— v1 是 read-only 渲染
- **不** 做 turn-level diff overlay（`/diff` 命令）—— FEATURE_138 后续根据数据决定
- **不** 做 git diff 集成（用户跑 `git diff` 自己看；本 feature 仅渲染 KodaX 自己的 edit 操作）
- **不** 做 syntax highlighting（diff 行不带语言着色 —— v1 仅 add/remove/context 三色）
- **不** 做 diff 在 logfile / artifact 持久化（仅 in-session 显示）
- **不** 做 inline edit suggestions（不是 diff 编辑器，是 read-only viewer）
- **不** 改 tool result 在 LLM 端的可见格式（diff payload 只给 UI 用，LLM 端继续看 text 摘要避免 context 浪费）

### 与其他 Feature 的关系

- **铺路 FEATURE_138（暂搁置）**：138 turn-level diff overlay 依赖 141 提供的结构化 diff payload；141 ship 后看用户实际是否需要 turn-level history 才决定是否做 138
- **协同 FEATURE_057（v0.7.30）**：057 Track F cell-level renderer 提供底座；141 用 Ink Box / Text + 颜色 token，不需要 cell-level 自定义
- **协同 FEATURE_007（v0.8.0）**：theme system consolidation 之后 141 切到 theme primitives；之前用硬编码颜色

## v0.7.36 Behavioral Eval Follow-ups（正式 track，非隐式 defer）

**Status**: Planned for v0.7.37
**Priority**: Medium
**Category**: Quality Gate / Eval

### 背景

v0.7.36 ship 了三个 LLM-facing 改动（FEATURE_119 Pattern B、FEATURE_131-B Unicode normalization fallback、FEATURE_143 prompt-overlay 位置迁移），并按 v0.7.36 design doc 要求建立了 ship gate。但实际 ship 的是**结构 eval**（无 API key、无 LLM judge）+ **dataset 回归**：

- [`tests/feature-119-pattern-b-async-dispatch.eval.ts`](../../tests/feature-119-pattern-b-async-dispatch.eval.ts) — 9 个结构断言，验证工具表面 + Worker prompt 包含 Pattern B 锚点
- [`tests/feature-131-unicode-dataset-regression.eval.ts`](../../tests/feature-131-unicode-dataset-regression.eval.ts) — 12 个真实 LLM-needle × file-haystack 对，覆盖 NFKC + smart quotes + em-dash + nbsp 组合场景
- [`tests/prompt-overlay-position-migration.eval.ts`](../../tests/prompt-overlay-position-migration.eval.ts) — 3 个结构断言，验证 promptOverlay 在 4 个 AMA 角色 prompt 中的位置正确

**v0.7.36 design doc 原本要求**的 multi-alias × multi-task LLM-judge 行为 eval 没跑（成本：~$5-15 per feature × 3 features，需要 8 alias provider key），ship 时把它标注为"v0.7.37 follow-up"。本节是把这个隐式 defer 升级为**正式 track**——不再是模糊的"未来某版本"，而是**v0.7.37 内必须完成**的 quality gate。

### Scope

#### A. FEATURE_143 prompt-overlay 位置迁移 — 行为对比 eval

**目标**：验证从 user-prompt 头迁移到 system-prompt section 后，Worker 在 H0/H1/H2 路由决策、SCOPE COMMITMENT 触发、instruction following 三个维度上无退化。

**Eval 规模**：

## FEATURE_147: npm Publishing Pipeline — 多包发布管线 + scope 重命名 + ai→llm 改名

**Status**: Planned
**Priority**: High
**Category**: Internal / Distribution

### 背景

KodaX 自 v0.7.35 起内部已经是 9 包 monorepo 结构（`@kodax/{ai, agent, coding, mcp, repl, repointel-protocol, session-lineage, skills, tracing}`），但**从未真正发布到 npm registry**。所有用户和 CI 都靠 `git clone` + `npm install`（workspace 模式）使用项目。这有三个问题：

1. **品牌名抢注风险**：v0.7.36 期间 `kodax` 这个 unscoped 名字一直空着——任何人都能 `npm publish kodax` 抢走
2. **scope 命名空间被占**：`@kodax` scope（npm org）已经被别人注册，无法直接用
3. **AI 抽象层名字 `@kodax/ai` 与 org `@kodax-ai` 重复尴尬**：发到 npm 后是 `@kodax-ai/ai`，重复"ai"语义

### v0.7.36 期间已经做的占位工作

| 时间 | 动作 | 结果 |
|---|---|---|
| 2026-05-07 | 注册 `@kodax-ai` org（账号 `icetomoyo`） | 锁住 scope ✅ |
| 2026-05-07 | 尝试发 unscoped `kodax@0.0.1` | npm 拒绝（403, 与 koa/thdax 相似），转 scoped |
| 2026-05-07 | 发占位包 `@kodax-ai/cli@0.0.1` | 锁住主入口 ✅ |

占位包内容：3 文件 / 1.9 KB，仅一个友好的 stdout banner 引导用户去 GitHub 安装。本 feature ship 时占位包升级为 `@kodax-ai/cli@0.7.37` 真实主 CLI。

### 为什么 `ai` 子包要改名为 `llm`

当前内部叫 `@kodax/ai`，发布后变 `@kodax-ai/ai`——重复"ai"语义令人困惑（用户看到 `npm install @kodax-ai/ai` 不知道这是干什么的）。把这个包改名为 **`llm`**：

- 准确：包内容是 LLM 抽象层（12 个 provider 适配器 + cost-tracker + retry/backoff + token 计数），不只是"AI"这个泛词
- 内部代码不改：`KodaXBaseProvider` / `KodaXEvents` 等类名照旧，只改包名 + import 路径
- 跟同行一致：`@anthropic-ai/sdk`, `@google/generative-ai` 类似命名都靠"领域词 + 抽象层名"

替代候选（已评估并否决）：
- `provider`：单数，跟内部目录 `packages/ai/src/providers/` 复数不一致
- `providers`：跟内部基类 `KodaXBaseProvider`（单数）不一致
- `ai`（不改）：与 org 名 `@kodax-ai` 直接重复，差

### Scope

#### A. 重命名所有内部 `@kodax/` → `@kodax-ai/`

| 旧名 | 新名 |
|---|---|
| `@kodax/agent` | `@kodax-ai/agent` |
| `@kodax/ai` | `@kodax-ai/llm` ⚠️（顺便改） |
| `@kodax/coding` | `@kodax-ai/coding` |
| `@kodax/mcp` | `@kodax-ai/mcp` |
| `@kodax/repl` | `@kodax-ai/repl` |
| `@kodax/repointel-protocol` | `@kodax-ai/repointel-protocol` |
| `@kodax/session-lineage` | `@kodax-ai/session-lineage` |
| `@kodax/skills` | `@kodax-ai/skills` |
| `@kodax/tracing` | `@kodax-ai/tracing` |
| root `kodax` | `@kodax-ai/cli` |

#### B. 实测改动量（v0.7.36 期间已 grep 实测）

| 改动类型 | 数量 |
|---|---|
| TypeScript `import ... from '@kodax/xxx'` 语句（packages/ + src/） | 733 处（其中 `@kodax/ai` 占 ~430 处） |

#### C. publish-only 字段补全（每个 `packages/*/package.json` 都加）

```json
{
  "files": ["dist", "README.md", "LICENSE"],
  "publishConfig": { "access": "public" }
}
```

`files` 防止默认把整个目录（含 src / 测试 / node_modules 残留）打进 tarball，包体积爆炸。`publishConfig.access: public` 让 scoped 包默认 public（不加的话 npm 按"私有 scope"对待，会要求订阅付费版）。

#### D. 把 workspace 通配 `*` 改为具体版本

monorepo workspace 内 `"@kodax/agent": "*"` 在本地工作正常（npm workspaces 解析到本地目录），但发到 registry 后用户安装拉不到具体版本。本 feature 落地时统一改为 `"^0.7.37"` 或 `"workspace:^"`（视 npm workspaces 支持情况选）。

#### E. 写一键发布脚本 `scripts/release-npm.mjs`

依次发布（依赖顺序）：
```
1.  @kodax-ai/llm           (no internal deps)
2.  @kodax-ai/tracing       (no internal deps)
3.  @kodax-ai/repointel-protocol  (no internal deps)
4.  @kodax-ai/session-lineage     (deps on llm + agent — agent 是 phantom dep, see below)
5.  @kodax-ai/agent         (deps on llm + tracing)
6.  @kodax-ai/mcp           (deps on llm + agent)
7.  @kodax-ai/skills        (零依赖)
8.  @kodax-ai/coding        (deps on agent + llm + mcp + repointel-protocol + session-lineage + skills)
9.  @kodax-ai/repl          (deps on agent + coding + session-lineage + skills)
10. @kodax-ai/cli           (deps on coding + repl + skills)  — root → 替换占位
```

脚本支持：
- `--dry-run`：所有 publish 走 `--dry-run`
- `--only=<pkg>`：只发指定包（用于 patch release）
- 自动跑 `npm run build` 前置
- 失败回滚提示（npm publish 不可撤回，回滚靠 `npm deprecate`）
