## 总览

### 用户场景

KodaX 用户实际工作流中存在以下多 session 协作场景：

1. **全栈开发**：用户开 2-3 个 KodaX session 分别跑 frontend / backend / DB schema 改动
2. **跨 repo 重构**：API 改动同时影响 client repo + server repo
3. **长任务并行**：一个 session 跑 e2e 测试 + 另一个继续开发
4. **多 worktree 并行 sub-task**：在不同 git worktree 上各自开 KodaX session

### 核心问题

如果用户**未做任何隔离**（同一 cwd 多开 session），多个 KodaX session 可能同时改同一个文件，造成：
- Race condition → 后写覆盖先写（**修改丢失**）
- 文件中间状态被另一 session 读到（**partial state**）
- 没有运行时机制保证 LLM 知道兄弟 session 的存在

### claude code Team Mode 调研对照（2026-05-06）

调研 claude code 源码证实它**没有任何冲突解决机制**：

| 检查项 | 真实状态 | 源码证据 |
|---|---|---|
| 多 teammate 默认 cwd | 全部共享 leader 的 cwd | [`spawnMultiAgent.ts:337`](file:///c:/Works/claudecode/src/tools/shared/spawnMultiAgent.ts#L337) `const workingDir = cwd \|\| getCwd()` |
| Worktree 隔离 | ❌ 不自动；`worktreePath` optional | [`backends/types.ts:217`](file:///c:/Works/claudecode/src/utils/swarm/backends/types.ts#L217) |
| File lock / fcntl / flock | ❌ 完全不存在 | grep 全 swarm 目录无 lock 协议 |
| 跨进程 mutation queue | ❌ 不存在 | grep `flock` / `fcntl` 在 swarm 路径零命中 |
| Prompt 引导分区 | ❌ 没有 | [`teammatePromptAddendum.ts`](file:///c:/Works/claudecode/src/utils/swarm/teammatePromptAddendum.ts) 18 行不提冲突 |

**claude code Team Mode 在冲突维度跟"用户自己多开 session"无区别**。它增加的便利（mailbox / permission sync / task 分配）全是低价值（每天省几次切 terminal），且引入 mode 切换认知负担 + 7 条已知限制 + token 消耗 10x。

### KodaX 的差异化路径

不照搬 mode-based + 不解决冲突的 claude code 设计。KodaX 走 **LLM-First + runtime safety net** 路径：

| 维度 | claude code Team Mode | KodaX FEATURE_125 |
|---|---|---|
| 用户认知负担 | mode 概念 + `/team create` + 记 team_id | **0**（自动感知）|
| 冲突解决保证 | 无（LLM 自律）| **runtime safety net**（content hash mismatch detection）|
| 多 session 不开 mode 的体验 | 完全无协调（race condition）| 自动协调（LLM 看见 + safety net）|
| 设计哲学 | 通信网络（mailbox / SendMessage / mode 切换）| LLM 自感知 + runtime 兜底 |
| 与 KodaX 极简 + LLM-First | 不一致（mode 反向 + LLM 不知情）| ✅ 一致 |

### 设计核心判断

之前我（设计者）一度倾向于"runtime hard lock + 用户裁决 dialog 30s 升级"的强 enforcement 设计。但这违反 KodaX `CLAUDE.md` 的核心原则：

> **Leverage LLM intelligence** - Design for LLM comprehension. Use LLM for generation, review, and testing.

正确思路：**LLM 是智能 entity，给它信息让它自决**；runtime 仅做"data race 物理兜底"（content hash mismatch detection）；用户介入是 LLM 累积失败后**自己 escalate**，不是 runtime 强加的 timeout dialog。

### Step 1：State Broadcast 机制

每个 KodaX session 启动时在 `~/.kodax/instances/<pid>/` 注册：

```
~/.kodax/instances/
├── 12345/
│   ├── state.json          # 实时状态，每秒刷新
│   ├── meta.json           # cwd / start time / git remote / branch
│   └── heartbeat           # mtime 用于 stale detection
└── 12389/
    └── ...
```

**`state.json` 内容**（每秒 / 每 tool 边界刷新）：

```json
{
  "version": "1",
  "updated_at": 1714780800123,
  "pid": 12345,
  "cwd": "/Users/me/work/myrepo",
  "git_branch": "main",
  "agent_phase": "running_tool",
  "current_intent": "implementing dark mode toggle in packages/ui",
  "active_files": ["packages/ui/Button.tsx"],
  "recently_modified_files": [
    {"path": "packages/ui/theme.ts", "modified_at": 1714780750}
  ]
}
```

字段语义：
- `agent_phase`: `idle` / `awaiting_llm` / `running_tool`
- `current_intent`: LLM 在做什么的简短描述（worker 自己产生 / runner 从最近 todo 推断）
- `active_files`: 当前**正在 edit/write** 的文件列表（mutation tool 调用的入参）
- `recently_modified_files`: 最近 5 分钟改过的文件 + 时间戳（指引 LLM 知道哪些文件可能 stale）

**Stale instance detection**：
- session 启动时扫 instances/，对每个目录查 heartbeat mtime
- mtime > 30s 未刷新 → 视为 dead → 清理目录
- 进程 normal exit 时主动清理；crash 时由下一个 session 自动清理

### Step 2：注入其他 session 状态到 system prompt

每次 worker 准备发 LLM call 之前，runner 调 `gatherOtherInstancesState()`：

```ts
function gatherOtherInstancesState(myPid: number): OtherSessionInfo[] {
  const dir = path.join(os.homedir(), '.kodax', 'instances');
  if (!fs.existsSync(dir)) return [];

  const result: OtherSessionInfo[] = [];
  for (const pidDir of fs.readdirSync(dir)) {
    const pid = parseInt(pidDir);
    if (pid === myPid) continue;

    const heartbeat = path.join(dir, pidDir, 'heartbeat');
    const stat = fs.statSync(heartbeat).mtime;
    if (Date.now() - stat.getTime() > 30_000) continue;  // stale

    const state = JSON.parse(fs.readFileSync(path.join(dir, pidDir, 'state.json'), 'utf8'));
    result.push(state);
  }
  return result;
}
```

如有 ≥1 个 alive 的其他 session，runner 在 worker system prompt 注入 block：

```
=== Other active KodaX sessions ===

You are not alone — the user has 2 other KodaX sessions running:

- pid 12389 @ /Users/me/work/myrepo (started 5 min ago, on branch main)
  Phase: running_tool
  Intent: "implementing dark mode toggle in packages/ui"
  Currently editing: packages/ui/Button.tsx
  Recently modified: packages/ui/theme.ts (2 min ago)

- pid 12422 @ /Users/me/work/myrepo (started 2 min ago, on branch main)
  Phase: awaiting_llm
  Intent: "refactor session expiry handling"
  Currently editing: packages/api/auth.ts

Coordination guidance:
- If your task overlaps with their active_files, consider:
  · Working on different files first (let them finish)
  · Reading their active file before editing (see their progress in real time)
  · Sending them a message via send_message (when peer-to-peer messaging
    extends across instances — currently scope-limited to within-instance)
- Their recently_modified_files may have just changed — re-read before
  relying on memory of their content
- Use your judgment. You can usually plan around concurrent work without
  conflict. Don't fight them — let them finish what they started.
```

LLM 看到这个 block 后**自己决定**：
- 选别的文件做（智能避让）
- read 对方正在改的文件看进展（智能感知）
- 调整任务顺序（智能调度）
- 通过 send_message 协调（如未来扩展跨 instance peer messaging）

**没有其他 session 时**：block 不注入（system prompt 干净，无开销）。

### Step 3：Tool-time Soft Warning（不阻断）

每次 LLM 调 Edit/MultiEdit/Write 时，runner 在 tool 执行**之前**检查重叠：

```ts
function checkActiveFileOverlap(filePath: string): SoftWarning | null {
  const others = gatherOtherInstancesState(process.pid);
  const conflicting = others.filter(o => o.active_files.includes(filePath));
  if (conflicting.length === 0) return null;

  return {
    kind: 'active-file-overlap',
    file: filePath,
    others: conflicting.map(c => ({
      pid: c.pid,
      intent: c.current_intent,
    })),
  };
}
```

有重叠 → tool result 前置 warning 段（**不阻断 tool 执行**）：

```
[Warning: Another session is editing this file]
- pid 12389 is editing packages/ui/Button.tsx
  Their intent: "implementing dark mode toggle"
Your edit may overwrite or conflict with theirs. Consider re-reading
the file first or working on a different file.

(Edit was applied. Result follows.)
```

LLM 看到 warning + edit 实际结果，自己决定：
- 直接接受（如果改的部分不冲突）
- undo + 改别的
- 继续但注意 follow-up

**关键**：不强制阻断、不弹用户对话框、不强制 wait —— **LLM 自决**。

### Step 4：Content Hash Safety Net（race condition 物理兜底）

唯一的"runtime 强制"机制 —— 防 race condition 修改丢失：

#### 4.1 Read 阶段：记录 hash

LLM 调 Read foo.ts → runner 在内部状态记录：

```ts
class ContentHashCache {
  private cache: Map<string, { hash: string; readAt: number }> = new Map();

  recordRead(filePath: string): void {
    const content = fs.readFileSync(filePath, 'utf8');
    const hash = crypto.createHash('sha256').update(content).digest('hex');
    this.cache.set(filePath, { hash, readAt: Date.now() });
  }
}
```

#### 4.2 Edit 阶段：检查 hash

LLM 调 Edit foo.ts → runner 在 tool 执行**之前**：

```ts
function checkStaleWrite(filePath: string): StaleWriteResult {
  const cached = contentHashCache.get(filePath);
  if (!cached) return { stale: false };  // 没 read 过；不检查（用户可能直接 write 新文件）

  const currentContent = fs.readFileSync(filePath, 'utf8');
  const currentHash = crypto.createHash('sha256').update(currentContent).digest('hex');

  if (currentHash !== cached.hash) {
    return {
      stale: true,
      message: `${filePath} has changed since you last read it (other session may have modified it). Re-read the file before editing.`,
    };
  }
  return { stale: false };
}
```

如果 stale → tool 不执行，返回 error：

```
[Tool Error] foo.ts has changed since you last read it (other session
may have modified it). Re-read the file before editing.
```

LLM 自然 re-read → 看到对方修改 → 决定整合 / 调整 / 放弃。

#### 4.3 边界 case

| Case | 行为 |
|---|---|
| LLM 没 read 直接 Write 新文件 | 不检查 hash（cache miss）—— 正常 write |
| LLM read 后立即 edit（无并发）| hash 一致 → 正常 apply |
| 其他 session edit 后我 edit | hash 不一致 → block + LLM re-read |
| LLM read → 我自己 edit → 再 edit | hash 检查（自己改后我自己更新 cache）|
| 文件被 user 用编辑器手动改 | hash 不一致 → block（这是好事，LLM 不该覆盖用户编辑）|

### Step 5：用户裁决（仅在 LLM 自己 escalate 时）

**取消所有 runtime 自动弹用户对话框**。LLM 多次 race condition 后自己处理：

```
LLM: Edit foo.ts → [Tool Error: file changed]
LLM: Read foo.ts → 看到对方修改
LLM: Edit foo.ts → [Tool Error: file changed again]
LLM: Read foo.ts → 看到对方修改
LLM: Edit foo.ts → [Tool Error: file changed again]
LLM 反复 3 次失败 → 自然向用户报告：
  "I tried 3 times to edit foo.ts but another session keeps modifying
   it. What would you like — wait, retry later, or skip?"
```

用户裁决是 LLM-driven escalation，不是 runtime-driven timeout。这是 KodaX `LLM-First Design` 的体现 —— LLM 知道何时该问用户，比 runtime 30s timer 更聪明。

### Step 6：与 FEATURE_131 单进程 mutation queue 的协同

| 层 | 作用范围 | 实现 |
|---|---|---|
| FEATURE_131（v0.7.36 同期）| **单进程内**同文件 race | Promise chain / Map mutex |
| FEATURE_125（本 feature） | **跨进程**同文件 race | content hash safety net |

两层正交叠加：
- 单进程内 child agent 并行改同文件 → FEATURE_131 串行化
- 跨进程多 session 改同文件 → FEATURE_125 hash 检查 + LLM 自决

### Step 7：与 worktree 的协同

- 用户用 git worktree 物理隔离（FEATURE_053/068）→ 不同 cwd → 不同绝对路径 → state.json 中 active_files 路径不重叠 → FEATURE_125 自然不触发 warning / safety net
- 用户**不**用 worktree 同 cwd 多开 → FEATURE_125 全功能生效

**两种使用方式都被 KodaX 支持**，用户自由选择。

### 验收标准

1. **单 session 不退化**：`~/.kodax/instances/` 仅 1 个 alive instance 时，system prompt **不**注入 other-instances block；overhead ≤ 1ms / tool call
2. **多 session 不同文件**：active_files 不重叠 → 不互相阻塞，无 warning，正常并行
3. **多 session 同文件 LLM 看见**：另一 session 在改 foo.ts，本 session worker LLM 启动时 system prompt 含其状态；LLM **自决**（FEATURE_104 prompt eval 验证 ≥80% case 选择避让 / 协作 / re-read）
4. **Tool-time soft warning**：LLM 选择 edit 已被另一 session 标 active 的文件，tool result 前置 warning；edit **仍然被 apply**（不阻断）
5. **Content hash safety net**：LLM read foo.ts → 其他 session edit foo.ts → LLM edit foo.ts → tool result error "file changed; re-read"；LLM re-read 后能正常 edit
6. **Stale instance 自动清理**：kill 一个 KodaX session（SIGKILL），其他 session 在 heartbeat > 30s 时自动清理目录
7. **Crash 恢复**：进程被强杀 → 下一个 session 启动时清理 stale instances/
8. **Cross-platform**：Windows / Linux / macOS 都跑通（heartbeat 用 mtime touch，跨平台一致）
9. **跟 FEATURE_131 协同**：单进程内 mutation queue + 跨进程 content hash 两层正交，无 deadlock
10. **跟 worktree 协同**：用户用 worktree 隔离 → 不同绝对路径 → 不触发本 feature warning（因 active_files 路径不重叠）
11. **跨 family 验证**：4 family LLM（GLM/Kimi/Claude/GPT）看到 other-instances block 后避让 / re-read 行为 max-min spread ≤ 15pp
12. **Prompt eval 触发**：本 feature 触及 worker system prompt（其他 instance block 注入），按 FEATURE_104 必须新增 eval `tests/multi-instance/awareness-prompt.eval.ts`

### 非目标

- **不** 引入 file lock / fcntl / flock 协议（runtime hard enforcement 反 LLM-First）
- **不** 引入 mode 概念 / `/team create` / `/team join` slash command（自动感知，零认知负担）
- **不** 引入 cross-instance peer SendMessage（FEATURE_123 peer SendMessage scope 在单 instance 内；跨 instance 通信留作未来 feature 看用户实际需求）
- **不** 引入跨 instance permission sync（用户在每个 session 各自决策即可，复用 FEATURE_092）
- **不** 引入跨 instance envelope spillover 文件共享（FEATURE_121 v0.7.40 rescope 后 envelope spillover 文件在每个 instance 的 `getAgentConfigPath('tool-results')/` 本地目录；跨 instance 共享非本 feature scope。**Note**：原稿写 "scratchpad scope 在单 instance 内"，FEATURE_121 已 rescope 不再有 scratchpad，但"本 feature 不做跨 instance 文件共享"这条约束仍成立）

#### 场景 C：真 race condition

```

  read at T0 → hash A
  edit at T1 → 期间 session 2 抢着改了
```

**结果**：物理 race 被 hash safety net 兜住，没有修改丢失。

> 中文标题：`Worker emit_handoff 子任务在途守卫`

### 背景与触发

**production trace（2026-05-15，zhipu-coding/glm-5.1 Worker）**：

## FEATURE_167 — Evaluator terminal-verdict 兜底（**design phase**）

**Status**: Design + eval phase（设计 + Layer 2 probe 落地，实现等 probe 数据后启动）

**Priority**: **High**（functional bug — `deriveFinalStatus` 在 verdict 为 undefined 时 falls back to `signal:'COMPLETE'`，**错误地把失败的 audit 报告成成功**；不是 lineage-only）

**Category**: Core / AMA runtime

### 背景

同 FEATURE_166 一起被 production session [`20260515_185354`](file:///c:/Users/iceto/.kodax/sessions/20260515_185354.jsonl) 暴露 —— Evaluator 在 Worker 干净 handoff 之后，**没有调 `emit_verdict` tool**，只发了一段 text（"Review 已全部完成。核心发现：..."），run 干净退出但 `recorder.verdict` 永远 `undefined`。

**Smoking gun（planner-review 2026-05-15 揭出）**：[runner-driven.ts:4146](../../packages/coding/src/task-engine/runner-driven.ts#L4146) `deriveFinalStatus` 在 `recorder.verdict` 为 undefined 时 hardcode `return { signal: 'COMPLETE' }`。这意味着 production run：

- Evaluator 没调 `emit_verdict` → recorder.verdict undefined
- → `KodaXResult.signal === 'COMPLETE'` （**错误的成功信号**）
- → 调用方 / lineage / SDK consumer 把 "audit failed silently" 误读为 "audit passed"

FEATURE_166 修了 UI label-lag（用户看到对的 `[Evaluator]`），但 functional 层面的影响：
- 调用方根据 `signal === 'COMPLETE'` 做 downstream 决策（merge / accept / 标 done）—— 实际 audit 没发生
- `buildManagedProtocolPayload` 默默 omit `verdict` field，SDK consumer 拿 `payload.verdict === undefined`
- `scorecard` ([runner-driven.ts:4493-4496](../../packages/coding/src/task-engine/runner-driven.ts#L4493)) 也默默 skip verdict directive
- 用户能看到 review 文本（fall back to last assistant text），但**机器系统全链路读到 false positive**

### 失败模式分类（基于 code reading）

| 模式 | 触发条件 | 当前行为 |
|---|---|---|
| **(F1) zhipu intent-vs-action floor** | `zhipu/glm-5.1` 在 Evaluator role 下输出 "Review complete" 文本但 `toolCalls: []` | run 干净退出，verdict 为空 |
| **(F2) 任意 model 用 fenced-block 形式** | LLM 输出 ` ```kodax-task-verdict ... ``` ` 但没调 `emit_verdict` tool | Prompt line 895 暗示这是 fallback，但 [parseManagedTaskVerdictDirectiveFromJson](../../packages/coding/src/task-engine/_internal/managed-task/parse-helpers.ts#L92) 在 V2 runner-driven 路径**完全没接线**（dead code）→ 同样空 verdict |
| **(F3) Evaluator 提前 `emit_handoff`** | Evaluator role 不应该有 emit_handoff，但 prompt 上没有 hard gate；如果 model 误调 | tool 不存在 → tool_result error，但 Evaluator 可能不 recover |
| **(F4) Evaluator emit_verdict 但 payload 缺 status** | `emit_verdict({})` schema 拒绝 → tool_result error | model 可能 retry 或放弃 |

主战场是 (F1) + (F2)。(F3)(F4) 罕见。

### 设计方案：三层防御（B0 → B1 → B2）

按成本/侵入度排序，逐层兜底：

**B0 — Fenced-block fallback parser 重新接线（cheap, recovery-first）**

Evaluator turn 退出时（runner.ts:558 toolCalls=0 路径）扫描最后一条 assistant 文本，查找 ` ```kodax-task-verdict``` ` 围栏；命中则用 [parseManagedTaskVerdictDirectiveFromJson](../../packages/coding/src/task-engine/_internal/managed-task/parse-helpers.ts#L92) 解析，合成 `metadata: { handoffTarget, isTerminal, payload: { verdict: {...} } }` 写入 `recorder.verdict`。

**实现位置**：放在 outer wrapper `runWithIdleYield` 的 `runOnce` 完成后、`computeSnapshot` 之前。如果 last agent 是 Evaluator + last turn 0 tool calls + recorder.verdict 仍空 → 尝试 parse。

**Blast radius**：低。死代码激活，prompt 已经文档了这个 fallback。

**B1 — Runtime gate 重试（mid retries before giving up）**

如果 B0 parse 失败（模型连围栏都没写），fire `detectMissingTerminalVerdict` predicate，把一条 user-role 消息注入 transcript。

**Pinned constant — `EVALUATOR_VERDICT_RETRY_PROMPT`**（probe + impl 用同一个字符串，**改字必须重跑 probe**）：

```typescript
export const EVALUATOR_VERDICT_RETRY_PROMPT = [
  'Your previous response ended without calling the `emit_verdict` tool ' +
    'and without a valid ```kodax-task-verdict``` fenced block. The run ' +
    'cannot terminate without a structured verdict.',
  '',
  'Call `emit_verdict` now with this shape:',
  '  emit_verdict({',
  '    status: "accept" | "revise" | "blocked",',
  '    reason: "<one-line reason>",',
  '    user_answer: "<final user-facing answer, multi-line ok>"',
  '  })',
  '',
  'Do NOT respond with text only. Do NOT repeat the review summary in ' +
    'prose — put the consolidated review in `user_answer` and call the tool.',
].join('\n');
```

**Length rationale**: 1 paragraph framing + 1 schema block + 1 anti-pattern line. Longer than "call the tool now" because Evaluator's text-only failure suggests the model lost track of the tool surface — restating schema helps. Shorter than re-rendering the full Verdict payload guidance from role-prompt.ts:884-896 because we don't want to crowd context.

**Imperative tone** ("Do NOT respond with text only"): per memory [`feedback_prompt_strengthening_cross_case_regression`](../../../../Users/iceto/.claude/projects/c--Works-GitWorks-KodaX-author-KodaX/memory/feedback_prompt_strengthening_cross_case_regression.md), prohibition style risks cross-case generalization. **But**: this prompt fires ONLY mid-retry — Evaluator never sees it on first turn, no risk of contaminating normal `emit_verdict` triggering. The cross-case regression risk is bounded to the retry-only path.

Resume Evaluator turn after injection. **Cap at 2 retries**（避免 zhipu intent floor 无限循环 + 不烧爆 budget）。

**实现位置**：扩展 [idle-yield.ts:detectIdleYield](../../packages/agent/src/orchestration/idle-yield.ts) 或新增 sibling predicate `detectMissingTerminalVerdict`。Outer wrapper 分支：
- pending children/banners → 现有 idle-yield prompt
- handoff emitted + no verdict + no children → NEW verdict-missing prompt

**Blast radius**：中。改 outer-loop snapshot 逻辑。需要在 unit test 上 pin：
1. 正常 emit_verdict 路径不退化（snapshot 走 `hasEmittedTerminalVerdict=true` 不进 retry）
2. Retry cap 不会死循环
3. 不影响 FEATURE_155 idle-yield（pending children 优先）

**B2 — Synthesized fallback verdict（last resort, never silently accept）**

如果 B1 retry 也用完了（model 仍然不调），合成一个 **保守** verdict：
```typescript
recorder.verdict = {
  source: 'fallback-synthesized',
  status: 'blocked',  // 故意不 accept — 缺 verdict 就是 evidence 不足
  reason: 'Evaluator failed to emit a terminal verdict after N retries. '
        + 'Run produced output but no structured audit decision.',
  userFacingText: <last assistant text from Evaluator>,
};
```

**为什么 status='blocked' 不是 'accept'**：accept 是 "audit passed" 的强保证，不能在 evaluator 失败时默认给。blocked 表达 "我没法确定是否成功"，强迫调用方介入。和 FEATURE_165 gate 返回 `isError:true` 的哲学一致——错的状态不掩盖。

**Ordering requirement（architect-flagged 2026-05-15）**：B2 synth 必须按下面的顺序执行：

1. Write `recorder.verdict = {source:'fallback-synthesized', ...}` —— **before** 任何 checkpoint persistence。Resume-from-checkpoint 必须看到 terminal verdict，否则恢复时再跑一遍 B1 retry 直接烧 budget。
2. Fire dedicated event `events.onEvaluatorFallbackSynthesized?.({reason, userFacingText, retryCount})` 或附在现有 logger 上——**before** `formatDeterministicEvaluatorResult` 构造 `KodaXResult`。运维 telemetry 需要在 result 落地前就能 trace。
3. Run terminates normally with `signal:'BLOCKED'`（由 `formatDeterministicEvaluatorResult` 从 verdict.status 派生）

**Retry counter state**：cap 计数器是 outer-loop snapshot 的 explicit field（同 `iterationCount` 一起），**不**是 `runOnce` 闭包内的 mutable variable。理由：未来 outer loop 重构 / 多 runOnce 重入时，闭包计数器会漏算或重复计数。Field 名建议：`evaluatorVerdictRetryCount: number`。

### Layer 2 probe 设计（per EVAL_GUIDELINES）

**Question**: "Evaluator 在不同 alias 上，首次 emit_verdict 命中率是多少？B1 retry prompt 能否把没命中的 case recover 到合理水平？"

**Cases**（3 个）：
1. `evaluator_first_turn_clean_handoff` — Worker 干净 handoff 后 Evaluator 首条 response 是否含 emit_verdict tool call？
2. `evaluator_retry_after_missing` — 模拟 turn 1 没调 verdict + 注入 B1 retry prompt 作为下条 user message，turn 2 是否调 emit_verdict？
3. `evaluator_text_only_with_fenced_block` —（覆盖 B0 路径）model 输出 fenced verdict 块但没调 tool 的概率多大？

**Variants**：单 variant `v_current` （没改 prompt，纯测量）。

**Panel**：5 alias `zhipu/glm51, kimi, ds/v4pro, ds/v4flash, mmx/m27`，5 run/cell = 3 case × 5 × 5 = **75 calls** ~$2-4。

**Sample size escalation**：5 run/cell 对 65-85% band 的统计辨识度偏弱（architect-flagged 2026-05-15）。如果首轮 probe 在 C1 上任一 alias 落进 65-85% 区间（border-line），**自动加跑 5 run/cell 把样本提到 10 run**，单 alias 加 30 calls (~$1)。最多到 10，不再继续——floor model 行为已经 settle，更多 sample 不增信息量。

**Mechanical assertions**：
- C1 PASS: `toolCalls.some(c => c.name === 'emit_verdict')`
- C2 PASS: 同 C1 但 in turn 2（注入 retry prompt 后）
- C3 PASS: `output.text` 含 ` ```kodax-task-verdict ``` ` 围栏 + body 可被 `parseManagedTaskVerdictDirectiveFromJson` 解析

**注意 C3 双重职责**：probe 测量的是 **emission frequency**（"实际有多少 LLM 自然会写围栏"），不是 parser correctness。Parser 正确性走 **B0 单元测试**（Acceptance §4 B0 bullet），$0 成本，覆盖 snake_case/camelCase variants + 各种 status enum + followup 形式。Probe 数据告诉我们 B0 是不是真实价值（vs again-dead-code）。

**Pre-registered SHIP matrix（B0 / B1 / B2 独立决策，per planner-review 2026-05-15）**：

每一层独立 ship/skip，不耦合彼此。三个 layer 的决策按三个独立 condition：

| Layer | SHIP condition | SKIP condition | 理由 |
|---|---|---|---|

**Eval-first**：实现 B0/B1/B2 之前必须先跑 probe，按 SHIP matrix 决定哪几层落地。Probe + LLM-judge audit 是这个 FEATURE 的 Layer 2 gating step。

### 背景与触发

**用户实战观察（2026-05-15）**：用户问 "计划列表列出之后，就不能修改了？比如做着做着发现计划有缺失需要增加或者修改"。

逐文件核对当前 v0.7.40 状态（[packages/coding/src/tools/todo-update.ts](../../packages/coding/src/tools/todo-update.ts)）后确认 KodaX **没有 per-task insert/delete/content-edit 能力**：

| op | input | 行为 |
|---|---|---|
| `op:'init'` | `{items:[{id, content, activeForm?, evaluator?}]}` | **整盘 replace** todo store，wipe 全部进行中 / 已完成 / pending 状态 |
| `op:'update'` | `{id, status, note?, activeForm?}` | **只能改 status**，无法 patch content / evaluator / metadata；无法 insert 新 item；无法 delete |

**矛盾点**：Worker 角色 prompt（[worker-role-prompt.ts:53-67](../../packages/coding/src/agents/worker-role-prompt.ts#L53)）显式承诺：

> "Replan iteratively: insert / cancel / adjust items via `todo_update` as the picture firms up. Do NOT reset the entire list mid-task..."

但 LLM 的唯一可用 insertion 路径 IS `op:'init'`（full replace），prompt 句中的 "Do NOT reset" 反过来禁掉了它能用的唯一手段——任何 mid-task 计划变更要么静默不发生（LLM 看到 `op:'update'` 不支持内容编辑就放弃），要么以 `op:'init'` 形式 wipe 用户可见进度条。

**触发为 FEATURE 不是 hotfix 的理由**：触及 prompt + tool schema + store API + extension contract 四面，非 1-2 行修法；需要走 FEATURE_104 prompt eval 规则；与 claudecode V2 的 alignment 决策本身是 standalone 设计权衡。

### 设计（Option C2 — per-task CRUD + 保留 op:'init'）

#### LLM-facing 工具表面（迁移后）

| Tool | Input | Output | 说明 |
|---|---|---|---|
| `todo_create` (新) | `{content, activeForm?, evaluator?, metadata?}` | `{ok:true, id}` 或 `{ok:false, reason}` | 单 item insert，store 自动生成 monotonic id |
| `todo_update` (扩展) | `{id, content?, activeForm?, status?, evaluator?, note?, metadata?}` | `{ok:true, changedFields:[...]}` 或 `{ok:false, reason}` | **strict-superset**：原 `{id, status}` 调用形式完全 unchanged |
| `todo_update` (保留) | `{op:'init', items:[{id, content, activeForm?, evaluator?}]}` | `{ok:true, count}` | fan-out plan-first batch 初始化（FEATURE_151 v0.7.38 contract 保留） |
| `todo_list` (不变) | `{}` | `{ok:true, count, items}` | — |

**关键决策**：
- **Delete 通过 `status:'deleted'`**（mirror claudecode TaskUpdate 特殊路径），不开新 tool
- **op:'init' 保留**（用户 2026-05-15 明确："keep `op:'init'` for fan-out plan-first，FEATURE_151 contract 还有约束力"）
- **Backwards-compat 严格**：现有 `op:'update'` callers（status-only）字节级不变；prompt 里残留 "use `todo_update({id, status})`" 写法仍工作

#### Store API 扩展（[todo-store.ts](../../packages/coding/src/task-engine/todo-store.ts)）

```ts
interface TodoStore {
  // ... existing init / updateStatus / replace / autoCompleteOnAccept / markInProgressFailed / resetFailed / reset

  /** Create new item with auto-generated id. Returns new id. */
  add(seed: {content: string; activeForm?: string; evaluator?: TodoEvaluatorHint; metadata?: Record<string, unknown>}): string;

  /** Patch existing item. Returns true iff id existed. */
  patch(id: string, partial: {content?: string; activeForm?: string; evaluator?: TodoEvaluatorHint; note?: string; metadata?: Record<string, unknown>; status?: TodoStatus}): boolean;

  /** Delete item. Returns true iff existed. */
  remove(id: string): boolean;
}
```

`updateStatus` 改为 `patch({status, note, activeForm})` 的薄包装（原 callsite 不动）。

**Id 生成契约**：`todo_${counter+1}`，counter 在 `init(seeds)` 时初始化为 seeds 中 numeric suffix 的最大值（**`todo_3`/`todo_5` 这种间断 ID 也能正确续上**）。
- **非数字 seed id 边界**：若 seeds 中 id 完全不含 `^todo_(\d+)$` 形式（极端情况，e.g. 早期定制 caller 传 `'step-a' / 'step-b'`），counter 初始化为 0，新 add 出来 `todo_1`。**禁止抛错**——store 必须对任意非空 seed 列表保持可用。
- **不复用 deleted id**：counter 是 monotonic，单调递增不回溯，避免 transcript 历史引用 `todo_3` 时指向新 item。

#### Extension events / hooks 增量（[extensions/types.ts:209-248](../../packages/coding/src/extensions/types.ts#L209)）

```ts
// Events（broadcast，非 blocking）
type ExtensionEventMap = {
  // ... existing 16 events
  'todo:created':   { id: string; item: TodoItem };
  'todo:updated':   { id: string; before: TodoItem; after: TodoItem; changedFields: ReadonlyArray<keyof TodoItem> };
  'todo:deleted':   { id: string; item: TodoItem };
};

// Hooks（blocking）—— 返回 string = block reason；返回 false = block 无 reason；返回 void = 放行
// **必须**含 `| false` 来 mirror 已有的 `tool:before` 返回类型，否则不一致
type ExtensionHookMap = {
  // ... existing tool:before / ...
  'todo:before-create':   (ctx: {seed: TodoInit}) => Promise<void | string | false> | void | string | false;
  'todo:before-complete': (ctx: {id: string; item: TodoItem}) => Promise<void | string | false> | void | string | false;
};
```

**Emit 站点**：
- `'todo:before-create'`：`todo_create` tool 入口；返回 string/false 时工具返回 `{ok:false, reason}`，**不**调 `store.add()`
- `'todo:created'`：`store.add()` 成功后立即 emit
- `'todo:before-complete'`：`todo_update` 收到 `status:'completed'` 时，在 `store.patch()` 前 emit；返回 string/false 时返回 `{ok:false, reason}`，status **不**翻
- `'todo:updated'`：`store.patch()` 实际产生 diff 时 emit（changedFields 非空）
- `'todo:deleted'`：`store.remove()` 成功后 emit

**KodaX 与 claudecode 的返回 shape 差异（明确写入设计）**：
- claudecode `executeTaskCompletedHooks` 命中 blockingError 时**直接 throw**，让上层 try/catch 把工具 result 转 error
- KodaX 已统一 tool result envelope（`{ok:true, ...} \| {ok:false, reason}`），hook 命中 block 时**不 throw**，直接构造 `{ok:false, reason: <hook-returned-string \| 'blocked-by-hook'>}` 返回。这是 KodaX 已有的 `tool:before` 模式延续，不引入新风格

**planFirstContract 改写草案**（line 60 周边）：

```
- The plan is live and mutable per item:
    * Insert a new step:  `todo_create({content, activeForm?})`
    * Modify a step (content / status / activeForm / etc.):  `todo_update({id, content?, status?, activeForm?, ...})`
    * Remove an obsolete step:  `todo_update({id, status:"deleted"})`
- Full-list reset via `todo_update({op:"init", items:[...]})` is reserved for batch initial seeding (e.g. fan-out plan-first). Don't use it for incremental changes — that wipes user-visible progress and forces a full re-render.
- Mark exactly ONE item `in_progress` at a time. Mark `completed` immediately after finishing a step — don't batch.
```

## FEATURE_171 — `runner-driven.ts` Modular Split（**design phase**）

**Status**: Planned — **必须先于 FEATURE_125 / FEATURE_170 落地**

**Category**: Internal / Refactor

### 背景与触发

`packages/coding/src/task-engine/runner-driven.ts` 当前已 **6,406 行**（v0.7.40 release 时 reviewer 提示是 4,930 行，半个 release cycle 又涨了 1,400+；FEATURE_165/166/167 各加了 100-300 行 hot-fix code）。单文件已经触及四个具体痛点：
