# v0.7.14 Feature Designs

> 中文标题：`v0.7.14 Feature 设计`
>
> Version: `v0.7.14`
>
> Status: InProgress
>
> Theme: AAMP async transport surface

---

## 总览

`v0.7.14` 的目标是把 KodaX 当前已经落地的 AAMP 方向收束成一个明确的“下一版本发布面”。

它不是新的 agent engine，也不是新的 provider 类型，而是给现有 runtime 增加一个正式的异步 mailbox transport，使外部 workflow / mailbox network 可以把 KodaX 作为一个可寻址的异步执行节点使用。

---

## FEATURE_046: AAMP SDK Transport Surface

**Status**: InProgress
**Priority**: High
**Category**: New

### Overview

`FEATURE_046` 为 KodaX 增加一个基于 `AAMP SDK` 的正式异步传输面，使外部 agent / workflow / mailbox network 可以把 KodaX 作为一个可寻址的异步执行节点来使用。

这不是一个新的执行引擎，也不是把邮件协议硬塞进 `@kodax/coding` 核心，而是：

- 在现有 `ACP server` 旁边新增一个 `AAMP` 入口面
- 复用 `runKodaX(...)`、session storage 和当前 runtime 语义
- 让 KodaX 能处理 `task.dispatch -> task.ack -> task.result`
- 为后续 `task.help_needed`、附件、structured result 留出清晰扩展位

### Why now

KodaX 当前已经具备：

- 稳定的本地执行入口 `runKodaX(...)`
- 持久化 session 与 lineage
- 一个对外协议适配先例 `ACP server`

缺少的是“异步外部任务网络”的正式接入面。

`FEATURE_046` 的价值在于：

- 让 KodaX 不只服务本地 CLI / ACP client，也能作为外部平台里的异步工作节点
- 为未来的多-surface 交付提供一个真实的 transport case
- 用最小侵入方式验证 mailbox-based agent interop，而不打乱现有 AMA / SA / harness 架构

### Product philosophy

#### 1. AAMP 只是 transport，不是新的 agent core

执行、工具、routing、session compact、managed task 都继续留在现有 KodaX runtime 内。

#### 2. 先做最小闭环，再做 richer protocol

第一阶段只要求：

- 接收入站任务
- 自动 ACK
- 执行任务
- 返回结果

不在第一阶段强行引入附件编排、复杂恢复图或多轮 help negotiation。

#### 3. 跟现有 ACP surface 保持同层级心智模型

`ACP` 面向交互式 client；`AAMP` 面向异步 mailbox network。
两者共享 runtime，不共享协议对象。

#### 4. 会话连续性优先于协议花样

同一 AAMP task 必须能稳定映射到同一个本地 session，不能每轮都开新会话。

### Scope

- 新增 `AAMP transport` 抽象端口
- 新增 `AAMP task store`，维护 `taskId <-> sessionId`
- 新增 `AAMP runtime bridge`，把 dispatch 映射到 `runKodaX(...)`
- 新增 `AAMP server` 入口，承载最小协议闭环
- 导出这些能力，供 CLI 和未来 SDK adapter 使用

### Non-goals

- 不引入新的 task-engine execution mode
- 不把 AAMP 做成 provider
- 不把 AAMP 主流程塞进 extension runtime
- 第一阶段不实现完整 `task.help_needed`
- 第一阶段不做附件收发和 structured result schema enforcement

### Primary user stories

1. 作为外部 workflow/platform，我可以把一个任务异步 dispatch 给 KodaX 并收到 ACK。
2. 作为外部 workflow/platform，我可以在任务完成后收到 KodaX 的结果回执。
3. 作为 KodaX 运行时，我能保证同一 task 的状态和 session 绑定是可恢复、可观察的。

### Architecture shape

建议的最小结构：

- `src/aamp_types.ts`
- `src/aamp_store.ts`
- `src/aamp_runtime.ts`
- `src/aamp_server.ts`

边界原则：

- `AAMP SDK` 只出现在 transport adapter 层
- `runKodaX(...)` 继续作为唯一执行入口
- session persistence 继续复用现有 `KodaXSessionStorage`

### State model

第一阶段显式维护这些状态：

1. `received`
2. `acknowledged`
3. `running`
4. `completed`
5. `failed`

后续预留：

1. `help_needed`

### Minimal protocol contract

#### Inbound

- `task.dispatch`
- `taskId`
- sender email
- body text
- optional dispatch context

#### Outbound

- `task.ack`
- `task.result(status=completed|failed)`

### Persistence contract

最小持久化字段：

- `aampTaskId`
- `sessionId`
- `status`
- `senderEmail`
- `dispatchContext`
- `inboundMessageId`
- `resultSummary`
- `createdAt`
- `updatedAt`

### Risks and constraints

#### 1. 不能污染现有 core layering

`@kodax/agent` 和 `@kodax/coding` 仍然保持协议无关。

#### 2. 不能依赖阻塞式人工交互

`AAMP` 是异步 transport，后续 `help_needed` 必须走可恢复邮件语义，而不是复用本地 REPL 阻塞输入模型。

#### 3. 幂等必须先于 richer features

同一 `taskId` 重复到达时，不能重复创建 session 或重复执行已完成任务。

### Acceptance criteria

- [x] 代码库中存在最小可用的 `AAMP` server/runtime/store/types 主干实现
- [x] 同一 `taskId` 首次 dispatch 时会创建 record 并发送 ACK
- [x] 执行完成后会发送 result，并将状态持久化为 `completed` 或 `failed`
- [x] 重复收到已完成 task 的 dispatch 时，不会重复执行
- [x] 已补齐 store 和 server 主流程的最小单测覆盖
- [ ] 发布前默认配置、运维日志与 operator guide 再做一次收口
- [ ] 在 `v0.7.14` 发布窗口完成最终 release note 和 smoke check

### Release target

`FEATURE_046` 当前作为 `v0.7.14` 的核心发布能力维护。

### Follow-up after v0.7.14

后续可继续演进：

- `task.help_needed`
- structured result
- attachment relay
- sender policy / dispatch context policy

## FEATURE_047: Demo Full-Auto Permission Mode

**Status**: Planned
**Priority**: High
**Category**: Enhancement

### Overview

`FEATURE_047` 为演示场景增加一个显式的 demo 权限模式，使 KodaX 在受控演示环境里可以跳过当前 `auto-in-project` 的项目边界确认、受保护路径确认和大部分交互式权限拦截，直接执行用户下发的全部指令。

这个能力的目标不是替代现有安全模型，而是给 demo / sandbox / disposable workspace 提供一个“明确知道自己在做什么”的全自动开关，避免演示过程中频繁卡在权限确认上。

### Why now

`FEATURE_046` 已经把 `AAMP` 作为一个异步 transport 面引入系统。对外演示时，如果一个通过 `AAMP` 或 ACP 驱动的会话仍然会频繁命中权限确认，就会直接打断 transport 闭环展示。

因此需要一个与 `AAMP` 同发布窗口的演示模式能力，用来证明：

- KodaX 可以作为异步节点连续处理端到端任务
- 演示环境下不会因为本地确认框而阻塞
- 安全放宽是显式配置而不是隐式失效

### Product philosophy

#### 1. 这是 demo override，不是默认权限模式升级

现有 `plan` / `accept-edits` / `auto-in-project` 仍然是默认推荐路径。

#### 2. 必须显式命名为高风险能力

避免把它包装成普通的“更方便 auto mode”；需要在名称、帮助文案、状态栏和日志里都明确体现它是 demo-only / high-risk。

#### 3. 放宽权限不等于移除可观测性

即使在 demo 模式下，也要保留执行日志、模式切换记录和 session 级可见提示。

### Scope

- 新增一个演示专用权限模式，例如 `full-auto-demo`
- REPL、ACP server、CLI 参数解析统一识别该模式
- 该模式下默认跳过：
  - `bash` 确认
  - 项目外写入确认
  - 受保护路径确认
  - demo 工作区内的临时 helper script 拦截
- UI 和日志中明确展示当前处于高风险 demo 模式
- 文档中补充适用范围、风险和退出方式

### Non-goals

- 不把 demo 模式作为新的默认值
- 不修改普通模式下的安全边界
- 不把该模式伪装成生产可用安全方案
- 不承诺跨任意主机环境都完全无风险

### Primary user stories

1. 作为演示者，我可以在一次 live demo 中让 agent 连续执行完整命令链，而不被权限确认打断。
2. 作为集成方，我可以在受控的 AAMP demo 环境中展示异步任务从 dispatch 到 result 的完整自动闭环。
3. 作为维护者，我可以明确区分“正常权限模型”与“演示特权模式”，避免二者混淆。

### Acceptance criteria

- [ ] 新增第四种 demo 专用权限模式，并可被 CLI / REPL / ACP 统一识别
- [ ] 该模式下，项目内外文件修改、`bash` 执行、受保护路径操作默认不再弹确认
- [ ] demo 模式有显式高风险提示，用户不会把它误认为默认安全模式
- [ ] 日志与状态展示中可以追溯 session 是否运行在 demo 模式
- [ ] 文档明确注明该模式只用于演示、临时环境或一次性工作区

### Release target

`FEATURE_047` 与 `FEATURE_046` 同属 `v0.7.14` 发布窗口，但作为同版本的后续需求维护，不单独切到下一个版本。

## FEATURE_048: AAMP Dangerous Permissions Mode

**Status**: Completed
**Priority**: High
**Category**: Enhancement

### Overview

`FEATURE_048` 为 `kodax aamp serve` 增加一个显式的高风险开关 `--dangerous-full-permissions`，让异步 worker 在受控环境下可以跳过本地交互式 shell 授权，对非只读 `bash` 工具调用直接放行。

这个能力只覆盖 `AAMP` worker surface，不改变普通 CLI / REPL / ACP 的默认权限模型。

### Why now

`AAMP` worker 处理 `task.dispatch` 时没有人类交互终端可用，因此一旦命中需要确认的 shell 写操作，就会卡在“理论上该弹确认，但实际上无处可弹”的中间态。

这次补足的目标是：

- 让 `AAMP` 默认行为更明确，而不是隐式失败
- 给受控 demo / automation 环境一个显式的特权开关
- 保留一条最小宿主机保护边界，避免把高风险命令也一并放开

### Scope

- 在 `kodax aamp serve` 增加 `--dangerous-full-permissions`
- `AAMP runtime` 在执行工具前增加 `beforeToolExecute` 守卫
- 默认模式下继续允许只读 shell 命令
- 默认模式下阻断非只读 shell 命令，并给出明确提示
- 即使开启特权模式，仍然保留少量硬黑名单
- 为上述行为补齐 server 层测试和中英文文档

### Non-goals

- 不把该模式扩展到普通交互式 CLI / REPL 会话
- 不把该模式包装成默认推荐配置
- 不取消所有宿主机保护
- 不替代未来更细粒度的策略化权限系统

### Implemented behavior

#### 1. 默认 AAMP 模式只自动允许只读 shell

`git status --short`、`ls`、`cat` 这类只读命令继续自动放行。

#### 2. 非只读 shell 默认阻断

像 `rm -rf dist` 这类命令不会再走到“等待交互确认”的死路，而是直接返回阻断信息，并提示 operator 使用 `--dangerous-full-permissions`。

#### 3. 特权模式只对 AAMP 生效

当 `kodax aamp serve --dangerous-full-permissions` 启动时，AAMP worker 会跳过普通的非只读 shell 审批逻辑。

#### 4. 特权模式下仍保留硬黑名单

以下类型的命令仍被阻断：

- `sudo` / `su`
- `dd`
- `mkfs*`
- `shutdown` / `reboot` / `halt` / `poweroff`
- `curl | sh`
- `wget | sh`
- PowerShell `Remove-Item -Recurse -Force`

### Acceptance criteria

- [x] `kodax aamp serve` 支持 `--dangerous-full-permissions`
- [x] 默认 AAMP 模式下非只读 shell 命令不会再进入不可交互的审批死路
- [x] 默认 AAMP 模式下只读 shell 命令仍自动允许
- [x] 特权模式下允许非只读 shell 执行
- [x] 特权模式下仍保留一组最小硬黑名单
- [x] 已补齐 server 层行为测试和 README / README_CN 文档
