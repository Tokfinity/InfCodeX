## 总览

v0.7.36 三件套之后，Worker 派 child 是**异步**的（FEATURE_119 Pattern B），且 message queue（FEATURE_115）已经支持 agentId-scoped routing。现在缺的是：

1. **Worker 给在跑 child 续指令**：用户原意是 "review repo" → 派 read-only child，跑了 30s 后用户插话 "对了帮我看下 auth 模块"。Worker 可以选择 `send_message(child_id, "...")` 把追加要求送进 child 的 message queue，child 在下一个 LLM call 边界 drain 后处理。
2. **优雅终止跑中的 child**：child 跑偏了或用户撤回任务，Worker 调 `task_stop(child_id)` 走 child 的 abort signal 路径，child 当前 tool 跑完后退出（不强行 kill）。
3. **`dispatch_child_task.model_hint` 字段**：撤销 FEATURE_127（per-agent model tier hard-coded 默认）后，把"读 vs 写差异化模型"做成 LLM 自决的可选 hint 字段——Worker 调 dispatch 时按任务复杂度标 `'fast'`（短 lookup）/ `'balanced'`（默认）/ `'deep'`（重 reasoning research）。具体 routing 行为合并到 FEATURE_102 (v0.7.45) 的 capability profile，本 feature 只引入 schema 字段。

三件事是 v0.7.36 三件套的自然延伸，一起 ship 减少 PR 风险面。

## FEATURE_120: Async Child Steering — SendMessage + TaskStop + Dispatch model_hint Field

**Status**: Planned
**Priority**: High
**Category**: Internal / Architecture

### 背景

#### 当前缺口（v0.7.36 后）

| 能力 | v0.7.36 状态 | v0.7.39 缺口 |
|---|---|---|
| 派 child 不阻塞 | ✅ FEATURE_119 Pattern B | / |
| 用户插话 mid-turn drain | ✅ FEATURE_115 Sleep-gated drain | / |
| Worker 给在跑 child 续指令 | ❌ 没工具 | ✅ FEATURE_120 新增 send_message |
| 优雅终止跑中 child | ❌ 只能 abort 整个 Worker | ✅ FEATURE_120 新增 task_stop |
| 按 child 任务复杂度选模型 | ❌ 全部走父 model | ⚠️ FEATURE_120 加 schema 字段；routing 由 FEATURE_102 实施 |

#### Phase 0.7 实测对照

Claude Code coordinator mode 有：
- `SEND_MESSAGE_TOOL_NAME`：coordinator → worker 续指令
- `TASK_STOP_TOOL_NAME`：coordinator → worker 优雅终止
- agent definition 的 `model: 'haiku'|'sonnet'|'opus'` 字段（per-agent model tier）

KodaX 的对应物：
- send_message：基于 FEATURE_115 message queue 实现（队列已经有 agentId routing）
- task_stop：基于既有 AbortController per-child 拆分实现
- model_hint：schema 字段 + FEATURE_102 routing decision

### 设计

#### Step 0（**前置 / 强制**）：dispatch / registry / idle-yield 提升到 `@kodax/agent` orchestration 层

**为什么是前置 / 强制**：FEATURE_120 本身就要在 `packages/agent/src/orchestration/` 下新建 `task-registry.ts` + `send-message-router.ts`（per v0.7.35.1 ADR-021 包归属修正）。但当前 `childTaskRegistry` 还在 `packages/coding/src/types.ts`，`dispatch_child_task` 工具实现 + `child-executor` + `idle-yield` 状态机全部在 coding 包。如果先做 Step 1-5 不做 Step 0，就会出现：

- 新的 send_message / task_stop 读 `@kodax/agent` 的 task-registry，但 dispatch 仍写 `@kodax/coding` 的 registry → 两个 source of truth；
- idle-yield 状态机要触达 registry + queue 才能 wake，留在 coding 层会让 agent 层 orchestration 反向依赖 coding；
- 任何复用 `@kodax/agent` 的下游 agent（不只 KodaX coding）都拿不到通用 fan-out 能力 — 违背 ADR-021 包归属原则。

#### Step 1：`send_message(to, content)` 工具

```ts
// packages/coding/src/tools/send-message.ts
const sendMessageSchema = {
  to: z.string().describe('child task_id (from dispatch_child_task) or "*" for all running children'),
  content: z.string().describe('Message content. Will appear as <coordinator-instruction> in child next LLM turn.'),
};

async function toolSendMessage(input, ctx): Promise<string> {
  const { to, content } = input;
  if (to === '*') {
    // broadcast 留给 FEATURE_123 Peer-to-peer，本 feature 不实现
    return `[Tool Error] Broadcast 'to: *' not yet supported (planned in FEATURE_123 v0.7.44)`;
  }
  if (!ctx.childTaskRegistry.has(to)) {
    return `[Tool Error] Unknown task_id: ${to}`;
  }
  ctx.messageQueue.enqueue({
    priority: 'user',  // coordinator 续指令视同 user priority
    agentId: to,
    mode: 'prompt',
    content: `<coordinator-instruction>\n${content}\n</coordinator-instruction>`,
  });
  return `Message sent to ${to}. Will be processed at child's next LLM turn boundary.`;
}
```

#### Step 2：`task_stop(task_id, reason?)` 工具

```ts
// packages/coding/src/tools/task-stop.ts
const taskStopSchema = {
  task_id: z.string().describe('child task_id to stop'),
  reason: z.string().optional().describe('Optional reason logged in child final result'),
};

async function toolTaskStop(input, ctx): Promise<string> {
  const { task_id, reason } = input;
  const childAbort = ctx.childAbortControllers.get(task_id);
  if (!childAbort) return `[Tool Error] Unknown task_id: ${task_id}`;

  // 把 reason 入 child 的 message queue（让 child LLM 看到为什么被终止）
  if (reason) {
    ctx.messageQueue.enqueue({
      priority: 'user',
      agentId: task_id,
      mode: 'system-reminder',
      content: `<coordinator-stop-request>\nReason: ${reason}\nFinish your current tool call gracefully and emit a final summary.\n</coordinator-stop-request>`,
    });
  }
  // 设置 abort signal — child 在下次 signal.throwIfAborted() 时退出
  childAbort.abort(new Error(`Stopped by coordinator: ${reason ?? 'unspecified'}`));
  return `task_stop signal sent to ${task_id}. Child will exit at next abort check.`;
}
```

**关键**：task_stop 不强行 kill child 进程——LLM call 中的 child 会在响应回来后看到 abort signal 退出，跑中的 tool（如 npm test 90s）不强行打断（与 FEATURE_115 soft-pause 一致的"tool 原子性"原则）。

#### Step 5：Worker prompt 引导

新增段落（追加到 worker-role-prompt.ts）：

```
Async child steering protocol:
- After dispatch_child_task launches a child, you may steer it via:
  - send_message(to=task_id, content="...") — append instruction to child's queue.
    Child will see <coordinator-instruction> tag at next LLM turn.
  - task_stop(task_id, reason="...") — request child to gracefully exit.
    Child finishes current tool call then emits final summary.

When to send_message:
- User added a follow-up requirement mid-task that affects an in-flight child.
- You realized the child needs additional context after launch.
- DO NOT spam children — typical pattern is 0-1 send_message per child.

When to task_stop:
- Child went off-scope (e.g., started writing files when launched read-only).
- User cancelled the task that justified the child.
- Child is taking pathologically long with no progress signal.

model_hint guidance (in dispatch_child_task):
- Mark 'fast' only for trivial single-file lookups.
- Mark 'deep' only for multi-file research or analytical synthesis.
- When in doubt, omit (defaults to 'balanced').
```

## SDK Formalization (ADR-024) — npm 包正名 + Subpath Exports

## FEATURE_158: auto[llm] 信号化分类器 — 决策层级倒置 + Windows-flag 误判结构性修复

> Design lead by [ADR-025](../ADR.md#adr-025-autollm-信号化分类器--决策层级倒置--windows-flag-误判结构性修复-feature_158-v0739).
>
> **Status**: Design (2026-05-12) — Tier 0 list frozen, implementation pending.
>
> **背景一句话**：[FEATURE_092 (v0.7.33)](v0.7.33.md#feature_092-auto-mode-classifier--llm-reviewed-permission-tier-for-high-risk-tool-calls) 引入的 auto-mode LLM 分类器在实际运行中**~70% 时间被 REPL 同步硬规则 short-circuit 掉**，承诺的"LLM 综合判断"形同虚设；同时 [`looksLikePath`](../../packages/repl/src/permission/permission.ts#L597) 的 Windows-flag 启发式把 `findstr /R` / `dir /B` / `where /R` 等 cmd 内置工具 flag 误判为 POSIX 绝对路径，触发"Protected path"假阳性。本 feature 通过决策层级倒置 + 信号收集器 + Tier 0 绝对禁令兜底**结构性解决两个问题**。
>
> **不引入新旧并行路径**：REPL Step 2.5/3 在 auto 路径直接删除，不留 feature flag；engine 降级到 'rules' 时**重新激活原规则**做 defense-in-depth，不是 dual-path。

### 设计核心

三层金字塔（详见 ADR-025）：

```
Tier 1 (REPL 层, zero LLM cost)
  • bash-read 白名单（FEATURE_152 AST + 扩 git tag/stash list/describe/config --get）
  • --help fast-path（FEATURE_154 保留）
  • projection==='' 工具（Read/Grep/Glob/Todo/Task ...）
        ↓ miss
Tier 0 (Guardrail 层, LLM 之前, 不可 override)
  绝对禁令 5 条（清单 frozen, 见下）
        ↓ miss
Tier 2 (Guardrail 层, LLM 综合裁决)
  1. 同步收集 signals[] (非决策)
  2. classify(action, signals, transcript, user_rules) with speculative race
  3. allow / block / escalate (escalate 时 UI 用 signals 渲染 Scope/Risk)
        ↓ engine='rules' 降级时
Fallback (REPL Step 2.5/3 重新激活)
  defense-in-depth：denial 3/20 或 breaker 5/10m 后等价今天的 auto-in-project
```

### Tier 0 绝对禁令（清单 frozen，扩张需新 ADR）

| # | 模式 | 触发判定 | Rationale |
|---|---|---|---|
| 1 | `rm -rf /` 或 `rm -rf ~` | AST argv[0]==='rm' && flags 含 r+f && target 是 `/` / `~` / `$HOME` | 删根目录，无任何合法场景 |
| 2 | `mkfs.* / fdisk / format X:` | AST argv[0] ∈ `{mkfs, mkfs.*, fdisk, format}` | 格式化磁盘 |
| 3 | `dd if=... of=/dev/sd*` | AST argv[0]==='dd' && of= 指向 `/dev/sd*` / `/dev/nvme*` / `\\.\PhysicalDrive*` | 裸盘写覆盖 |
| 4 | Fork bomb `:(){ :\|:& };:` | 命令字符串包含 `:()\s*\{\s*:\|:&\s*\}\s*;:` 子串 | 拒绝服务 |
| 5 | 写入 `~/.kodax/` | path-extractor 识别 write 目标在 `getAgentConfigHome()` 内 | credentials 红线（无 IPC 例外；合法编辑走 `kodax config set`） |

**纪律**：清单进 ADR-025 评审后冻结。每加 1 条须新立 ADR addendum 答两个问题：(a) 是否任何情境下都不该被允许？(b) LLM 在 prompt 注入下是否有放行风险？两个都"是"才能加。

### Signals 类型与收集器

新模块：`packages/coding/src/guardrails/auto-mode/signals.ts`

```typescript
export type ToolCallSignal =
  | { kind: 'dangerous_pattern'; pattern: string; severity: 'high' | 'medium' }
  | { kind: 'protected_path'; path: string; zone: 'project-kodax' | 'user-kodax' }
  | { kind: 'outside_project'; path: string }
  | { kind: 'shell_redirect_outside'; target: string }
  | { kind: 'package_install'; manager: 'npm' | 'pnpm' | 'yarn' | 'pip' | 'cargo' | 'apt' | 'brew' }
  | { kind: 'git_write'; verb: 'commit' | 'push' | 'reset' | 'clean' | 'rebase' | 'cherry-pick' | 'revert' }
  | { kind: 'network'; tool: 'curl' | 'wget' | 'fetch' }
  | { kind: 'file_modification'; targets: readonly string[] };

export interface SignalCollector {
  readonly toolNames: ReadonlySet<string>;
  collect(call: RunnerToolCall, projectRoot: string): readonly ToolCallSignal[];
}

export function collectAllSignals(
  call: RunnerToolCall,
  projectRoot: string,
  collectors: readonly SignalCollector[],
): readonly ToolCallSignal[];
```

**关键约束**：收集器**只描述事实**。`dangerous_pattern` 信号说"匹配了 `git push --force` 模式"，**不**说"该不该确认"——决定权交给 LLM。

收集器对应到现有规则的拆解：

| 现有规则函数 | 拆解为 SignalCollector | 退化兜底 |
|---|---|---|
| [`classifyBashCommand`](../../packages/coding/src/permissions/bash-classifier.ts) 返 `level: 'dangerous'` | `dangerousPatternCollector` 输出 `dangerous_pattern` 信号 | 9 类规则全保留为信号；Tier 0 子集（rm -rf / mkfs / dd / 格式化）升 hard block |
| [`isCommandOnProtectedPath`](../../packages/repl/src/permission/permission.ts#L698) | `protectedPathCollector` 输出 `protected_path` 信号 | `~/.kodax/` 写命中升 Tier 0；其余作 signal |
| [`getBashOutsideProjectWriteRisk`](../../packages/repl/src/permission/permission.ts) | `outsideProjectCollector` 输出 `shell_redirect_outside` 信号 | 不升 Tier 0（用户经常合法写 `/tmp/...`） |
| pattern detect `curl/wget` | `networkCollector` | 不升 |
| pattern detect `npm install` / `pnpm add` 等 | `packageInstallCollector` | 不升 |

### Speculative Classify

新模块：`packages/coding/src/guardrails/auto-mode/speculative.ts`

```typescript
const DEFAULT_WINDOW_MS = 500;

export async function speculativeClassify<T>(
  classifyPromise: Promise<T>,
  windowMs: number = readWindowFromEnv() ?? DEFAULT_WINDOW_MS,
): Promise<{ kind: 'resolved'; value: T } | { kind: 'window-expired' }>;
```

集成位置：[`guardrail.ts:beforeTool`](../../packages/coding/src/guardrails/auto-mode/guardrail.ts) Tier 2 路径——`classify(...)` 调用包一层 `speculativeClassify`，window 内返回 allow 则直放，否则 escalate 走 confirm 流程；用户确认期间 classify 仍在后台跑（不取消）。

### REPL 层瘦身

[`InkREPL.tsx:beforeToolExecute`](../../packages/repl/src/ui/InkREPL.tsx) 在 `mode==='auto' && engine==='llm'` 时仅保留 Tier 1：

```typescript
// === Auto[llm] mode: defer to guardrail ===
if (mode === 'auto' && autoModeEngineRef.current === 'llm') {
  // Tier 1 fast-path
  if (tool === 'bash') {
    const command = (input.command as string) ?? '';
    if (isHelpCommand(command) || isBashReadCommand(command)) return true;
  }
  if (isAutoModeAllowlistedTool(tool)) return true;

  // 其他全部交给 Runner.beforeTool guardrail
  return true;
}

// === plan / accept-edits / auto[rules-fallback]: 原路径不变 ===
// (Step 2.5 dangerous + Step 3 protected path + Step 4 confirmTools 全保留)
```

**关键**：`autoModeEngineRef.current === 'llm'` 这个判定让 engine 降级到 'rules' 时**自动重新激活**原硬规则路径——通过 `onEngineChange` 回调把 guardrail state 暴露给 REPL。

### Engine 降级回路

[`AutoModeToolGuardrail`](../../packages/coding/src/guardrails/auto-mode/guardrail.ts) 已有 `onEngineChange` callback，本 feature **复用**接线到 REPL：

```typescript
// InkREPL.tsx 启动期
const autoModeEngineRef = useRef<AutoModeEngine>('llm');
const guardrail = createAutoModeToolGuardrail({
  ...config,
  onEngineChange: (engine) => {
    autoModeEngineRef.current = engine;
    addStatusMessage(`[auto-mode] engine → ${engine}`);
  },
});
```

降级触发时 (denial 3/20 或 breaker 5/10m)，下一次 `beforeToolExecute` 自动走 Step 2.5/3 全规则路径。状态栏显示 `auto[rules]` 让用户感知。手动恢复仍走 `/auto-engine llm` slash command (FEATURE_092 已落)。

### UI Scope/Risk 渲染源迁移

[`tool-confirmation.ts:buildToolConfirmationDisplay`](../../packages/repl/src/common/tool-confirmation.ts) 在 auto 模式 escalate 时**从 signals 而非 input marker 取值**：

```typescript
// 旧逻辑（保留给 plan/accept-edits）：
const scope = input._outsideProject === true ? t("scope.outside")
            : input._alwaysConfirm === true ? t("scope.protected")
            : undefined;

// 新逻辑（auto 模式 escalate 时走）：
const signals = input._classifierSignals as ToolCallSignal[] | undefined;
const scope = signals?.find(s => s.kind === 'outside_project') ? t("scope.outside")
            : signals?.find(s => s.kind === 'protected_path') ? t("scope.protected")
            : undefined;
const risks = signals?.flatMap(s => signalToRiskLabel(s)) ?? [];
```

`_classifierSignals` 由 guardrail 在 `escalateOrAsk` 时附加到 input 副本。**plan / accept-edits 模式行为不变**——这些模式不走 guardrail，input marker 路径保留。
