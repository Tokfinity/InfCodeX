# v0.7.39 Feature Designs

> 中文标题：`v0.7.39 Feature 设计`
>
> Version: `v0.7.39`
>
> Status: Planned (not yet released)
>
> Theme: **Async Child Steering + Chat-While-Waiting** — 在 v0.7.36 FEATURE_119（Pattern B Launch+Await）+ FEATURE_115（Message Queue）+ FEATURE_114（Worker+Evaluator V2）的底座上，做两件相互独立但都围绕"异步子任务"主题的工作：
>
> 1. **FEATURE_120 Async Child Steering**：引入 `send_message` + `task_stop` 工具让 Worker 操控在跑 child（v0.7.36 三件套的自然延伸）。
> 2. **FEATURE_155 Chat-While-Waiting**：删 `await_child_task` 工具，对齐 Claude Code 的 idle-yield 模式——Worker dispatch 后 turn 自然 idle，子任务完成 + 用户输入都通过同一 message queue 回灌。**用户体验是核心驱动**：FEATURE_119 现状下用户在 Worker await 期间无法立即聊天 / 修改任务方向；CC 借鉴改造后用户可即时输入 + Worker 即时响应。

---

## 总览

v0.7.36 三件套之后，Worker 派 child 是**异步**的（FEATURE_119 Pattern B），且 message queue（FEATURE_115）已经支持 agentId-scoped routing。现在缺的是：

1. **Worker 给在跑 child 续指令**：用户原意是 "review repo" → 派 read-only child，跑了 30s 后用户插话 "对了帮我看下 auth 模块"。Worker 可以选择 `send_message(child_id, "...")` 把追加要求送进 child 的 message queue，child 在下一个 LLM call 边界 drain 后处理。
2. **优雅终止跑中的 child**：child 跑偏了或用户撤回任务，Worker 调 `task_stop(child_id)` 走 child 的 abort signal 路径，child 当前 tool 跑完后退出（不强行 kill）。
3. **`dispatch_child_task.model_hint` 字段**：撤销 FEATURE_127（per-agent model tier hard-coded 默认）后，把"读 vs 写差异化模型"做成 LLM 自决的可选 hint 字段——Worker 调 dispatch 时按任务复杂度标 `'fast'`（短 lookup）/ `'balanced'`（默认）/ `'deep'`（重 reasoning research）。具体 routing 行为合并到 FEATURE_102 (v0.7.45) 的 capability profile，本 feature 只引入 schema 字段。

三件事是 v0.7.36 三件套的自然延伸，一起 ship 减少 PR 风险面。

## FEATURE_120: Async Child Steering — SendMessage + TaskStop + Dispatch model_hint Field

**Status**: Planned
**Priority**: High
**Category**: Internal / Architecture

### 背景

#### 当前缺口（v0.7.36 后）

| 能力 | v0.7.36 状态 | v0.7.39 缺口 |
|---|---|---|
| 派 child 不阻塞 | ✅ FEATURE_119 Pattern B | / |
| 用户插话 mid-turn drain | ✅ FEATURE_115 Sleep-gated drain | / |
| Worker 给在跑 child 续指令 | ❌ 没工具 | ✅ FEATURE_120 新增 send_message |
| 优雅终止跑中 child | ❌ 只能 abort 整个 Worker | ✅ FEATURE_120 新增 task_stop |
| 按 child 任务复杂度选模型 | ❌ 全部走父 model | ⚠️ FEATURE_120 加 schema 字段；routing 由 FEATURE_102 实施 |

#### Phase 0.7 实测对照

Claude Code coordinator mode 有：
- `SEND_MESSAGE_TOOL_NAME`：coordinator → worker 续指令
- `TASK_STOP_TOOL_NAME`：coordinator → worker 优雅终止
- agent definition 的 `model: 'haiku'|'sonnet'|'opus'` 字段（per-agent model tier）

KodaX 的对应物：
- send_message：基于 FEATURE_115 message queue 实现（队列已经有 agentId routing）
- task_stop：基于既有 AbortController per-child 拆分实现
- model_hint：schema 字段 + FEATURE_102 routing decision

### 设计

#### Step 0（**前置 / 强制**）：dispatch / registry / idle-yield 提升到 `@kodax/agent` orchestration 层

**为什么是前置 / 强制**：FEATURE_120 本身就要在 `packages/agent/src/orchestration/` 下新建 `task-registry.ts` + `send-message-router.ts`（per v0.7.35.1 ADR-021 包归属修正）。但当前 `childTaskRegistry` 还在 `packages/coding/src/types.ts`，`dispatch_child_task` 工具实现 + `child-executor` + `idle-yield` 状态机全部在 coding 包。如果先做 Step 1-5 不做 Step 0，就会出现：

- 新的 send_message / task_stop 读 `@kodax/agent` 的 task-registry，但 dispatch 仍写 `@kodax/coding` 的 registry → 两个 source of truth；
- idle-yield 状态机要触达 registry + queue 才能 wake，留在 coding 层会让 agent 层 orchestration 反向依赖 coding；
- 任何复用 `@kodax/agent` 的下游 agent（不只 KodaX coding）都拿不到通用 fan-out 能力 — 违背 ADR-021 包归属原则。

所以 Step 0 必须先做。这条线索 2026-05-11 user 提出后正式加入 FEATURE_120 设计。

#### Step 1：`send_message(to, content)` 工具

```ts
// packages/coding/src/tools/send-message.ts
const sendMessageSchema = {
  to: z.string().describe('child task_id (from dispatch_child_task) or "*" for all running children'),
  content: z.string().describe('Message content. Will appear as <coordinator-instruction> in child next LLM turn.'),
};

async function toolSendMessage(input, ctx): Promise<string> {
  const { to, content } = input;
  if (to === '*') {
    // broadcast 留给 FEATURE_123 Peer-to-peer，本 feature 不实现
    return `[Tool Error] Broadcast 'to: *' not yet supported (planned in FEATURE_123 v0.7.44)`;
  }
  if (!ctx.childTaskRegistry.has(to)) {
    return `[Tool Error] Unknown task_id: ${to}`;
  }
  ctx.messageQueue.enqueue({
    priority: 'user',  // coordinator 续指令视同 user priority
    agentId: to,
    mode: 'prompt',
    content: `<coordinator-instruction>\n${content}\n</coordinator-instruction>`,
  });
  return `Message sent to ${to}. Will be processed at child's next LLM turn boundary.`;
}
```

#### Step 2：`task_stop(task_id, reason?)` 工具

```ts
// packages/coding/src/tools/task-stop.ts
const taskStopSchema = {
  task_id: z.string().describe('child task_id to stop'),
  reason: z.string().optional().describe('Optional reason logged in child final result'),
};

async function toolTaskStop(input, ctx): Promise<string> {
  const { task_id, reason } = input;
  const childAbort = ctx.childAbortControllers.get(task_id);
  if (!childAbort) return `[Tool Error] Unknown task_id: ${task_id}`;

  // 把 reason 入 child 的 message queue（让 child LLM 看到为什么被终止）
  if (reason) {
    ctx.messageQueue.enqueue({
      priority: 'user',
      agentId: task_id,
      mode: 'system-reminder',
      content: `<coordinator-stop-request>\nReason: ${reason}\nFinish your current tool call gracefully and emit a final summary.\n</coordinator-stop-request>`,
    });
  }
  // 设置 abort signal — child 在下次 signal.throwIfAborted() 时退出
  childAbort.abort(new Error(`Stopped by coordinator: ${reason ?? 'unspecified'}`));
  return `task_stop signal sent to ${task_id}. Child will exit at next abort check.`;
}
```

**关键**：task_stop 不强行 kill child 进程——LLM call 中的 child 会在响应回来后看到 abort signal 退出，跑中的 tool（如 npm test 90s）不强行打断（与 FEATURE_115 soft-pause 一致的"tool 原子性"原则）。

#### Step 3：`KodaXToolExecutionContext` 扩展

```ts
interface KodaXToolExecutionContext {
  // ... 既有
  childTaskRegistry: Map<string, Promise<KodaXChildExecutionResult>>;  // FEATURE_119
  childAbortControllers: Map<string, AbortController>;                 // 新增 FEATURE_120
  messageQueue: KodaXMessageQueue;                                     // FEATURE_115
}
```

每个 dispatch_child_task launch 时同时分配独立的 AbortController，存入 `childAbortControllers`。child 完成或 task_stop 后从两个 map 一起清理。

#### Step 4：`dispatch_child_task.model_hint` schema 字段

```ts
const dispatchChildTaskSchema = {
  // ... 既有字段（id / objective / readOnly / scope_summary / evidence_refs / constraints）
  model_hint: z.enum(['fast', 'balanced', 'deep']).optional()
    .describe(`Optional hint for routing this child to a tier-appropriate model.
'fast' for short lookups (read 1-2 files, simple grep);
'balanced' (default) for normal subtasks;
'deep' for heavy reasoning (multi-file analysis, complex audit).
Routing decision is made by FEATURE_102 capability profile (v0.7.45).`),
};
```

**v0.7.39 阶段**：schema 字段引入，但 routing 行为是 **no-op**——所有 child 仍走父 model。FEATURE_102 (v0.7.45) 上线后激活实际 routing。这是为了让 prompt eval 数据先开始积累（看 LLM 是否会自然标 hint）。

#### Step 5：Worker prompt 引导

新增段落（追加到 worker-role-prompt.ts）：

```
Async child steering protocol:
- After dispatch_child_task launches a child, you may steer it via:
  - send_message(to=task_id, content="...") — append instruction to child's queue.
    Child will see <coordinator-instruction> tag at next LLM turn.
  - task_stop(task_id, reason="...") — request child to gracefully exit.
    Child finishes current tool call then emits final summary.

When to send_message:
- User added a follow-up requirement mid-task that affects an in-flight child.
- You realized the child needs additional context after launch.
- DO NOT spam children — typical pattern is 0-1 send_message per child.

When to task_stop:
- Child went off-scope (e.g., started writing files when launched read-only).
- User cancelled the task that justified the child.
- Child is taking pathologically long with no progress signal.

model_hint guidance (in dispatch_child_task):
- Mark 'fast' only for trivial single-file lookups.
- Mark 'deep' only for multi-file research or analytical synthesis.
- When in doubt, omit (defaults to 'balanced').
```

**Step 1-5（功能层）**：

1. **send_message 路由正确**：Worker 调 `send_message(to=child_id, content="...")`，child 在下一个 LLM turn 边界 drain 看到 `<coordinator-instruction>` 标签
2. **task_stop 优雅终止**：child 跑中调 task_stop，当前 tool 完成后 child 退出；childTaskRegistry / childAbortControllers 清理
3. **task_stop reason 入 child**：child final result 中可见 reason；Worker 拿到 child 结果后能向用户说明终止原因
4. **未知 task_id 报错**：send_message / task_stop 对未知 id 返 `[Tool Error]`
5. **broadcast `to: '*'` 暂禁**：明确返 `[Tool Error] Broadcast not yet supported (FEATURE_123 v0.7.44)`
6. **per-child abort 独立**：parent abort 整个 Worker 仍走既有 AbortController（ESC abort 路径）；per-child task_stop 不影响 parent
7. **model_hint schema 接受三档**：dispatch_child_task 接受 `'fast'|'balanced'|'deep'` 不报错；wire-level 在 v0.7.39 仍走父 model（routing no-op）
8. **Worker 自主使用 steering**：FEATURE_104 prompt eval 验证 Worker 在 "用户 mid-task 加要求"、"child 跑偏"、"child 卡死"三类场景下能正确选择 send_message / task_stop
9. **跨 family 验证**：4 family LLM steering 工具使用率 / 正确率 max-min spread ≤ 15pp
10. **无回归**：FEATURE_115 / FEATURE_119 / FEATURE_155 既有路径全绿；既有 dispatch_child_task 调用方（不带 model_hint）行为不变

### 非目标

- **不** 实现 `to: '*'` broadcast（v0.7.44 FEATURE_123）
- **不** 实现 child-to-child SendMessage（v0.7.44 FEATURE_123）
- **不** 在 v0.7.39 激活 model_hint routing 行为（v0.7.45 FEATURE_102）
- **不** 强行 kill child 进程（task_stop 走 abort signal，等 tool 跑完）
- **不** 引入 send_message 优先级 vs task_stop 优先级冲突机制（FEATURE_115 已有 priority='user'，足够）
- **不** 持久化 childAbortControllers（重启丢失，与 childTaskRegistry / message queue 一致）
- **不** 实现 Coordinator Mode 完整 wrapper（FEATURE_122 v0.7.41 引入 thinking framework prompt；hard tool restriction FEATURE_126 v0.8.x 数据驱动决定）

## FEATURE_155: Chat-While-Waiting — Remove `await_child_task`, Adopt Claude-Code Idle-Yield Pattern

**Status**: Shipped through Slice C3 (v0.7.39, 2026-05-10 user sign-off → 2026-05-11 Phase C complete; D1 docs / D2 final eval pending)
**Priority**: High
**Category**: Internal / Architecture + Enhancement / UX

### 背景

FEATURE_119 (v0.7.36) 引入 Pattern B：`dispatch_child_task` 立即返回 `task_id`，child 后台跑；Worker 后续调 `await_child_task({task_id})` 拿结果。FEATURE_148 (v0.7.37) 加了 anti-immediate-await prompt 反例，eval 跑 0/75 degenerate-rate ✅。

但**实际 v0.7.38 生产用户测试**显示，Worker 在"edit + build"多步任务上仍然 dispatch 完立即连续 await（截屏证据：5 个 dispatch 后 5 个 await 一字排开）；FEATURE_114 Slice 6 V2 baseline eval 实测 V1 Scout 10% / V2 Worker 45% commit 计划列表（4 alias × 5 run）。**根因**：await 工具一旦存在，LLM 无论 prompt 怎么教都倾向于"派出去就立刻收"的串行心智模型。

Claude Code 调研（`c:/Works/claudecode`，2026-05-10 thorough scout）证明 CC 的"chat while waiting" UX **不靠任何并行对话层**——靠的是**根本不存在 `await_child_task` 这种工具**：

1. `AgentTool.tsx:733` 用 `void` 关键字显式丢弃 sub-agent promise，工具立即返回 `{ status: 'async_launched', agentId }`
2. Main agent 在 dispatch 完之后没有更多 tool call，turn 自然 idle
3. `QueryGuard` 从 `running` → `idle`
4. 用户输入立即被处理（不再 queue 等待 main turn 结束）
5. Sub-agent 完成时通过 `LocalAgentTask.tsx:197-262` 的 `enqueueAgentNotification` 把结果包成 `<task_notification>` XML 入消息队列（priority `'later'`）
6. 下一个 turn 处理时，main agent 看到 `<task_notification>` 就像收到一条 user message——LLM 自然知道"哦 child 干完了"

**关键洞察**：用户感知的"agent 在等，但能聊天"——实际是"agent 已经完事 idle 了，只是子任务结果还没回来"。同一个消息队列承载两种事件（user input + task completion），靠 priority 区分顺序。

### 设计目标

KodaX 删 `await_child_task` 工具，对齐 CC idle-yield 模式。从用户视角看：

```
User: review一下 5 个包
Worker: dispatch_child_task × 5
Worker: "5 个 review 已派出，等结果。"  ← turn 自然结束，idle
[用户立即可输入]
User: "那个 packages/ai 我不想要了"
Worker: "好，我会 cancel 它，等其他 4 个就行。"  ← 立刻响应
[10 秒后]
<task-completed task_id="..." result="..."> ← 队列回灌
Worker: "packages/agent review 结果：..."  ← 新一轮
```

### Phase 划分（10 commit / ~5 天 / 单 patch release）

#### Phase A — 架构基础（无 LLM 可见变化）

**Slice A1（已 ship，commit `6a420504`）— idle-yield foundation utilities**：
- 新模块 [`packages/coding/src/task-engine/_internal/managed-task/idle-yield.ts`](../../packages/coding/src/task-engine/_internal/managed-task/idle-yield.ts)
- `detectIdleYield(snapshot)`：纯谓词，3 条件 AND（last assistant 0 tool calls / pending children > 0 / 未 emit_handoff）
- `waitForWakeEvent(options)`：child Promise / message queue poll / abort signal 三路 race，返回 `{ kind: 'child-completed' | 'child-failed' | 'messages-arrived' | 'aborted' }`
- 16 个 unit test 锁定语义边界
- 不改 `runner-driven.ts`——纯 utility 落地，等 Slice A2 wire

**Slice A2（已 ship，commits `1f0d1eab` + `bbf747d3`）— runner-driven outer loop wiring（合并原 A2+A3）**：
- 在 `runManagedTaskViaRunnerInner` 内将 `Runner.run` 包进 `while (true)`，gated by `KODAX_IDLE_YIELD=true`（默认 OFF）。
- 检测 idle-yield → `waitForWakeEvent` → `composeIdleYieldUserMessage` 把 wake 内容拼成合成 user message → 再次进入 `Runner.run`，Worker 接续。
- 加 3 个工具函数：`isIdleYieldEnabled`（env gate）、`countLastAssistantToolCalls`（snapshot helper）、`composeIdleYieldUserMessage`（wake → KodaXMessage）。
- 守卫：`IDLE_YIELD_MAX_ITERATIONS = 64` 防止 prompt bug 卡死循环；abort signal 整个 race 内即时退出。
- 重构副作用：guardrails / toolObserver 提为 const（无状态 factory，单纯避免循环内重复构造）；comment 自我审 tweak。
- Test：33 个 idle-yield 单元 + 2 个 runner-driven e2e（happy-path resume + flag-off no-resume），全部绿。flag OFF 时 113 个原有测试零回归。

> 之前规划的"Slice A2 drain trigger"在调研中发现不需要——`waitForWakeEvent` 在 outer loop 直接 `dequeue('background')`，绕开 mid-turn drain；A2/A3 合并为单 wiring slice。
